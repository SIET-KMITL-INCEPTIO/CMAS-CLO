2.1 ทฤษฎีด้านการวัดและประเมินผลลัพธ์การเรียนรู้

2.1.1 การจัดการศึกษาที่มุ่งผลลัพธ์ (Outcome-Based Education: OBE)

คืออะไร — แนวคิดการจัดการศึกษาที่เริ่มต้นจากการกำหนดว่า "ผู้เรียนต้องทำอะไรได้เมื่อจบ" ก่อน แล้วจึงย้อนกลับไปออกแบบเนื้อหา วิธีสอน และวิธีวัดผลให้สอดคล้องกัน (Spady, 1994) ต่างจากการจัดการศึกษาแบบเดิมที่เริ่มจากเนื้อหาที่จะสอนแล้วค่อยวัดว่าจำได้เท่าไร

เกี่ยวข้องกับโครงงานอย่างไร — โครงงานนี้ตั้งอยู่บนสมมติฐานของ OBE ทั้งหมด กล่าวคือ ระบบไม่ได้เก็บ "คะแนนสอบ" เป็นเป้าหมายสุดท้าย แต่เก็บคะแนนกิจกรรมเพื่อแปลงกลับเป็นคำตอบว่า ผู้เรียนบรรลุผลลัพธ์การเรียนรู้ข้อใดบ้าง ซึ่งเป็นเหตุผลที่ฐานข้อมูลไม่มีคอลัมน์ "คะแนน CLO" ให้กรอกโดยตรง (ASM-02 ใน srs §2.3) — คะแนน CLO ต้องเป็นค่าคำนวณเสมอ

2.1.2 ผลลัพธ์การเรียนรู้ระดับหลักสูตรและระดับรายวิชา (PLO / CLO)

ระดับ ชื่อ ขอบเขต สถานะในโครงงานนี้
หลักสูตร PLO (Program Learning Outcomes) สิ่งที่บัณฑิตทำได้เมื่อจบหลักสูตร อยู่นอกขอบเขต v1
รายวิชา CLO (Course Learning Outcomes) สิ่งที่ผู้เรียนทำได้เมื่อจบรายวิชา ขอบเขตหลักของระบบ
หน่วยการเรียน จุดประสงค์เชิงพฤติกรรม (Behavioral Objectives) พฤติกรรมย่อยที่สังเกต/วัดได้ภายใต้ CLO แต่ละข้อ มีในระบบ (BehavioralObjective)

CLO ต้องเขียนด้วยคำกริยาที่สังเกตได้และวัดได้ เช่น "ออกแบบ" "วิเคราะห์" "อธิบาย" ไม่ใช่คำที่วัดไม่ได้อย่าง "เข้าใจ" หรือ "ตระหนักถึง" ข้อกำหนดนี้เป็นเหตุผลที่ระบบบังคับให้ CLO ทุกข้อต้องมีเกณฑ์ผ่าน (threshold) เป็นตัวเลขร้อยละ — ถ้า CLO เขียนแบบวัดไม่ได้ จะกรอก threshold ไม่ได้ตั้งแต่ต้น

2.1.3 การจัดวางแนวให้สอดคล้องเชิงโครงสร้าง (Constructive Alignment)

คืออะไร — หลักการของ Biggs (1996) ที่ระบุว่าผลลัพธ์การเรียนรู้ กิจกรรมการเรียนการสอน และวิธีการวัดผล ต้อง "เรียงตรงแนวเดียวกัน" ถ้าอย่างใดอย่างหนึ่งหลุดแนว การประเมินจะไม่ได้ วัดสิ่งที่ตั้งใจจะวัด

เกี่ยวข้องกับโครงงานอย่างไร — นี่คือทฤษฎีที่อยู่เบื้องหลังตาราง AssessmentCriteria โดยตรง ระบบบังคับให้ทุกกิจกรรมการประเมินต้องถูกผูกกับ CLO อย่างน้อยหนึ่งข้อ พร้อมระบุน้ำหนักเป็นตัวเลข ไม่ใช่เพียงเครื่องหมายถูก (FR-44) เพราะการทำเครื่องหมายถูกบอกได้แค่ว่า "เกี่ยวข้อง" แต่บอกไม่ได้ว่า "เกี่ยวข้องเท่าไร" ซึ่งไม่พอสำหรับการคำนวณ นอกจากนี้ระบบยังเตือนเมื่อมี CLO ที่ไม่มีกิจกรรมใดวัดเลย (FR-48) เพราะนั่นคืออาการของการหลุดแนวที่พบบ่อยที่สุด

2.1.4 การจำแนกจุดมุ่งหมายทางการศึกษา (Bloom's Taxonomy ฉบับปรับปรุง)

คืออะไร — การจัดลำดับพฤติกรรมการเรียนรู้ด้านพุทธิพิสัย 6 ระดับ ตามฉบับปรับปรุงของ Anderson และ Krathwohl (2001): จำ (Remember) → เข้าใจ (Understand) → ประยุกต์ (Apply) → วิเคราะห์ (Analyze) → ประเมินค่า (Evaluate) → สร้างสรรค์ (Create)

เกี่ยวข้องกับโครงงานอย่างไร — ใช้เป็นกรอบให้อาจารย์เลือกคำกริยาตอนเขียน CLO และจุดประสงค์ เชิงพฤติกรรม ระบบไม่ได้บังคับระดับ Bloom ในฐานข้อมูล (ไม่มีคอลัมน์ bloomLevel ใน v1) เพราะการบังคับจะทำให้ระบบผูกกับกรอบใดกรอบหนึ่งจนใช้กับหลักสูตรที่ใช้กรอบอื่นไม่ได้ — ถือเป็นข้อจำกัดที่ตั้งใจ และเป็นข้อเสนอแนะสำหรับการพัฒนาต่อในบทที่ 5

2.1.5 การทำแผนที่การประเมิน (Assessment Mapping) และเมทริกซ์น้ำหนัก

หัวใจเชิงคณิตศาสตร์ของระบบคือเมทริกซ์สองมิติ ระหว่างกิจกรรมการประเมิน (แถว) กับ CLO (คอลัมน์) โดยแต่ละช่องเก็บน้ำหนักเป็นร้อยละ ทฤษฎีที่รองรับคือการที่คะแนนของกิจกรรมหนึ่งสามารถ แตกออกไปวัดผลลัพธ์ได้มากกว่าหนึ่งข้อพร้อมกัน ในสัดส่วนที่ต่างกัน

ข้อกำหนดที่ตามมาจากทฤษฎีนี้ (CR-01 ใน srs §3):

ค่า ความหมาย เงื่อนไขบังคับ
Activity.weight สัดส่วนของกิจกรรมต่อคะแนนรวมรายวิชา ผลรวมทุกกิจกรรมในวิชา = 100
AssessmentCriteria.weight สัดส่วนของกิจกรรมนั้นที่ใช้วัด CLO แต่ละข้อ ผลรวมต่อ 1 กิจกรรม = 100
น้ำหนักของ CLO ไม่เก็บ — เป็นค่าอนุพัทธ์ คำนวณตาม CR-02

การไม่เก็บน้ำหนักของ CLO เป็นการตัดสินใจเชิงทฤษฎี ไม่ใช่เชิงเทคนิค: ถ้าเก็บทั้งสองที่ ค่าทั้งสองจะขัดแย้งกันเองได้ทันทีที่มีการแก้ไขด้านใดด้านหนึ่ง ซึ่งเป็นปัญหาความไม่สอดคล้อง ของข้อมูล (data inconsistency) แบบเดียวกับที่การทำ Normalization พยายามกำจัด (§2.2.4)

2.1.6 การคำนวณระดับการบรรลุผลลัพธ์การเรียนรู้ (CLO Attainment)

ระบบใช้แนวทาง two-level attainment ที่แพร่หลายในงานประกันคุณภาพการศึกษา คือแยกการวัด เป็นสองระดับที่ตอบคำถามคนละข้อ

ระดับที่ 1 — รายบุคคล (CR-03) ตอบว่า "นักศึกษาคนนี้บรรลุ CLO ข้อนี้หรือยัง"

                Σ over a  [ score(s,a) / maxScore(a) × Criteria.weight(a,c) ]
cloScore(s,c) = ─────────────────────────────────────────────────────────── × 100
                          Σ over a  [ Criteria.weight(a,c) ]

จุดสำคัญเชิงทฤษฎีคือตัวหารนับเฉพาะกิจกรรมที่มีคะแนนแล้ว ผลคือค่าที่ได้เป็น "ร้อยละความสำเร็จเท่าที่ประเมินไปแล้ว" ไม่ใช่ "ร้อยละของทั้งเทอม" ซึ่งทำให้ระบบรายงานผล ระหว่างภาคการศึกษาได้โดยไม่ต้องรอคะแนนครบ — และนี่คือกลไกที่ตอบสาเหตุรากของปัญหาโดยตรง (สมมติฐาน H2)

ระดับที่ 2 — ระดับรายวิชา (CR-04) ตอบว่า "การสอนวิชานี้ทำให้ผู้เรียนส่วนใหญ่บรรลุ CLO ข้อนี้หรือไม่"

attainment(c) = (จำนวนนักศึกษาที่ผ่าน c / จำนวนนักศึกษาที่มีคะแนนพอจะคำนวณ c) × 100
CLO c "บรรลุ"  ⟺  attainment(c) ≥ Class Target

การแยก "ไม่มีคะแนน" ออกจาก "ได้ 0 คะแนน" — ข้อกำหนดนี้ (FR-62, FR-84) มาจากทฤษฎีการวัด โดยตรง: ค่าที่ไม่มีการวัด (missing) กับค่าที่วัดแล้วได้ศูนย์ เป็นข้อมูลคนละชนิดกัน การนำค่าว่างมานับเป็น 0 จะทำให้ค่าเฉลี่ยเอนต่ำอย่างเป็นระบบ (systematic bias) และรายงาน นักศึกษาที่อาจารย์ยังไม่ได้ตรวจงานว่าเป็นกลุ่มเสี่ยง ระบบจึงคืนค่า null และแสดง —

2.1.7 การประเมินเพื่อพัฒนาและการประเมินเพื่อตัดสิน (Formative vs Summative)

ประเภท จังหวะเวลา คำถามที่ตอบ ใช้ทำอะไรได้
Summative สิ้นภาคการศึกษา ผู้เรียนได้เกรดอะไร ตัดสินผล — แก้ไขอะไรไม่ทันแล้ว
Formative ระหว่างภาคการศึกษา ตอนนี้ใครยังไม่บรรลุข้อใด แทรกแซงช่วยเหลือได้ทัน

วิธีทำงานด้วย Excel แบบเดิมให้ผลแบบ summative เท่านั้น เพราะต้องรอรวมทุกไฟล์จึงจะคำนวณได้ โครงงานนี้จึงไม่ได้แค่ทำให้การคำนวณเร็วขึ้น แต่เปลี่ยนประเภทของการประเมิน — ประเด็นนี้คือแกนของบทที่ 5 และควรเขียนไว้ในเล่มอย่างชัดเจน

2.1.8 กรอบมาตรฐานคุณวุฒิระดับอุดมศึกษาของไทย (TQF / มคอ.)

คืออะไร — กรอบที่กำหนดให้หลักสูตรต้องระบุผลลัพธ์การเรียนรู้และแสดงหลักฐานว่าวัดผลอย่างไร โดยเอกสารที่เกี่ยวข้องโดยตรงกับโครงงานนี้คือ มคอ.3 (รายละเอียดรายวิชา) และ มคอ.5 (รายงานผลการดำเนินการของรายวิชา) [ต้องเติมเลขที่ประกาศและปีจากเอกสารจริง]

เกี่ยวข้องกับโครงงานอย่างไร — ผลลัพธ์ที่ระบบผลิตได้ (ตารางระดับการบรรลุ CLO ราย CLO พร้อม Target และ Actual) คือข้อมูลที่ต้องกรอกลง มคอ.5 พอดี ซึ่งเป็นเหตุผลที่ FR-87 กำหนดให้ส่งออกรายงานเป็นไฟล์ได้ — เพื่อให้ผลจากระบบไปต่อในกระบวนการประกันคุณภาพจริง ไม่ใช่จบอยู่บนหน้าจอ

2.1.9 ทฤษฎีที่ใช้ในการประเมินตัวระบบ

หลักการ ใช้ตรงไหนในโครงงาน
มาตรวัดประมาณค่าแบบลิเคิร์ท (Likert Scale) 5 ระดับ (Likert, 1932) แบบประเมินผู้ทรงคุณวุฒิและแบบสอบถามความพึงพอใจ (objectives-hypotheses-evaluation §3.3)
ดัชนีความสอดคล้องระหว่างข้อคำถามกับวัตถุประสงค์ (IOC) (Rovinelli & Hambleton, 1977) ตรวจคุณภาพแบบประเมินก่อนใช้จริง เกณฑ์ IOC ≥ 0.50 (งาน 5.3.2)
การทดสอบแบบกล่องดำ (Black Box Testing) การประเมินโดยผู้ทรงคุณวุฒิ 4 ด้าน (งาน 5.4)
การแปลผลค่าเฉลี่ย ช่วง 3.51–4.50 = ระดับดี เกณฑ์ตัดสินว่าโครงงานผ่าน (H5, H6)

หัวข้อนี้เขียนตามลำดับการทำงานจริงของโครงงาน: เลือกกระบวนการพัฒนา → เก็บความต้องการด้วย Use Case → อธิบายการไหลของข้อมูลด้วย DFD → ออกแบบที่เก็บข้อมูลด้วย ER → ออกแบบส่วนติดต่อ ผู้ใช้ → แล้วจึงลงมือเขียนโค้ดตามสถาปัตยกรรมที่วางไว้

2.2.1 วงจรการพัฒนาระบบ (System Development Life Cycle: SDLC)

คืออะไร — กรอบขั้นตอนการพัฒนาระบบสารสนเทศตั้งแต่ต้นจนส่งมอบ ประกอบด้วย 6 ระยะหลัก

ระยะ ทำอะไร ผลลัพธ์ในโครงงานนี้
1. วางแผน (Planning) กำหนดปัญหา ขอบเขต ทรัพยากร และตารางเวลา Root Cause Analysis · project-plan
2. วิเคราะห์ (Analysis) เก็บความต้องการและอธิบายระบบปัจจุบัน srs · Use Case Diagram · DFD
3. ออกแบบ (Design) ออกแบบข้อมูล สถาปัตยกรรม และส่วนติดต่อผู้ใช้ ER Diagram · สัญญา API · Design System · UI ทุกหน้า
4. พัฒนา (Implementation) เขียนโปรแกรมตามที่ออกแบบ 10 sprint ตาม project-plan CLO 4
5. ทดสอบ (Testing) ทดสอบหน่วย · ทดสอบระบบ · ทดสอบการยอมรับ unit test สูตร CR-01…CR-07 · Black Box โดยผู้ทรงคุณวุฒิ
6. บำรุงรักษา (Maintenance) แก้ไขและปรับปรุงหลังส่งมอบ นอกขอบเขตโครงงาน — เขียนเป็นข้อเสนอแนะในบทที่ 5

รูปแบบที่โครงงานนี้เลือกใช้: แบบวนซ้ำเป็นรอบ (Iterative / Agile) ไม่ใช่แบบน้ำตก (Waterfall)

Waterfall Iterative (ที่ใช้จริง)
ลำดับงาน ทำทีละระยะจนจบ ห้ามย้อนกลับ วนครบทุกระยะในทุกรอบ รอบละ 2 สัปดาห์
เหมาะเมื่อ ความต้องการนิ่งตั้งแต่ต้น ความต้องการยังไม่นิ่ง
ความเสี่ยง รู้ว่าออกแบบผิดตอนทดสอบ = สายเกินแก้ รู้เร็วกว่า แต่ต้องมีวินัยเรื่องเอกสาร

เหตุผลที่ต้องเป็นแบบวนซ้ำในโครงงานนี้: สูตรคำนวณ CR-03 ยังไม่ถูก sign-off ตอนเริ่มพัฒนา (ประเด็น OI-10 ใน srs §9) การรอให้ทุกอย่างนิ่งก่อนเขียนโค้ดจะทำให้เวลาที่มีไม่พอ ขณะเดียวกันการเขียนโค้ดโดยยังไม่รู้สูตรที่ถูกต้องก็ต้องรื้อ — การซอยเป็นรอบสั้นทำให้ งานส่วนที่ไม่ขึ้นกับสูตร (auth, รายวิชา, รายชื่อนักศึกษา) เดินหน้าไปได้ก่อน

โครงสร้างการแบ่งงาน (Work Breakdown Structure: WBS) คือการแตกงานใหญ่เป็นงานย่อยที่ ประมาณเวลาและมอบหมายผู้รับผิดชอบได้ ในโครงงานนี้ WBS ทุกงานถูกผูกกลับไปยัง CLO ของรายวิชา โครงงาน เพื่อให้ตรวจสอบได้ว่างานที่ทำครอบคลุมผลลัพธ์การเรียนรู้ครบทุกข้อ

2.2.2 แผนภาพยูสเคส (Use Case Diagram — UML)

คืออะไร — แผนภาพในกลุ่ม Unified Modeling Language (UML) ประเภท behavioural diagram ที่แสดงว่า ใคร (Actor) ใช้ระบบ ทำอะไรได้บ้าง (Use Case) โดยมองจากมุมผู้ใช้ ไม่ใช่จากมุมโครงสร้างภายในโปรแกรม

องค์ประกอบ

สัญลักษณ์ ชื่อ ความหมาย
รูปคน Actor ผู้กระทำที่อยู่นอกระบบ — คนหรือระบบอื่น
วงรี Use Case หน้าที่หนึ่งอย่างที่ระบบให้บริการ เขียนด้วยคำกริยา
กรอบสี่เหลี่ยม System Boundary ขอบเขตของระบบ — สิ่งที่อยู่นอกกรอบคือสิ่งที่ระบบไม่รับผิดชอบ
เส้นตรง Association actor คนนั้นใช้ use case นั้น
<<include>> ความสัมพันธ์แบบบังคับ use case หลักเรียกใช้เสมอ เช่น ทุกงานต้อง include "เข้าสู่ระบบ"
<<extend>> ความสัมพันธ์แบบมีเงื่อนไข ทำเพิ่มเฉพาะบางกรณี เช่น "นำเข้าไฟล์ผิดพลาด" extend "นำเข้าคะแนน"
ลูกศรหัวสามเหลี่ยมโปร่ง Generalization actor หนึ่งเป็นชนิดพิเศษของอีก actor

เกี่ยวข้องกับโครงงานอย่างไร — ระบบมี 2 actor (ADMIN, INSTRUCTOR) และ 11 use case (UC1–UC11 ใน srs §8) โดยมีจุดที่ต้องเขียนให้ถูก 3 ข้อ

  1. นักศึกษาไม่ใช่ actor — เป็น ข้อมูล ที่อาจารย์บันทึก ไม่ใช่ผู้ใช้ที่ล็อกอินได้ใน v1 การวาดนักศึกษาเป็น actor คือความผิดพลาดที่กรรมการจับได้ทันที เพราะขัดกับ srs §2.2
  2. ไม่มี actor "ผู้ดูแลระบบส่วนกลาง" — ตัดออกพร้อมกับการตัดสินใจ single-tenant (เดิมมี UC0 จัดการสถาบัน ซึ่งถูกยกเลิกทั้ง use case แล้ว)
  3. use case ต้องเขียนด้วยคำกริยาที่ผู้ใช้พูดเอง เช่น "นำเข้าคะแนนจากไฟล์ Excel" ไม่ใช่ "เรียก API POST /excel/import" ซึ่งเป็นภาษาของนักพัฒนา ไม่ใช่ภาษาของผู้ใช้

Use Case Description (คำบรรยายยูสเคส) — แผนภาพบอกได้แค่ว่า "ทำอะไรได้" แต่ไม่บอกว่า "ทำอย่างไร" จึงต้องมีตารางบรรยายกำกับทุก use case หลัก ประกอบด้วย ชื่อ · actor · เงื่อนไขก่อนเริ่ม (pre-condition) · ลำดับเหตุการณ์หลัก (main flow) · ลำดับเหตุการณ์ทางเลือก (alternative flow) · เงื่อนไขเมื่อจบ (post-condition) — ส่วน alternative flow คือจุดที่มักถูกละเลย ทั้งที่เป็นที่มาของข้อกำหนดการจัดการข้อผิดพลาดเกือบทั้งหมด (เช่น FR-67, FR-68, FR-69)

2.2.3 แผนภาพกระแสข้อมูล (Data Flow Diagram: DFD)

คืออะไร — แผนภาพที่แสดงว่าข้อมูลไหลจากที่ใดไปที่ใด ผ่านกระบวนการอะไร และถูกเก็บไว้ที่ไหน เป็นเครื่องมือของการวิเคราะห์เชิงโครงสร้าง (Structured Analysis) ที่ DeMarco (1979) เผยแพร่

องค์ประกอบ 4 อย่าง (สัญลักษณ์แบบ Yourdon–DeMarco ที่โครงงานนี้ใช้)

สัญลักษณ์ ชื่อ ความหมาย
สี่เหลี่ยม External Entity ผู้ให้หรือรับข้อมูลที่อยู่นอกระบบ
วงกลม Process การแปลงข้อมูลจาก input เป็น output
เส้นสองขีด / สี่เหลี่ยมเปิดข้าง Data Store ที่พักข้อมูล — ตารางในฐานข้อมูลหรือแฟ้ม
ลูกศร Data Flow ข้อมูลที่กำลังเคลื่อนที่ ต้องมีชื่อกำกับเสมอ

การแบ่งระดับ (Leveling) — DFD เขียนจากหยาบไปละเอียด และทุกระดับต้องสมดุล (balanced) คือ input/output ที่เข้าออกกระบวนการหนึ่งในระดับบน ต้องปรากฏครบในระดับที่แตกย่อยลงมา

ระดับ ขอบเขต ที่โครงงานทำ
Level 0 (Context Diagram) ระบบทั้งหมดเป็น 1 กระบวนการ ตอบว่าใครคุยกับระบบบ้าง 2 actor + ระบบไฟล์ + ฐานข้อมูล
Level 1 แตกเป็นกระบวนการหลัก 10 กระบวนการ (auth, access control, รายวิชา, CLO, คะแนน, Excel, รายงาน …)
Level 2 แตกเฉพาะกระบวนการที่ซับซ้อน การนำเข้าไฟล์ Excel (6 กระบวนการย่อย) และการคำนวณ attainment (6 กระบวนการย่อย)

กฎที่ต้องไม่ละเมิด (เป็นข้อที่กรรมการตรวจบ่อยที่สุด)

  • ข้อมูลต้องไม่ไหลจาก data store ไป data store โดยตรง ต้องผ่านกระบวนการเสมอ
  • ข้อมูลต้องไม่ไหลจาก external entity ไป data store โดยตรง
  • ทุกกระบวนการต้องมีทั้ง input และ output — กระบวนการที่มีแต่ input เรียกว่า black hole ส่วนที่มีแต่ output เรียกว่า miracle ทั้งสองอย่างคืออาการของการวิเคราะห์ที่ยังไม่จบ
  • ห้ามวาดลำดับก่อนหลังหรือเงื่อนไข if/else — นั่นเป็นหน้าที่ของ flowchart ไม่ใช่ DFD

เกี่ยวข้องกับโครงงานอย่างไร — นอกจากใช้อธิบายระบบในบทที่ 3 แล้ว DFD ของโครงงานนี้ยังถูกใช้ เป็น input ของการทำ threat modeling ตามแนวทาง STRIDE โดยเพิ่ม ขอบเขตความเชื่อถือ (Trust Boundary) ทับลงบนแผนภาพ เพื่อระบุว่าข้อมูลข้ามจากเขตที่เชื่อถือไม่ได้เข้าสู่เขตที่เชื่อถือได้ ตรงจุดใด — ซึ่งเป็นหลักฐานตอบข้อประเมิน "ด้านความปลอดภัย" ได้โดยตรง

3NF 2NF + ไม่มี attribute ที่ขึ้นกับ attribute ที่ไม่ใช่คีย์ ชื่อกิจกรรมไม่ถูกเก็บซ้ำในตาราง Score

ข้อยกเว้นที่จงใจในโครงงานนี้ — Course.passCriteria และ Course.classTarget เก็บค่าไว้ราย Course แทนที่จะอ้างถึงค่ากลางของคณะ ทั้งที่ค่ามักเหมือนกันทุกวิชา เหตุผลคือความถูกต้องเชิงประวัติศาสตร์: ถ้าอ้างค่ากลางแล้ว resolve ตอนอ่าน การแก้ค่ากลาง ในปีนี้จะเขียนผลการประเมินของเทอมที่แล้วใหม่เงียบ ๆ ซึ่งเป็นสิ่งที่รับไม่ได้สำหรับเอกสาร ที่อนุมัติไปแล้ว — ต้องเขียนเหตุผลนี้กำกับในเล่ม ไม่ปล่อยให้ดูเหมือนความผิดพลาดของการออกแบบ

ข้อบังคับที่ ERD และ ORM แสดงไม่ได้ — เงื่อนไขบางข้อของระบบเป็นกฎข้ามตาราง เช่น "คะแนนต้องไม่เกินคะแนนเต็มของกิจกรรมนั้น" หรือ "กิจกรรมกับ CLO ที่ผูกกันต้องอยู่วิชาเดียวกัน" ซึ่งต้องบังคับด้วย CHECK constraint และ trigger ที่ระดับฐานข้อมูล เพราะการตรวจที่ชั้น แอปพลิเคชันอย่างเดียวป้องกันไม่ได้หากมีการเขียนข้อมูลผ่านช่องทางอื่น

Visibility of system status — ระบบต้องบอกสถานะปัจจุบันเสมอ แสดงความคืบหน้าการกรอกคะแนน กรอกแล้ว x/y คน (FR-64)
Match between system and the real world — ใช้ภาษาของผู้ใช้ เมนูและข้อความทั้งหมดเป็นภาษาไทย ใช้คำว่า "กิจกรรม" ไม่ใช่ "Activity record"
Error prevention — กันไม่ให้ผิดตั้งแต่แรก ดีกว่าแจ้งทีหลัง เตือนเมื่อผลรวมน้ำหนักไม่ครบ 100% (FR-43) · เตือนก่อนออกจากหน้าที่ยังไม่บันทึก (FR-65)
Help users recognize, diagnose, and recover from errors ข้อความผิดพลาดต้องเป็นภาษาไทย บอกสาเหตุและวิธีแก้ ห้ามแสดงรหัส error ดิบ (NFR-10)
Recognition rather than recall — ให้จำได้ ดีกว่าให้นึกออกเอง ไฟล์ต้นแบบ Excel เติมรหัสและชื่อนักศึกษาไว้ให้แล้ว (FR-66)

ระบบออกแบบ (Design System) — ชุดกฎและคอมโพเนนต์ที่นำกลับมาใช้ซ้ำได้ ประกอบด้วย design token (สี ตัวอักษร ระยะห่าง) และคอมโพเนนต์มาตรฐาน (ปุ่ม ตาราง ฟอร์ม กล่องข้อความ) เหตุผลที่ต้องมีในโครงงานนี้โดยเฉพาะคือ สีสื่อความหมายของสถานะ — บรรลุ / ต้องปรับปรุง / ยังไม่ประเมิน — ถ้านักพัฒนาสามคนเลือกสีกันเองคนละหน้า ผู้ใช้จะตีความผลการประเมินผิด ซึ่งร้ายแรงกว่าเรื่องความสวยงาม

การออกแบบที่เข้าถึงได้ (Accessibility) — ใช้เกณฑ์ WCAG เป็นแนวทาง: อัตราส่วนความคมชัด ของสีต่อพื้นหลังอย่างน้อย 4.5:1 · ใช้งานด้วยคีย์บอร์ดได้ทั้งหมด · ห้ามใช้สีเป็นตัวสื่อ ความหมายเพียงอย่างเดียว ต้องมีข้อความหรือสัญลักษณ์กำกับด้วย เพราะผู้ใช้ที่ตาบอดสี จะแยกสถานะ "บรรลุ" กับ "ต้องปรับปรุง" ไม่ออกถ้าต่างกันแค่สีแดง-เขียว

2.2.6 สถาปัตยกรรมแบบไคลเอนต์–เซิร์ฟเวอร์ และ REST API

ระบบแยกเป็นสองส่วนที่ deploy แยกกัน: เว็บแอปพลิเคชันหน้าเดียว (Single-Page Application) ฝั่งเบราว์เซอร์ และ API เซิร์ฟเวอร์ที่ไม่เก็บสถานะ (stateless) ติดต่อกันผ่าน HTTP ด้วยรูปแบบ REST (Fielding, 2000) โดยส่งข้อมูลเป็น JSON

ข้อดีในบริบทนี้ — ตรรกะการคำนวณ CLO อยู่ฝั่งเซิร์ฟเวอร์ที่เดียว ทำให้ผลลัพธ์บนหน้าจอ กับผลลัพธ์ในไฟล์ที่ส่งออกมาจากแหล่งเดียวกันเสมอ (FR-88) ถ้าคำนวณฝั่งเบราว์เซอร์ด้วย จะเกิดตัวเลขสองชุดที่ไม่ตรงกันทันทีที่แก้สูตรเพียงฝั่งเดียว

2.2.7 สถาปัตยกรรมแบบแบ่งชั้น (Layered Architecture)

Request → Route → Middleware (auth → rbac) → Validator (Zod)
        → Controller (แปลง HTTP ↔ โดเมน) → Service (กฎทางธุรกิจ)
        → Prisma (เข้าถึงข้อมูล) → PostgreSQL

กฎที่บังคับในโครงงาน: ตรรกะการคำนวณต้องอยู่ในชั้น Service เท่านั้น โดยเฉพาะ attainment.service.ts ซึ่งเป็นที่เดียวที่รู้จักสูตร CR-01 ถึง CR-07 — controller ห้ามคำนวณเอง เหตุผลเชิงทฤษฎีคือการแยกความรับผิดชอบ (Separation of Concerns) และในทางปฏิบัติคือ ทำให้เขียน unit test เทียบกับใบคำนวณมือได้โดยไม่ต้องยิง HTTP (สมมติฐาน H1)

2.2.8 การยืนยันตัวตน การควบคุมสิทธิ์ และขอบเขตข้อมูล

Authentication กับ Authorization ต่างกัน — อย่างแรกตอบว่า "คุณเป็นใคร" อย่างหลังตอบว่า "คุณทำสิ่งนี้ได้หรือไม่" ระบบใช้ JSON Web Token (JWT) สำหรับข้อแรก และใช้ การควบคุมสิทธิ์ตามบทบาท (Role-Based Access Control: RBAC) สำหรับข้อหลัง

RBAC (Sandhu et al., 1996) คือการให้สิทธิ์ผ่าน "บทบาท" แทนการให้สิทธิ์รายบุคคล ระบบมี 2 บทบาทคือ ADMIN และ INSTRUCTOR เก็บไว้ที่ User.role

ขอบเขตข้อมูล (Data Scope) — ระบบเป็นแบบสถาบันเดียว (Single-Tenant)

โครงงานนี้เลือกออกแบบเป็น single-tenant คือใช้ภายในคณะเดียว ฐานข้อมูลชุดเดียวเก็บข้อมูล ขององค์กรเดียว ต่างจาก multi-tenant ที่หลายองค์กรใช้ฐานข้อมูลร่วมกันแล้วแยกข้อมูลด้วย คอลัมน์ระบุเจ้าของ (Chong & Carraro, 2006)

Single-tenant (ที่ใช้จริง) Multi-tenant (ทางเลือกที่ตัดออก)
ขอบเขตข้อมูล รายวิชา สถาบัน แล้วจึงรายวิชา
ความซับซ้อนของโค้ด ตรวจสิทธิ์ชั้นเดียว ต้องมีชั้นกรองข้อมูลตามสถาบันทุกคิวรี
ความเสี่ยงหลัก เข้าถึงวิชาของเพื่อนร่วมงาน ข้อมูลรั่วข้ามสถาบัน — ร้ายแรงกว่ามาก
เหมาะกับ ระบบภายในคณะ ระบบที่ให้บริการหลายมหาวิทยาลัย

เหตุผลของการเลือก — ขอบเขตของโครงงานคือหลักสูตร ค.อ.บ. ของคณะเดียว การทำ multi-tenant จะเพิ่มทั้งโค้ดที่ต้องเขียนและกรณีทดสอบที่ต้องพิสูจน์ โดยไม่มีผู้ใช้จริงที่ต้องการ ความสามารถนั้นเลย ซึ่งขัดกับข้อจำกัด CON-04 (ทีม 3 คน เวลาจำกัด) โดยตรง

ผลที่ตามมาและสิ่งที่ต้องระวัง — เมื่อตัดชั้นกรองระดับสถาบันออก ขอบเขตข้อมูลที่เหลืออยู่ เพียงชั้นเดียวคือรายวิชา จึงไม่มีด่านสำรองอีกต่อไป ทุกเส้นทาง API ที่รับรหัสรายวิชาต้อง เรียกฟังก์ชันตรวจสิทธิ์ก่อนเสมอ และต้องมีการทดสอบกำกับทุกเส้นทาง ไม่ใช่พึ่งการตรวจทานของคน ข้อนี้ถูกบันทึกไว้เป็นความเสี่ยงในเอกสาร DFD §7 และเป็นสิ่งที่ต้องเขียนอธิบายในบทที่ 3 เพราะเป็นการแลกความเรียบง่ายกับความเสี่ยงอย่างมีเจตนา ไม่ใช่การมองข้าม

เหตุผลที่ระบบตอบ 404 ไม่ใช่ 403 เมื่อเข้าถึงรายวิชาที่ไม่มีสิทธิ์: การตอบ 403 เป็นการยืนยันกลาย ๆ ว่ารายวิชานั้นมีอยู่จริง ซึ่งเปิดช่องให้กวาดหารหัสที่ใช้ได้ (enumeration) จึงถือเป็นการเปิดเผยข้อมูลรูปแบบหนึ่ง (NFR-07)

2.3 เทคโนโลยีที่ใช้ในการพัฒนา (Technology Stack)

รูปแบบการเขียนแต่ละหัวข้อ: คืออะไร → ใช้ทำอะไรในโครงงาน → ข้อดีที่เป็นเหตุผลของการเลือก → ข้อจำกัด โดยข้อจำกัดต้องเขียนจริง ไม่ใช่เขียนให้ครบรูปแบบ เพราะกรรมการมักถามข้อนี้

2.3.1 ภาษาและสภาพแวดล้อมพื้นฐาน

TypeScript 5.9

  • คืออะไร — ภาษาที่ต่อยอดจาก JavaScript โดยเพิ่มระบบชนิดข้อมูลแบบตรวจสอบตอนคอมไพล์ (static type checking) แล้วแปลงกลับเป็น JavaScript เพื่อรันจริง
  • ใช้ทำอะไร — เป็นภาษาหลักทั้งฝั่งเบราว์เซอร์และเซิร์ฟเวอร์ เปิดโหมด strict และห้ามใช้ชนิด any ตามมาตรฐานของโปรเจกต์
  • ข้อดีที่เลือกใช้ — ระบบนี้มีสูตรคำนวณที่ค่า null (ยังไม่ประเมิน) กับ 0 (ได้ศูนย์) ต้องไม่ปนกันเด็ดขาด TypeScript บังคับให้ผู้เขียนโค้ดจัดการกรณี null อย่างชัดเจน ตั้งแต่ตอนคอมไพล์ แทนที่จะไปพังตอนรัน อีกทั้งใช้ภาษาเดียวทั้งสองฝั่ง ทีม 3 คนจึงสลับ กันทำงานข้ามฝั่งได้โดยไม่ต้องเรียนภาษาใหม่
  • ข้อจำกัด — การตรวจชนิดมีผลเฉพาะตอนคอมไพล์ ไม่คุ้มครองข้อมูลที่มาจากภายนอกตอนรันจริง จึงยังต้องมีการตรวจสอบด้วย Zod ที่ขอบระบบเสมอ (§2.3.7) และเพิ่มเวลาในขั้นตอน build

Node.js 20 ขึ้นไป

  • คืออะไร — สภาพแวดล้อมสำหรับรัน JavaScript นอกเบราว์เซอร์ ทำงานแบบ event-driven และ non-blocking I/O
  • ใช้ทำอะไร — รัน API เซิร์ฟเวอร์ สคริปต์ migration/seed และเครื่องมือพัฒนาทั้งหมด
  • ข้อดีที่เลือกใช้ — งานหลักของระบบนี้เป็นงานรอ I/O (คิวรีฐานข้อมูล อ่านไฟล์ Excel) ไม่ใช่งานคำนวณหนัก ซึ่งเป็นรูปแบบที่โมเดล non-blocking ของ Node.js รับมือได้ดีด้วย ทรัพยากรที่น้อย เหมาะกับการ deploy ในระดับคณะ
  • ข้อจำกัด — ทำงานบนเธรดเดียว งานที่กินซีพียูต่อเนื่อง เช่น การแยกไฟล์ Excel ขนาดใหญ่ จะบล็อกคำขออื่นได้ จึงต้องจำกัดขนาดไฟล์อัปโหลด และเป็นเหตุผลที่ NFR-03 กำหนดเพดาน การนำเข้าไว้ที่ 500 แถว

npm workspaces (Monorepo)

  • คืออะไร — ความสามารถของ npm ที่ให้เก็บหลายแพ็กเกจ (app/client, app/server) ไว้ในที่เก็บโค้ดเดียว โดยติดตั้ง dependency ร่วมกันจากรากเดียว
  • ใช้ทำอะไร — รวมโค้ดฝั่งหน้าเว็บ ฝั่งเซิร์ฟเวอร์ และสคีมาฐานข้อมูลไว้ที่เดียว สั่งรันทั้งระบบด้วย npm run dev คำสั่งเดียว
  • ข้อดีที่เลือกใช้ — การแก้ที่กระทบทั้งสองฝั่ง เช่น เพิ่มฟิลด์ในฐานข้อมูลแล้วต้องแก้ ทั้ง API และหน้าจอ จบได้ใน pull request เดียว ทีม 3 คนจึงไม่ต้องประสานข้าม repository
  • ข้อจำกัด — เวลาที่ CI ต้องใช้เพิ่มขึ้นเพราะทดสอบทั้งสองฝั่งทุกครั้ง และแยกสิทธิ์ การเข้าถึงระหว่างส่วนไม่ได้

2.3.2 ส่วนติดต่อผู้ใช้ (Frontend)

React 19

  • คืออะไร — ไลบรารีสำหรับสร้างส่วนติดต่อผู้ใช้แบบแบ่งเป็นคอมโพเนนต์ ใช้แนวคิด declarative คือประกาศว่าหน้าจอควรมีหน้าตาอย่างไรตามสถานะปัจจุบัน แล้วให้ไลบรารี จัดการปรับ DOM เอง
  • ใช้ทำอะไร — สร้างหน้าจอทั้ง 15 หน้า โดยเฉพาะส่วนที่มีสถานะซับซ้อน ได้แก่ ตารางกรอกคะแนน เมทริกซ์ผูกกิจกรรมกับ CLO และหน้าตรวจไฟล์ก่อนนำเข้า
  • ข้อดีที่เลือกใช้ — หน้าจอที่ยากที่สุดของระบบคือตารางที่หลายร้อยช่องเปลี่ยนค่าพร้อมกัน และต้องรู้ว่าช่องไหนแก้ไปแล้วบ้าง แนวคิด declarative ทำให้ไม่ต้องเขียนโค้ดตามแก้ DOM ทีละช่อง ซึ่งเป็นแหล่งของข้อผิดพลาดโดยตรง อีกทั้งมีชุมชนผู้ใช้ขนาดใหญ่ หาทางแก้ปัญหาได้เร็ว
  • ข้อจำกัด — เป็นเพียงไลบรารีสำหรับส่วนแสดงผล ไม่มีระบบ routing หรือการดึงข้อมูลมาให้ ต้องเลือกไลบรารีเสริมเอง (React Router, TanStack Query) และการเรนเดอร์ซ้ำที่ไม่จำเป็น ทำให้ตารางขนาดใหญ่ช้าได้ถ้าไม่ระวัง

Vite 7 (+ plugin React SWC)

  • คืออะไร — เครื่องมือสำหรับพัฒนาและรวมไฟล์ (build tool) ที่ตอนพัฒนาใช้ ES Modules ของเบราว์เซอร์โดยตรง และตอน build ใช้ Rollup
  • ใช้ทำอะไร — รันเซิร์ฟเวอร์ตอนพัฒนา แทนที่โค้ดที่แก้แบบทันที (Hot Module Replacement) และสร้างไฟล์สำหรับใช้งานจริง
  • ข้อดีที่เลือกใช้ — เวลารอตอนพัฒนาสั้นมากแม้โปรเจกต์โต ซึ่งสำคัญกับตารางที่ต้องปรับ รายละเอียดการแสดงผลซ้ำหลายรอบ และตั้งค่า proxy ให้เรียก API ข้ามพอร์ตได้โดยไม่ติดปัญหา CORS ตอนพัฒนา
  • ข้อจำกัด — พฤติกรรมตอนพัฒนากับตอน build ต่างกัน ปัญหาบางอย่างจึงพบเฉพาะตอน build ทีมต้องทดสอบกับไฟล์ที่ build จริงก่อนส่งมอบเสมอ

React Router 7

  • คืออะไร — ไลบรารีจัดการเส้นทาง (route) ของเว็บแอปหน้าเดียว แปลง URL เป็นหน้าจอ
  • ใช้ทำอะไร — ผูก URL ทั้ง 15 เส้นทางตามแผนผังหน้าจอ รวมถึงเส้นทางที่ซ้อนกัน เช่น /courses/:courseId/dashboard/students/:studentId และกันไม่ให้เข้าหน้าที่ไม่มีสิทธิ์
  • ข้อดีที่เลือกใช้ — โครงสร้างข้อมูลของระบบเป็นลำดับชั้น (วิชา → CLO/กิจกรรม/นักศึกษา → คะแนน) ซึ่งจับคู่กับ nested route ได้ตรง ทำให้ส่วนหัวและเมนูของรายวิชาไม่ต้องเขียนซ้ำในทุกหน้า
  • ข้อจำกัด — มีการเปลี่ยนรูปแบบการใช้งานระหว่างเวอร์ชันบ่อย ตัวอย่างที่ค้นเจอบนอินเทอร์เน็ต จำนวนมากเป็นของเวอร์ชันเก่าและใช้ไม่ได้ ต้องยึดเอกสารทางการเป็นหลัก

TanStack Query 5

  • คืออะไร — ไลบรารีจัดการข้อมูลที่มาจากเซิร์ฟเวอร์ (server state) ดูแลการแคช การดึงข้อมูลซ้ำ สถานะกำลังโหลด และสถานะผิดพลาดให้อัตโนมัติ
  • ใช้ทำอะไร — ดึงข้อมูลทุกชนิดจาก API และทำให้หน้า Dashboard แสดงข้อมูลใหม่ทันที หลังบันทึกคะแนน โดยสั่งให้ข้อมูลที่เกี่ยวข้องหมดอายุ
  • ข้อดีที่เลือกใช้ — แก้ปัญหาที่เกิดขึ้นแน่นอนในระบบนี้ คือกรอกคะแนนแล้วเปิดหน้า Dashboard เห็นตัวเลขเก่า ถ้าเขียนเองต้องจัดการแคชและการทำให้ข้อมูลหมดอายุด้วยมือทุกจุด ซึ่งเป็นงานที่พลาดง่ายและตรวจไม่เจอจนกว่าผู้ใช้จะแจ้ง
  • ข้อจำกัด — มีแนวคิดที่ต้องเรียนรู้พอสมควร (query key, stale time, invalidation) และถ้าตั้ง query key ผิด จะได้ข้อมูลของรายวิชาอื่นมาแสดง — อันตรายเป็นพิเศษเพราะรายวิชา คือขอบเขตข้อมูลเดียวของระบบ จึงต้องกำหนดมาตรฐานการตั้ง key ให้มี courseId เสมอ

Zustand 5

  • คืออะไร — ไลบรารีจัดการสถานะฝั่งเบราว์เซอร์ (client state) ขนาดเล็ก
  • ใช้ทำอะไร — เก็บสถานะที่ไม่ได้มาจากเซิร์ฟเวอร์ เช่น ข้อมูลผู้ใช้ที่ล็อกอินอยู่ การเปิด/ปิดเมนู และสถานะ "มีการแก้ไขที่ยังไม่บันทึก" ของหน้ากรอกคะแนน
  • ข้อดีที่เลือกใช้ — เบาและเขียนสั้นกว่าทางเลือกอย่าง Redux มาก เหมาะกับระบบที่ สถานะส่วนใหญ่เป็นข้อมูลจากเซิร์ฟเวอร์อยู่แล้ว (ซึ่ง TanStack Query ดูแลไป) เหลือสถานะฝั่งเบราว์เซอร์จริง ๆ ไม่มาก
  • ข้อจำกัด — ไม่มีเครื่องมือติดตามประวัติการเปลี่ยนสถานะที่ครบเท่า Redux DevTools และเพราะเข้าถึงได้ง่ายจากทุกที่ จึงต้องมีวินัยไม่เอาข้อมูลจากเซิร์ฟเวอร์มาเก็บซ้ำไว้ที่นี่

Tailwind CSS 4

  • คืออะไร — เฟรมเวิร์ก CSS แบบ utility-first ที่ให้เขียนคลาสสำเร็จรูปประกอบกัน แทนการตั้งชื่อคลาสและเขียนไฟล์ CSS แยก
  • ใช้ทำอะไร — จัดรูปแบบทุกหน้าจอ และผูกกับ design token ที่กำหนดไว้ในระบบออกแบบ โดยเฉพาะสีสถานะ (บรรลุ / ต้องปรับปรุง / ยังไม่ประเมิน) ที่ต้องเหมือนกันทั้งระบบ
  • ข้อดีที่เลือกใช้ — สีที่สื่อความหมายของสถานะถูกกำหนดจากที่เดียว ทำให้นักพัฒนาสามคน ไม่เผลอใช้สีต่างกันในหน้าคนละหน้า ซึ่งจะทำให้ผู้ใช้ตีความผิด และตัดโค้ด CSS ที่ไม่ได้ใช้ออกตอน build อัตโนมัติ
  • ข้อจำกัด — โค้ดใน JSX ยาวและอ่านยากขึ้น ต้องแยกเป็นคอมโพเนนต์ที่ใช้ซ้ำได้ (ใช้ class-variance-authority และ tailwind-merge ช่วย) และมีสิ่งที่ต้องเรียนรู้ใหม่ สำหรับคนที่คุ้นกับ CSS ปกติ

Recharts 3

  • คืออะไร — ไลบรารีสร้างกราฟสำหรับ React สร้างเป็น SVG
  • ใช้ทำอะไร — กราฟแท่งเปรียบเทียบ Target กับ Actual รายข้อ CLO บนหน้า Dashboard (FR-81) และกราฟความก้าวหน้าในรายงานรายบุคคล
  • ข้อดีที่เลือกใช้ — เขียนเป็นคอมโพเนนต์แบบเดียวกับ React ทั้งหมด ไม่ต้องสลับไป จัดการ DOM เอง และกราฟที่ระบบต้องใช้เป็นรูปแบบมาตรฐาน ไม่จำเป็นต้องใช้เครื่องมือ ที่ยืดหยุ่นสูงและซับซ้อนกว่าอย่าง D3
  • ข้อจำกัด — ปรับแต่งรูปแบบที่ผิดไปจากที่ไลบรารีเตรียมไว้ได้จำกัด และการเรนเดอร์ SVG จำนวนจุดมาก ๆ จะช้า — ในบริบทนี้ไม่เป็นปัญหาเพราะกราฟมีจำนวนแท่งเท่ากับจำนวน CLO ซึ่งปกติไม่เกิน 10 ข้อ

2.3.3 ส่วนเซิร์ฟเวอร์ (Backend)

Fastify 5

  • คืออะไร — เว็บเฟรมเวิร์กสำหรับ Node.js ที่เน้นประสิทธิภาพ มีระบบ plugin และตรวจสอบ/แปลงข้อมูลด้วย JSON Schema ในตัว
  • ใช้ทำอะไร — เป็นแกนของ API เซิร์ฟเวอร์ จัดการ route ทั้งหมด และเป็นที่แขวน middleware สามชั้น (ยืนยันตัวตน → สิทธิ์ตามบทบาท → ขอบเขตรายวิชา)
  • ข้อดีที่เลือกใช้ — ระบบ hook และ plugin แบบมีขอบเขต (encapsulation) ทำให้บังคับได้ว่า ทุก route ใต้ /api/courses/:courseId ต้องผ่านการตรวจสิทธิ์เสมอ โดยไม่ต้องพึ่งให้นักพัฒนา จำใส่เองทุกเส้นทาง ซึ่งตรงกับข้อกำหนดความปลอดภัย NFR-07 ที่การลืมเพียงจุดเดียว หมายถึงข้อมูลรั่วข้ามรายวิชา อีกทั้งมีระบบ log ในตัว (pino) ที่ใช้ตรวจสอบย้อนหลังได้
  • ข้อจำกัด — ชุมชนและตัวอย่างการใช้งานเล็กกว่า Express มาก ปัญหาที่พบต้องอ่าน เอกสารทางการเป็นหลัก และการเขียน plugin ต้องเข้าใจเรื่องขอบเขตการมองเห็นของ plugin ซึ่งเป็นแนวคิดที่ผิดพลาดได้ง่ายในช่วงแรก

Prisma 6 (ORM)

  • คืออะไร — เครื่องมือเชื่อมระหว่างโค้ดกับฐานข้อมูล ที่นิยามโครงสร้างข้อมูลไว้ในไฟล์ schema.prisma แล้วสร้างไคลเอนต์ที่มีชนิดข้อมูลถูกต้องตามสคีมาให้อัตโนมัติ พร้อมระบบ migration
  • ใช้ทำอะไร — นิยามทั้ง 18 ตาราง จัดการ migration ทุกครั้งที่โครงสร้างเปลี่ยน และเป็นชั้นเข้าถึงข้อมูลของทุก service
  • ข้อดีที่เลือกใช้ — ชนิดข้อมูลของผลลัพธ์ที่คิวรีได้มาถูกสร้างจากสคีมาโดยตรง ถ้าเปลี่ยนชื่อคอลัมน์แล้วลืมแก้โค้ดที่ใช้ TypeScript จะฟ้องทันทีตอนคอมไพล์ ไม่ต้องรอพังตอนรัน ซึ่งมีค่ามากกับระบบที่มีตารางจำนวนมากและมีความสัมพันธ์ซับซ้อน นอกจากนี้ไฟล์ migration ที่เก็บไว้ในที่เก็บโค้ดยังเป็นหลักฐานประกอบบทที่ 3
  • ข้อจำกัด — สำคัญและต้องเขียนลงเล่ม: Prisma แสดง CHECK constraint, trigger และ partial unique index ไม่ได้ ทั้งสามอย่างจึงต้องเขียนเป็น SQL ในไฟล์ migration แยก และคำสั่ง prisma db push จะลบสิ่งเหล่านี้ทิ้งเงียบ ๆ โครงงานจึงห้ามใช้คำสั่งนี้ ในทุกสภาพแวดล้อม อีกทั้งคิวรีที่ซับซ้อนมากอาจต้องเขียน SQL ตรงผ่าน $queryRaw และหากเขียนความสัมพันธ์ซ้อนกันไม่ระวังจะเกิดปัญหา N+1 query ซึ่ง NFR-02 ห้ามไว้

PostgreSQL

  • คืออะไร — ระบบจัดการฐานข้อมูลเชิงสัมพันธ์แบบโอเพนซอร์ส รองรับ ACID
  • ใช้ทำอะไร — เก็บข้อมูลทั้งหมดของระบบ และเป็นด่านสุดท้ายที่บังคับความถูกต้องของข้อมูล ด้วย constraint และ trigger
  • ข้อดีที่เลือกใช้ — รองรับ partial unique index ซึ่งจำเป็นโดยตรงกับข้อกำหนด "หนึ่งรายวิชามีอาจารย์ LEAD ได้ไม่เกิน 1 คน" (FR-23) — ฐานข้อมูลที่ไม่รองรับความสามารถนี้ ต้องไปบังคับที่ชั้นแอปพลิเคชันซึ่งมีช่องโหว่เมื่อมีคำขอพร้อมกัน นอกจากนี้ยังรองรับ transaction ที่จำเป็นกับการบันทึกคะแนนทั้งชุดแบบสำเร็จทั้งหมดหรือไม่สำเร็จเลย (FR-63)
  • ข้อจำกัด — ต้องดูแลเซิร์ฟเวอร์ฐานข้อมูลเอง (โครงงานใช้บริการที่มีผู้ให้บริการจัดการให้) และ trigger ที่เขียนไว้เป็นตรรกะที่อยู่นอกโค้ดหลัก ผู้ที่มาพัฒนาต่ออาจไม่ทราบว่ามีอยู่ จึงต้องบันทึกไว้ในเอกสารอย่างชัดเจน

Zod 4

  • คืออะไร — ไลบรารีสำหรับประกาศรูปแบบข้อมูลที่คาดหวังและตรวจสอบข้อมูลจริงตอนรัน พร้อมสรุปชนิดข้อมูลให้ TypeScript ใช้ต่อได้
  • ใช้ทำอะไร — ตรวจสอบข้อมูลทุกชิ้นที่เข้าสู่ API ทั้ง body, params และ query รวมถึงตรวจข้อมูลแต่ละแถวของไฟล์ Excel ที่นำเข้า
  • ข้อดีที่เลือกใช้ — เป็นจุดที่แปลงข้อมูลจากภายนอกซึ่ง "เชื่อไม่ได้" ให้กลายเป็นข้อมูล ที่มีชนิดแน่นอน ทำให้ชั้น service ไม่ต้องตรวจซ้ำ และข้อความผิดพลาดที่ได้สามารถแปลง เป็นข้อความภาษาไทยรายฟิลด์ ซึ่งตรงกับเกณฑ์ด้านการใช้งานที่กำหนดว่าข้อความผิดพลาด ต้องบอกวิธีแก้ไข
  • ข้อจำกัด — การตรวจสอบเกิดตอนรัน จึงมีต้นทุนเวลาเมื่อข้อมูลมีจำนวนแถวมาก และถ้าประกาศ schema ไม่ตรงกับความจริงของฐานข้อมูล ก็ยังผ่านไปพังที่ชั้นล่างอยู่ดี จึงต้องถือ schema.prisma เป็นแหล่งอ้างอิงหลักเสมอ

argon2 และ jose (ความปลอดภัย)

  • คืออะไร — argon2 คืออัลกอริทึมแฮชรหัสผ่านที่ชนะการแข่งขัน Password Hashing Competition ปี 2015 ออกแบบให้กินหน่วยความจำมากเพื่อต้านการเดาด้วยฮาร์ดแวร์เฉพาะทาง ส่วน jose คือไลบรารีสำหรับสร้างและตรวจสอบ JSON Web Token (JWT) ตาม RFC 7519
  • ใช้ทำอะไร — เก็บรหัสผ่านผู้ใช้ (FR-02) และออก access token อายุ 15 นาที กับ refresh token อายุ 7 วัน (FR-01)
  • ข้อดีที่เลือกใช้ — argon2 ต้านการโจมตีด้วย GPU ได้ดีกว่าอัลกอริทึมรุ่นเก่า ส่วน JWT ทำให้เซิร์ฟเวอร์ไม่ต้องเก็บสถานะ session ซึ่งเข้ากับสถาปัตยกรรม stateless และ jose เป็นไลบรารีที่ใช้ Web Crypto API มาตรฐาน ไม่พึ่งการตั้งค่าที่ผิดพลาดง่าย
  • ข้อจำกัด — argon2 กินหน่วยความจำและเวลาโดยตั้งใจ จึงทำให้การล็อกอินช้ากว่าปกติ เล็กน้อยและต้องตั้งค่าพารามิเตอร์ให้เหมาะกับเครื่องที่ใช้ ส่วน JWT ที่ออกไปแล้ว ยกเลิกกลางคันไม่ได้ จนกว่าจะหมดอายุ ระบบจึงต้องตั้งอายุ access token ให้สั้น และการปิดบัญชีผู้ใช้จะมีผลเต็มที่ภายใน 15 นาที ซึ่งเป็นข้อจำกัดที่ต้องระบุในเล่ม

  • คืออะไร — ไลบรารีอ่านและเขียนไฟล์สเปรดชีต รองรับ .xlsx และ .xls
  • ใช้ทำอะไร — สร้างไฟล์ต้นแบบที่เติมรหัสและชื่อนักศึกษาไว้แล้ว (FR-66) อ่านไฟล์ที่อาจารย์อัปโหลดเพื่อตรวจสอบก่อนบันทึก (FR-67) และส่งออกคะแนนกับรายงาน (FR-70)
  • ข้อดีที่เลือกใช้ — เป็นสะพานเชื่อมกับวิธีทำงานเดิมของผู้ใช้ซึ่งใช้ Excel ทั้งหมด ถ้าระบบรับเฉพาะการกรอกทีละช่อง อาจารย์ที่มีคะแนนอยู่แล้วในไฟล์เดิมจะไม่ย้ายมาใช้ และใช้ไลบรารีตัวเดียวกันได้ทั้งฝั่งเซิร์ฟเวอร์และเบราว์เซอร์
  • ข้อจำกัด — เวอร์ชันที่แจกฟรีติดตั้งจาก CDN ของผู้พัฒนาโดยตรง ไม่ได้ผ่าน registry ของ npm ตามปกติ ซึ่งเป็นเรื่องที่ต้องบันทึกไว้เพื่อให้ผู้พัฒนาต่อทราบ อีกทั้งการอ่านไฟล์ทำในหน่วยความจำทั้งไฟล์ จึงต้องจำกัดขนาดไฟล์ที่รับ และไฟล์ที่ผู้ใช้แก้โครงสร้างเอง เช่น แทรกคอลัมน์หรือรวมเซลล์ จะทำให้การอ่านผิดพลาด ระบบจึงต้องมีขั้นตรวจสอบก่อนบันทึกเสมอ

2.3.4 เครื่องมือด้านคุณภาพและกระบวนการพัฒนา

Vitest 3

  • คืออะไร — เครื่องมือทดสอบที่ทำงานร่วมกับ Vite ใช้รูปแบบการเขียนแบบเดียวกับ Jest
  • ใช้ทำอะไร — ทดสอบหน่วยของสูตรคำนวณทั้งหมดใน attainment.service.ts รวมถึงกรณีขอบ 5 แบบ และทดสอบว่าทุกเส้นทางที่รับ :courseId เรียกตรวจสิทธิ์รายวิชาจริง
  • ข้อดีที่เลือกใช้ — เป็นเครื่องมือที่ใช้พิสูจน์สมมติฐาน H1 โดยตรง เพราะข้อกำหนด ระบุว่าผลคำนวณต้องตรงกับใบคำนวณด้วยมือ 100% ซึ่งพิสูจน์ได้ก็ต่อเมื่อมีชุดทดสอบที่รัน ซ้ำได้ทุกครั้งที่แก้โค้ด ไม่ใช่การกดทดสอบด้วยมือครั้งเดียว
  • ข้อจำกัด — วัดได้เฉพาะสิ่งที่เขียนทดสอบไว้ ค่าความครอบคลุมของโค้ด (coverage) สูง ไม่ได้แปลว่าสูตรถูก จึงต้องใช้คู่กับใบคำนวณมือที่อาจารย์ที่ปรึกษาตรวจรับแล้วเสมอ

ESLint 10 + typescript-eslint + Prettier

  • คืออะไร — ESLint ตรวจรูปแบบการเขียนโค้ดที่เสี่ยงต่อข้อผิดพลาด ส่วน Prettier จัดรูปแบบการวางโค้ดให้เป็นแบบเดียวกันอัตโนมัติ
  • ใช้ทำอะไร — บังคับกฎของโปรเจกต์ เช่น ห้ามใช้ any และจัดรูปแบบโค้ดของทั้ง 3 คน ให้เหมือนกัน
  • ข้อดีที่เลือกใช้ — ตัดข้อขัดแย้งเรื่องรูปแบบการเขียนออกจากการรีวิว pull request ทำให้การรีวิวเหลือเฉพาะเนื้อหาที่สำคัญจริง และลด conflict ตอนรวมโค้ดที่เกิดจาก การจัดรูปแบบต่างกัน
  • ข้อจำกัด — ตรวจได้เฉพาะรูปแบบ ไม่เข้าใจความหมายของโปรแกรม โค้ดที่ผ่าน lint ทั้งหมดยังคำนวณผิดได้

Git, GitHub และ GitHub Actions (CI)

  • คืออะไร — Git คือระบบควบคุมเวอร์ชันแบบกระจาย GitHub คือบริการฝากที่เก็บโค้ด และ GitHub Actions คือระบบรันงานอัตโนมัติเมื่อมีการส่งโค้ด
  • ใช้ทำอะไร — ทีมทำงานแบบ GitHub Flow คือแยก branch ต่อหนึ่งงาน แล้วรวมผ่าน pull request ที่ต้องมีผู้รีวิว โดย CI รัน lint, typecheck, test และตรวจสคีมาทุกครั้ง
  • ข้อดีที่เลือกใช้ — บังคับให้โค้ดที่รวมเข้า main ผ่านเกณฑ์เดียวกันเสมอ โดยไม่ต้อง อาศัยความจำของสมาชิก และประวัติการเปลี่ยนแปลงเป็นหลักฐานการทำงานที่ใช้ประกอบ การประเมินความก้าวหน้าตามแผนได้
  • ข้อจำกัด — ทีมต้องมีวินัยเรื่องขนาดของ pull request หากรวมงานใหญ่มาในครั้งเดียว การรีวิวจะไร้ความหมาย และเวลาที่ CI ใช้จะเพิ่มขึ้นตามจำนวนการทดสอบ

Docker และ Docker Compose

  • คืออะไร — เทคโนโลยีที่บรรจุแอปพลิเคชันพร้อมสภาพแวดล้อมทั้งหมดไว้ใน container โดย Docker Compose ใช้สั่งรันหลาย container พร้อมกันจากไฟล์ตั้งค่าเดียว
  • ใช้ทำอะไร — ให้สมาชิกทีมและผู้ที่นำระบบไปติดตั้งรันได้ด้วยคำสั่งเดียวโดยไม่ต้อง ติดตั้ง Node.js และฐานข้อมูลเองทีละอย่าง
  • ข้อดีที่เลือกใช้ — ตัดปัญหา "เครื่องผมรันได้" ซึ่งกินเวลาทีมที่ใช้เครื่องต่างกัน และทำให้ขั้นตอนติดตั้งในภาคผนวกของเล่มสั้นและทำตามได้จริง
  • ข้อจำกัด — มีสิ่งที่ต้องเรียนรู้เพิ่มสำหรับสมาชิกที่ไม่เคยใช้ และกินทรัพยากรเครื่อง มากกว่าการรันตรง โดยเฉพาะบนเครื่องที่หน่วยความจำจำกัด

2.3.6 สรุปเหตุผลเชิงภาพรวมของการเลือกเทคโนโลยี

การเลือกทั้งหมดตั้งอยู่บนข้อจำกัดจริง 3 ข้อของโครงงาน ไม่ใช่ความนิยมของเทคโนโลยี

  1. ทีมมี 3 คน เวลาจำกัด → ใช้ TypeScript ภาษาเดียวทั้งระบบใน monorepo เดียว เพื่อให้สลับกันทำงานข้ามส่วนได้โดยไม่ต้องเรียนภาษาใหม่
  2. ความถูกต้องของตัวเลขคือเกณฑ์ผ่านของโครงงาน (ต้องตรง 100%) → เลือกเครื่องมือที่ ดันข้อผิดพลาดให้โผล่เร็วที่สุด ได้แก่ TypeScript strict, Zod ที่ขอบระบบ, constraint/trigger ที่ฐานข้อมูล และ Vitest ที่รันซ้ำได้
  3. ผู้ใช้ทำงานด้วย Excel อยู่เดิม → ต้องมีเส้นทางนำเข้า/ส่งออก Excel ที่ใช้ได้จริง ตั้งแต่รุ่นแรก มิฉะนั้นผู้ใช้จะไม่เปลี่ยนมาใช้ระบบ และสมมติฐาน H6, H7 จะพิสูจน์ไม่ได้

  • ตารางเปรียบเทียบระบบเดิมกับสิ่งที่โครงงานเพิ่มเข้ามา (ผลงาน 1.2.3)
