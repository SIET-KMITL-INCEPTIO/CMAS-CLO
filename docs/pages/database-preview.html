กติกาที่ฐานข้อมูลบังคับเอง

กติกาที่สำคัญพอจะทำให้ข้อมูลผิดถาวร ไม่ควรอยู่ที่โค้ดฝั่งเดียว — สิ่งที่อยู่ในตารางนี้ถูกบังคับที่ฐานข้อมูล แม้มีคนเขียนตรงเข้า SQL ก็ยังผิดไม่ได้

ชนิดกติกาตารางจำนวน
CHECK อีเมลมีรูปแบบ · ชื่อไม่ว่าง · hash ยาว ≥ 20 ตัวอักษร User3
CHECK ภาค 1–6 · ปี 1900–2700 · หน่วยกิต 0–30 · ชั่วโมงไม่ติดลบ · เกณฑ์ผ่านและเป้าหมาย 0–100 Course10
CHECK เลขข้อ > 0 · เกณฑ์ผ่าน 0–100 · คะแนนเต็ม > 0 · น้ำหนักไม่ติดลบ · คะแนนไม่ติดลบ CLO · Activity · Score22
TRIGGER คะแนนต้องไม่เกิน maxScore ของกิจกรรมนั้น — CHECK อ้างข้ามตารางไม่ได้ Score1
TRIGGER กิจกรรมกับ CLO ในเกณฑ์เดียวกันต้องอยู่รายวิชาเดียวกัน AssessmentCriteria1
TRIGGER วัตถุประสงค์ต้องอยู่ใต้ CLO เดียวกับเกณฑ์ที่ผูก ObjectiveAssessment1
TRIGGER รายวิชาแบบ PASS_FAIL ต้องมีขั้นเกรดสองขั้นพอดี GradeBand1
UNIQUE คีย์ระบุตัวตนของแต่ละตาราง เช่น (รหัสวิชา, ภาค, ปี, หมู่เรียน) และ (นักศึกษา, กิจกรรม) 10 ตาราง10
PARTIAL ผู้ประสานงานรายวิชา (LEAD) มีได้ไม่เกิน 1 คนต่อวิชา — unique index เฉพาะแถวที่ role = LEAD CourseInstructor1
 ที่มา database/migrations/0002_constraints_and_triggers และ 0004_grading_constraints_and_triggers
ทำไมบางกติกาต้องเป็น trigger ไม่ใช่ CHECK
ทั้ง PostgreSQL และ MySQL ห้ามใช้ subquery ใน CHECK กติกาใดที่ต้องอ่านตารางอื่น จึงเขียนเป็น CHECK ไม่ได้ เช่น "คะแนนต้องไม่เกินคะแนนเต็มของกิจกรรมนั้น" ต้องไปอ่าน Activity.maxScore ก่อน · สี่กติกาในตารางด้านบนที่เป็น trigger ล้วนเป็นแบบนี้ทั้งหมด

ครั้งหนึ่งเคยมี trigger สำหรับความสมบูรณ์ข้ามผู้เช่า (tenant) อีกสี่ตัว ถูกถอดออกเมื่อระบบตัดสินใจเป็น single-tenant — trigger ที่ไม่มีวันทำงานคือคำโกหกที่ฝังอยู่ใน schema

สิ่งที่ schema ยังไม่รองรับ

รายการนี้สำคัญเท่ากับสิ่งที่มี เพราะเป็นสิ่งที่จะเซอร์ไพรส์ตอนต่อระบบจริง — ทุกข้อคือช่องว่างของ ER ไม่ใช่ของหน้าจอ

ยังไม่มีผลกระทบข้อเสนอ
ประวัติการใช้งานบัญชี UC 1.6 ต้องการดูว่าเกิดอะไรกับบัญชีบ้าง แต่มีแค่ ScoreUploadLog ซึ่งบันทึกเฉพาะการนำเข้าคะแนน เพิ่ม AuthEvent (userId, actorId, action, detail, at)
รายละเอียดแถวที่ถูกปฏิเสธ ScoreUploadLog เก็บแค่จำนวน recordsFail ไม่ได้เก็บว่าแถวไหนผิดเพราะอะไร — รายงานข้อผิดพลาด (FR-65) จึงสร้างจริงไม่ได้ เพิ่ม UploadReject (logId, row, field, value, reason)
สถานะการถอนรายวิชา CR-10 บอกว่าไม่นับผู้ถอนใน mean/SD ของการตัดเกรดอิงกลุ่ม แต่ Student ไม่มีคอลัมน์สถานะ เพิ่ม Student.status (ENROLLED · WITHDRAWN)
ประวัติการแก้คะแนนรายช่อง รู้ว่าใครอัปโหลดไฟล์ไหน แต่ไม่รู้ว่าใครแก้คะแนนช่องไหนเมื่อไร เพิ่ม ScoreAudit — ยังไม่มีความต้องการชัด
คะแนนข้ามหมู่เรียน ไม่ใช่ข้อบกพร่อง — ตัดออกโดยเจตนาตามมติ 2.7 · CLO และ Activity ผูกกับ courseId ถ้าต้องรองรับ ต้องเพิ่มชั้น CourseOffering เหนือ Course — ห้ามทำครึ่ง ๆ กลาง ๆ
ทำอะไรต่อ สามข้อแรกมีต้นแบบหน้าจอรองรับแล้วใน index-q.html — การเพิ่มตารางเหล่านี้เป็น migration ไม่ใช่การออกแบบใหม่
หน้านี้อธิบาย database/schema.prisma เวอร์ชัน 4 · ถ้า schema เปลี่ยน python scripts/check-schema-pages.py จะล้มและบอกว่าต้องแก้อะไร
