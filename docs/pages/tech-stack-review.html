3 ภาษาและรันไทม์ — ข้อดี ข้อเสีย ความเหมาะสม

เทคโนโลยีข้อดีข้อเสีย / ข้อจำกัดความเหมาะสมกับโครงงานนี้
TypeScript จับข้อผิดพลาดตั้งแต่ตอนคอมไพล์ · autocomplete แม่นยำ · type จาก Prisma และ Zod ไหลถึงกันทั้งระบบ · รีแฟกเตอร์ปลอดภัย เขียนช้ากว่า JS ตอนเริ่ม · ต้องเข้าใจ generics/utility types · เพิ่มขั้นตอน build เหมาะมาก ระบบคำนวณคะแนนต้องแม่นยำ — ความผิดพลาดเรื่องชนิดข้อมูล (เช่น null vs 0) คือความเสี่ยงตรงกับ H1 ที่ต้องถูก 100%
Node.js 20 LTS ใช้ภาษาเดียวกับฝั่ง client · ecosystem ใหญ่ที่สุด · เหมาะกับงาน I/O-bound เช่น API + ฐานข้อมูล · โฮสต์ได้เกือบทุกที่และมีตัวเลือกฟรี Single-threaded — งาน CPU หนักจะบล็อก event loop · ประสิทธิภาพเชิงคำนวณด้อยกว่า Go/Java เหมาะ ภาระหลักคือ query และรวมคะแนน ไม่ใช่การคำนวณหนัก · การใช้ภาษาเดียวลดภาระผู้พัฒนาคนเดียวได้จริง
npm workspaces ไม่ต้องติดตั้งเครื่องมือเพิ่ม (มากับ npm) · lockfile เดียว · แชร์ type และสคริปต์ระหว่าง client/server · clone แล้วรันได้ทันที ไม่มี task cache/graph แบบ Nx หรือ Turborepo · npm ci ติดตั้งทุก workspace แม้แก้ที่เดียว เหมาะ โปรเจกต์มีเพียง 2 แพ็กเกจ ความซับซ้อนไม่ถึงจุดที่ต้องใช้ build system เต็มรูปแบบ

4 ฝั่งผู้ใช้ (Frontend)

เทคโนโลยีข้อดีข้อเสีย / ข้อจำกัดความเหมาะสม
React 19 ชุมชนใหญ่ที่สุด หาเอกสาร/ตัวอย่างง่าย · component นำกลับมาใช้ซ้ำได้ · เหมาะกับ UI ที่มีสถานะซับซ้อนอย่างตารางกรอกคะแนน ต้องประกอบ library เองหลายตัว (router, data fetching, form) · React 19 ยังใหม่ ไลบรารีบางตัวตามไม่ทัน · SPA มี first-load ที่ใหญ่กว่า MPA เหมาะมาก หน้าจอกรอกคะแนน/แผนที่ CLO ต้องโต้ตอบสูงและอัปเดตทันทีโดยไม่รีโหลด — ตรงกับ NFR-01
Vite 7 + SWC Dev server เริ่มเร็วระดับวินาที · HMR แทบทันที · build ด้วย Rollup ที่ tree-shake ดี · ตั้งค่าน้อย ตอน dev กับ prod ใช้กลไกต่างกัน (ESM ตรง vs bundle) จึงมีโอกาสเจอบั๊กเฉพาะ prod · ปลั๊กอินบางตัวยังผูกกับ webpack เหมาะมาก รอบการพัฒนาเร็วมีผลโดยตรงกับงานที่มีผู้พัฒนาคนเดียวและกรอบเวลาจำกัด
Tailwind CSS 4 สไตล์อยู่ติดกับ markup แก้เร็ว · ไม่มีปัญหา CSS ชนกันทั้งโปรเจกต์ · ผูกกับ design token ได้ตรง ๆ · ไฟล์ผลลัพธ์เล็กเพราะตัดคลาสที่ไม่ใช้ HTML ยาวและอ่านยากตอนแรก · ต้องเรียนชื่อคลาส · ถ้าไม่แยก component จะเกิดการคัดลอกสไตล์ซ้ำ เหมาะ Verdure Design System กำหนด token ไว้แล้ว การใช้ Tailwind ทำให้เปลี่ยนสี/ระยะทั้งระบบได้จากไฟล์เดียว
React Router 7 มาตรฐานโดยพฤตินัยของ React SPA · nested route เหมาะกับ layout แดชบอร์ด · ทำ route guard ตามบทบาทได้ตรงไปตรงมา API เปลี่ยนบ่อยระหว่างเวอร์ชันหลัก ทำให้ตัวอย่างเก่าใช้ไม่ได้ · ต้องระวังว่า guard ฝั่ง client เป็นเพียง UX ไม่ใช่ความปลอดภัย เหมาะ โดยมีเงื่อนไขว่าการบังคับสิทธิ์จริงต้องอยู่ฝั่งเซิร์ฟเวอร์ (NFR-07) เสมอ
TanStack Query 5 จัดการ cache/refetch/stale state ให้อัตโนมัติ · ตัดโค้ด useEffect + useState ซ้ำ ๆ ออกได้มาก · มี loading/error state มาตรฐาน ทำให้ UI สม่ำเสมอ มีแนวคิดที่ต้องเรียน (queryKey, staleTime, invalidation) · ถ้าตั้ง key ผิดจะเห็นข้อมูลเก่าโดยไม่รู้ตัว เหมาะมาก หลังบันทึกคะแนน หน้าสรุป CLO ต้องอัปเดตตาม — invalidation จัดการเรื่องนี้ได้ตรงจุด
Zustand 5 API เล็กมาก เรียนรู้ครึ่งชั่วโมง · ไม่มี boilerplate แบบ Redux · bundle เล็ก · ใช้คู่กับ TanStack Query ได้ดีเพราะแยกหน้าที่ชัด ไม่มี devtools/time-travel ที่ครบเท่า Redux · โครงสร้างหลวม ถ้าโปรเจกต์โตอาจไร้ระเบียบ เหมาะ client-state ในระบบนี้มีน้อยมาก (auth เป็นหลัก) การใช้ Redux จะเกินความจำเป็น
Recharts 3 เขียนเป็น React component ตรงไปตรงมา · responsive ในตัว · รองรับ bar/line/radar ที่ต้องใช้กับผล CLO ครบ bundle ค่อนข้างใหญ่ (ควร lazy-load) · ปรับแต่งลึก ๆ สู้ D3 ไม่ได้ · เรนเดอร์ SVG จำนวนมากจะช้าเมื่อจุดข้อมูลเยอะ เหมาะ (มีเงื่อนไข) กราฟในระบบมีจุดข้อมูลหลักสิบ ไม่ถึงขีดจำกัด แต่ควรโหลดแบบ lazy เพื่อรักษาเกณฑ์ NFR-01
SheetJS (xlsx) มาตรฐานโดยพฤตินัยของการอ่าน/เขียน Excel ใน JS · ใช้โค้ดชุดเดียวกันได้ทั้ง client และ server · รองรับ .xlsx/.xls/.csv รุ่นชุมชนติดตั้งจาก CDN ไม่ใช่ npm registry (ต้องมีเน็ตตอนติดตั้งและ pin URL) · ฟีเจอร์จัดรูปแบบขั้นสูงอยู่ในรุ่น Pro · ไฟล์ใหญ่กินหน่วยความจำ เหมาะ (มีเงื่อนไข) จำเป็นเพราะ workflow เดิมของอาจารย์คือ Excel — แต่ต้องจำกัดขนาดไฟล์และตรวจสอบด้วย Zod ก่อนบันทึกเสมอ
lucide-react · sonner · clsx/cva ไอคอนชุดเดียวสม่ำเสมอและ tree-shake ได้ · toast ตั้งค่าน้อยแต่เข้าถึงได้ (a11y) · cva ทำให้ variant ของปุ่ม/badge เป็นระบบเดียว เพิ่มจำนวน dependency ที่ต้องดูแล · ถ้า import ไอคอนทั้งชุดโดยไม่ระวังจะทำให้ bundle โต เหมาะ เป็นส่วนที่ทำให้ทำตาม design system ได้จริงโดยไม่ต้องเขียน CSS ซ้ำ

5 ฝั่งเซิร์ฟเวอร์ (Backend)

เทคโนโลยีข้อดีข้อเสีย / ข้อจำกัดความเหมาะสม
Fastify 5 เร็วกว่า Express ราว 2 เท่าในงาน JSON · มี schema validation และ logger (pino) ในตัว · TypeScript support เป็นชั้นหนึ่ง · plugin system มีขอบเขตชัด (encapsulation) ชุมชนเล็กกว่า Express มาก ตัวอย่างและ middleware สำเร็จรูปน้อยกว่า · แนวคิด hook/plugin ต้องใช้เวลาเรียน · เอกสารภาษาไทยแทบไม่มี เหมาะ โครงงานต้องรายงานตัวเลขประสิทธิภาพ (NFR-01/02/03) การเลือกเฟรมเวิร์กที่เร็วและมี logger/validation ในตัวช่วยทั้งผลลัพธ์และเวลาเขียนโค้ด
Zod 4 ประกาศ schema ครั้งเดียวได้ทั้งการตรวจสอบตอนรันและ TypeScript type · ข้อความ error กำหนดเองเป็นภาษาไทยได้ (ตรงกับข้อ 3.3 ของแบบประเมิน) · ใช้ตรวจ .env ตอนบูตได้ด้วย เพิ่มขนาด bundle ถ้านำไปใช้ฝั่ง client ด้วย · schema ที่ซ้อนลึกอ่านยาก · การตรวจตอนรันมีต้นทุนเวลาเล็กน้อย เหมาะมาก เป็นเส้นแบ่ง “ห้ามเชื่อ input จาก client” ที่ระบุไว้ใน NFR-08 และเป็นหลักฐานตรงของข้อประเมิน 4.4
@fastify/helmet · cors · rate-limit · multipart ได้ security header, การจำกัด origin และการกันยิงซ้ำโดยเขียนโค้ดไม่กี่บรรทัด · เป็นปลั๊กอินทางการ ดูแลพร้อมกับ core ค่าเริ่มต้นของ helmet (โดยเฉพาะ CSP) อาจบล็อกทรัพยากรของ client จนต้องปรับ · rate-limit แบบเก็บในหน่วยความจำใช้ไม่ได้ถ้าขยายเป็นหลายอินสแตนซ์ เหมาะ ระบบเป็น single instance ของคณะเดียว ข้อจำกัดเรื่อง in-memory store จึงยังไม่กระทบ
tsx (dev) + tsc (build) แก้ไฟล์แล้วเซิร์ฟเวอร์รีสตาร์ตเองทันที ไม่ต้อง build ระหว่าง dev · ตอน production คอมไพล์เป็น JS ล้วนจึงเริ่มเร็วและไม่ต้องพึ่ง tsx พฤติกรรมตอน dev (esbuild ไม่ตรวจ type) ต่างจากตอน build (tsc ตรวจ) จึงต้องรัน typecheck แยก ไม่งั้นบั๊กจะโผล่ตอน build เหมาะ สคริปต์ verify ที่ราก บังคับ typecheck ก่อน build อยู่แล้ว ช่องว่างนี้จึงถูกปิดด้วยกระบวนการ

6 ฐานข้อมูลและ ORM

เทคโนโลยีข้อดีข้อเสีย / ข้อจำกัดความเหมาะสม
PostgreSQL รองรับ transaction และ foreign key อย่างเคร่งครัด · มี CHECK constraint, trigger, partial unique index ที่ระบบนี้ใช้จริง · ชนิดข้อมูลครบ (enum, JSON, numeric ที่ไม่เพี้ยน) · โอเพนซอร์สและฟรี ตั้งค่าและปรับจูนยากกว่า MySQL เล็กน้อย · ต้องเข้าใจ connection pooling เมื่อโฮสต์แบบ serverless · เครื่องมือ GUI ไม่แพร่หลายเท่า เหมาะมาก ความถูกต้องของคะแนนคือหัวใจ (H1) — การบังคับ score ≤ maxScore และ “LEAD ไม่เกิน 1 คนต่อวิชา” ที่ระดับฐานข้อมูล คือสิ่งที่ MySQL รุ่นเก่าทำได้ไม่ครบ
Supabase (โฮสต์ Postgres) ได้ Postgres จริงพร้อมใช้โดยไม่ต้องดูแลเซิร์ฟเวอร์ · มีแดชบอร์ด สำรองข้อมูล และ connection string สองแบบ (pooled/direct) ที่ Prisma ต้องใช้ · มีระดับใช้งานฟรีที่พอสำหรับโครงงาน ผูกกับผู้ให้บริการภายนอกและต้องมีอินเทอร์เน็ต · โครงการฟรีถูกพักการทำงานเมื่อไม่ใช้งานนาน ทำให้คำขอแรกช้า (กระทบการวัด NFR-01 ถ้าไม่วอร์มก่อน) · ข้อมูลอยู่นอกประเทศ เหมาะ (มีเงื่อนไข) เหมาะกับช่วงพัฒนาและนำเสนอ แต่ถ้าคณะนำไปใช้จริงกับข้อมูลนักศึกษา ควรย้ายไปโฮสต์ภายในสถาบัน — ควรระบุไว้เป็นข้อเสนอแนะในบทที่ 5
Prisma ORM 6 ไฟล์ schema เดียวเป็น source of truth ของโครงสร้างข้อมูล · query แบบ type-safe ทั้งหมด · migration มีประวัติชัดเจน ย้อนดูได้ · prisma studio ช่วยตรวจข้อมูลตอนพัฒนา · แก้ปัญหา N+1 ได้ด้วย include/select เขียน CHECK constraint และ trigger ในไฟล์ schema ไม่ได้ ต้องเขียน SQL แยก · query ที่ซับซ้อนมากอาจต้องกลับไปใช้ raw SQL · เพิ่มขั้นตอน prisma generate ในทุกที่ที่ build · เอนจินเป็นไบนารีทำให้ image ใหญ่ขึ้น เหมาะ ข้อจำกัดถูกรับมือแล้วด้วย migration 0002 และกฎห้ามใช้ db push ซึ่งบันทึกไว้ในหัวไฟล์ schema แล้ว
Raw SQL migration (0002) ทำให้กฎทางธุรกิจที่สำคัญที่สุดถูกบังคับที่ชั้นล่างสุด แม้แอปจะมีบั๊กก็ยังกันข้อมูลเสียได้ · เป็นหลักฐานเชิงวิศวกรรมที่ดีเวลานำเสนอ ถูกลบเงียบ ๆ ได้ถ้าใช้ prisma db push · ต้องดูแล SQL ด้วยมือและทดสอบเอง · ผู้ที่มาสานต่อต้องรู้ว่ามีอยู่ เหมาะ (ต้องระวัง) คุ้มค่ากับความเสี่ยง แต่ต้องเขียน unit test ครอบและระบุข้อห้ามให้ชัดในคู่มือผู้พัฒนา

7 ความปลอดภัย

เทคโนโลยีข้อดีข้อเสีย / ข้อจำกัดความเหมาะสม
argon2 (Argon2id) ชนะ Password Hashing Competition ปี 2015 และเป็นคำแนะนำอันดับหนึ่งของ OWASP ปัจจุบัน · ต้านการเดารหัสด้วย GPU ได้ดีกว่า bcrypt เพราะกิน memory · ปรับ cost ได้ตามฮาร์ดแวร์ เป็น native module ต้องคอมไพล์ตอนติดตั้ง ทำให้ CI/Docker ช้าลงและอาจพังบนบางแพลตฟอร์ม · ใช้ RAM ต่อการแฮชสูงกว่า bcrypt เหมาะมาก ข้อประเมิน 4.1 และ NFR-05 ต้องการหลักฐานว่ารหัสผ่านไม่ได้เก็บแบบอ่อนแอ — Argon2id คือคำตอบที่อธิบายต่อกรรมการได้ง่ายที่สุด
jose (JWT) รองรับมาตรฐาน JOSE ครบและใช้ Web Crypto API · เป็น ESM สมัยใหม่ ทำงานได้ทั้ง Node และ edge runtime · ยังได้รับการดูแลต่อเนื่อง ต่างจาก jsonwebtoken ที่นิ่งไปนาน API ละเอียดกว่าและตัวอย่างน้อยกว่า jsonwebtoken · JWT โดยธรรมชาติเพิกถอนกลางคันไม่ได้จนกว่าจะหมดอายุ · ถ้าเก็บ token ผิดที่ (localStorage) จะเสี่ยง XSS เหมาะ (มีเงื่อนไข) อายุ access token 15 นาที + refresh 7 วัน ลดผลของการเพิกถอนไม่ได้ แต่ควรระบุวิธีเก็บ token และการ logout ให้ชัดในเอกสารความปลอดภัย
RBAC + course-scope guard ตอบคำถามการเข้าถึงด้วยเพียงสองข้อ (บทบาทอะไร · สอนวิชาไหน) ทำให้ตรวจสอบและทดสอบง่าย · ตอบ 404 แทน 403 จึงไม่รั่วข้อมูลว่ามีรายวิชานั้นอยู่จริง ตรรกะกระจายอยู่ใน middleware และ service ต้องระวังไม่ให้ลืมป้องกันบาง endpoint · ยังไม่มีสิทธิ์ระดับละเอียด (per-field) เหมาะ ตรงกับ NFR-06/07 และข้อประเมิน 4.2/4.3 โดยตรง — และควรมีเทสต์ครอบทุก endpoint เพื่อกันการลืม

8 เครื่องมือพัฒนาและ CI/CD

เทคโนโลยีข้อดีข้อเสีย / ข้อจำกัดความเหมาะสม
Vitest 3 + coverage-v8 ใช้ค่าคอนฟิกร่วมกับ Vite จึงตั้งค่าน้อย · เร็วมากและ watch mode ลื่น · API เข้ากันได้กับ Jest ทำให้หาตัวอย่างง่าย · รายงาน coverage เป็นหลักฐานประกอบ NFR-14 ได้ทันที ระบบนิเวศเล็กกว่า Jest · ปลั๊กอินบางตัวยังไม่รองรับ · ตัวเลข coverage สูงไม่ได้แปลว่าทดสอบครบเชิงตรรกะ เหมาะมาก H1 ต้องการหลักฐานว่าสูตรคำนวณถูกต้องรวมกรณีขอบ — unit test คือหลักฐานที่ตรวจซ้ำได้ ไม่ใช่คำกล่าวอ้าง
ESLint 10 + typescript-eslint + Prettier จับรูปแบบที่เสี่ยงผิดตั้งแต่ก่อนรัน · กฎ react-hooks กัน bug ที่หายาก · Prettier ยุติการถกเรื่องรูปแบบโค้ด · ตรวจอัตโนมัติใน CI ตั้งค่าให้ทั้งสองตัวไม่ทะเลาะกันต้องใช้เวลา · กฎที่เข้มเกินไปทำให้เสียเวลากับเรื่องไม่สำคัญ เหมาะ ผู้พัฒนาคนเดียวไม่มีคนรีวิว — เครื่องมืออัตโนมัติทำหน้าที่ผู้รีวิวคนที่สองแทน
GitHub Actions (CI) รัน format → lint → typecheck → test → build ทุก PR โดยไม่ต้องจำ · ยกเลิกงานที่ถูกแทนที่อัตโนมัติเพื่อประหยัดเวลา · ฟรีสำหรับ repo สาธารณะ · เป็นหลักฐานกระบวนการพัฒนาที่ใส่ในเล่มได้ โควตานาทีจำกัดสำหรับ repo ส่วนตัว · ผูกกับ GitHub · ต้องใส่ค่า env หลอกเพื่อให้ prisma generate ผ่าน ซึ่งอาจสับสนสำหรับผู้อ่านใหม่ เหมาะ ทำให้ไม่มีโค้ดที่คอมไพล์ไม่ผ่านหรือเทสต์ตกหลุดเข้า main ได้เลย
Docker Compose (dev) รันเหมือนกันทุกเครื่อง ลดปัญหา “เครื่องผมรันได้” · เตรียมทางสำหรับการส่งมอบให้คณะในอนาคต กินทรัพยากรเครื่องมากและ hot reload ช้ากว่ารันตรง ๆ (โดยเฉพาะบน Windows) · ต้องดูแล Dockerfile เพิ่ม · compose ปัจจุบันไม่ได้รวมบริการฐานข้อมูล จึงยังต้องพึ่ง Supabase เหมาะ (เสริม) มีไว้ดีเวลาสาธิตหรือส่งมอบ แต่ระหว่างพัฒนาจริงการรัน npm run dev ตรง ๆ ยังเร็วกว่า
สคริปต์เอกสาร (docx, plan-csv) สร้างเอกสารบทที่ 2 และแผนงานจาก Markdown ที่เป็น source of truth อัตโนมัติ · แก้ที่เดียวแล้วเอกสารตรงกันเสมอ ลดงานคัดลอกด้วยมือ รูปแบบเอกสารที่ได้อาจยังต้องจัดหน้าเพิ่มให้ตรงข้อกำหนดรูปเล่ม · เป็นสคริปต์เฉพาะกิจที่ต้องดูแลเอง เหมาะ ตรงกับปัญหาจริงของงานปริญญานิพนธ์ที่เอกสารกับโค้ดมักไม่ตรงกัน

11 สรุปความเหมาะสมโดยรวม

เมื่อพิจารณาเทียบกับข้อจำกัดจริงของโครงงาน — ผู้พัฒนาคนเดียว · กรอบเวลาหนึ่งภาคการศึกษา · ต้องรายงานตัวเลขประสิทธิภาพและความถูกต้อง 100% — stack ชุดนี้มีความเหมาะสมในระดับสูง โดยมีเหตุผลหลัก 4 ข้อ

เกณฑ์พิจารณาคำอธิบายผล
1. ความถูกต้องของข้อมูลTypeScript strict + Zod ที่ขอบระบบ + CHECK/trigger ที่ฐานข้อมูล ทำให้มีการป้องกันสามชั้น สอดคล้องโดยตรงกับ H1 ที่ต้องถูก 100%สูงมาก
2. ความเร็วในการพัฒนาภาษาเดียวทั้งระบบ · Vite HMR · Prisma generate type ให้เอง · monorepo สคริปต์เดียว — ลดเวลาที่เสียไปกับงานประกอบร่างสูง
3. ประสิทธิภาพตามเกณฑ์ NFRFastify + Postgres + Prisma ที่ใช้ include อย่างถูกวิธี เพียงพอกับเป้าหมาย < 1–2 วินาที ที่ 200 นักศึกษา อย่างมีระยะเผื่อสูง
4. ความยั่งยืน / ส่งต่อได้ทุกอย่างเป็นโอเพนซอร์สและเป็นที่นิยม หาคนสานต่อได้ · CI และเอกสารอัตโนมัติทำให้ผู้รับช่วงเข้าใจระบบเร็วดี
