# ความจุฐานข้อมูลและการทำความสะอาด (Supabase Free · PostgreSQL 17)

See also: [[schema]] · [[threat-mitigations]] · [[api-design-plan]]

> **วัดเมื่อ:** 2026-10-22 บน Supabase จริง (ap-northeast-1, transaction pooler + `pgbouncer=true`) ·
> ข้อมูลจำลอง `TEST-SIM` ถูกลบหลังวัด · ผลดิบอยู่ที่ `docs/evidence/report-04/db-load-simulation.txt`

## 1. สมมติฐานการใช้งาน

อาจารย์มากกว่า 10 คน (ใช้ 12) · คนละ 4 วิชา × 2 ห้อง · ห้องละ 40 หรือ 60 คน · 15 กิจกรรม (สัปดาห์ละ 1)
หนึ่งห้อง = `Course` หนึ่งแถว → **96 ห้องต่อเทอม** · ช่องคะแนน 96 × 40 × 15 = **57,600** (ห้องละ 60 คน: 86,400)

## 2. สิ่งที่วัดได้ (2 ห้อง × 60 คน × 15 กิจกรรม = 1,800 ช่อง)

| เหตุการณ์ | ผล |
|---|---|
| กรอกครั้งแรกทุกช่อง | `Score` ≈ 0.27 KB/ช่อง · `ScoreChange` ≈ 0.3 KB/แถว |
| แก้ทุกช่อง 10 รอบ (18,000 ครั้ง) | `ScoreChange` โต 616 KB → 5.8 MB (เพิ่มเชิงเส้น) · `Score` โต 512 KB → 2.3 MB จาก dead tuple 17,564 แถว |
| burst: PUT 900 ช่อง 2 ห้อง + แดชบอร์ด 3 หน้า พร้อมกัน | ทั้งหมด 200 เสร็จใน ≈ 5 วินาที · PUT 900 ช่อง ≈ 4.6–5.0 วินาที (NFR-03 นำเข้า 500 แถว ≤ 10 วินาที ผ่าน) · เขียน `ScoreChange` 1,800 แถวครบ |
| `VACUUM (ANALYZE)` | 1.1 วินาที ไม่ล็อกตาราง · dead tuple เหลือ 0 แต่ขนาดไฟล์ไม่ลด (พื้นที่ถูกนำกลับมาใช้) |
| `VACUUM FULL "Score"` | 0.2 วินาที ล็อกตารางระหว่างทำ · 2.5 MB → 0.4 MB (คืนพื้นที่จริง) |
| autovacuum | เปิดอยู่ · เริ่มเมื่อ dead tuple > 50 + 20% ของแถวที่มี · ตรวจทุก 60 วินาที (รอบทดสอบแรกเห็น autovacuum ทำงานเองระหว่างแก้รอบที่ 10) |

**ข้อสรุปสำคัญ:** `Score` บวมชั่วคราวแต่ autovacuum ดูแลเอง · **`ScoreChange` (ประวัติการแก้) คือตัวที่กินพื้นที่จริง** เพราะเพิ่มอย่างเดียว ทุกการแก้ 1 ช่อง = 1 แถวถาวร (A-12, NFR-16) และ VACUUM ไม่ทำให้มันเล็กลง

## 3. ประมาณการต่อเทอม (96 ห้อง)

`ขนาด ≈ ช่อง × 0.27 KB × (1–2 เท่าจาก bloat) + ช่อง × จำนวนครั้งที่เขียนต่อช่อง × 0.3 KB + ≈ 2 MB ตารางอื่น`

| รูปแบบการใช้งาน (เขียนต่อช่องรวมครั้งแรก) | ห้องละ 40 คน | ห้องละ 60 คน |
|---|---|---|
| ปกติ — กรอก 1 ครั้ง แก้ 1 ครั้ง (2) | ≈ 50–70 MB | ≈ 75–100 MB |
| แก้บ่อย (5) | ≈ 105–120 MB | ≈ 155–180 MB |
| แก้หนักเหมือนการจำลอง (10) | ≈ 190–205 MB | ≈ 285–310 MB |

**ใช้ได้กี่เทอมก่อนถึงเส้นเตือน 350 MB (70% ของ 500 MB · ฐานตอนนี้ 12 MB):**

| | 40 คน | 60 คน |
|---|---|---|
| ปกติ | 5–6 เทอม | 3–4 เทอม |
| แก้บ่อย | ≈ 3 เทอม | ≈ 2 เทอม |
| แก้หนัก | ≈ 1.5 เทอม | ≈ 1 เทอม |

**ถ้าถึง 500 MB:** Supabase Free เปลี่ยนโปรเจกต์เป็น **read-only** — `INSERT` ล้มด้วย `cannot execute INSERT in a read-only transaction` · กรอกคะแนนไม่ได้จนกว่าจะลบข้อมูล + `vacuum` หรืออัปเกรดเป็น Pro (8 GB)

## 4. ตารางทำความสะอาด

| เมื่อไร | ทำอะไร | ผลกระทบ |
|---|---|---|
| ตลอดเวลา | autovacuum (เปิดอยู่แล้ว ไม่ต้องทำอะไร) | ไม่มี |
| หลังสัปดาห์ที่นำเข้า/แก้คะแนนจำนวนมาก (สอบกลางภาค ~สัปดาห์ 8 · ปลายภาค ~สัปดาห์ 15 · วันตัดเกรด) | `VACUUM (ANALYZE) "Score", "ScoreChange";` | ≈ 1 วินาที ไม่ล็อก · ทำให้สถิติของ query planner สดด้วย |
| ทุกเดือน | ตรวจขนาดด้วย SQL ข้อ 5 | ไม่มี |
| ปลายเทอม หลังตรึงเกรดและพ้นช่วงอุทธรณ์ | ส่งออก `ScoreChange` ของเทอมนั้นเป็นไฟล์เก็บ แล้วลบแถวที่เก่ากว่าที่ตกลงกันไว้ จากนั้น `VACUUM FULL "ScoreChange";` | `VACUUM FULL` ล็อกตาราง ทำนอกเวลาใช้งาน (ช่วงปิดเทอม) |
| ขนาด ≥ 350 MB | ทำขั้นปลายเทอมทันที หรือวางแผนอัปเกรด | — |
| ขนาด ≥ 450 MB | ด่วน: ใกล้ read-only | — |

`VACUUM` ต้องรันผ่าน **SQL Editor ของ Supabase** หรือการเชื่อมต่อพอร์ต **5432** (`DIRECT_URL`) · ผ่าน `DATABASE_URL` ที่มี `pgbouncer=true` ไม่ได้ (วัดแล้วได้ `VACUUM cannot run inside a transaction block`)

**ต้องตัดสินใจร่วมกัน:** เก็บ `ScoreChange` ไว้นานแค่ไหน — NFR-16 ต้องการประวัติไว้ตอบการอุทธรณ์เกรด จึงไม่ควรลบก่อนพ้นช่วงอุทธรณ์ของเทอมนั้น

## 5. SQL ตรวจสุขภาพ (รันใน SQL Editor)

```sql
-- ขนาดรวมเทียบโควตา
SELECT pg_size_pretty(pg_database_size(current_database())) AS used, '500 MB' AS free_quota;

-- ตารางใหญ่สุด และ dead tuple ที่ค้าง
SELECT relname, pg_size_pretty(pg_total_relation_size(relid)) AS size,
       n_live_tup AS live, n_dead_tup AS dead, last_autovacuum
FROM pg_stat_user_tables ORDER BY pg_total_relation_size(relid) DESC LIMIT 8;
```

`dead` มากกว่า `live` ค้างนานหลายวัน = autovacuum ตามไม่ทัน ให้รัน `VACUUM (ANALYZE)` ตารางนั้นเอง

## 6. ข้อจำกัดของการประมาณ

- วัดจาก 2 ห้องแล้วคูณ · ขนาดจริงต่อแถวขึ้นกับความยาวชื่อและเหตุผลการยกเว้น
- ไม่ได้วัด 96 ห้องพร้อมกันจริง · `GET /dashboard/overview` วนโหลดทีละวิชา จึงช้าตามจำนวนวิชาที่มองเห็น (ประมาณ 20–40 วินาทีสำหรับ 8 ห้อง ยังไม่ได้แก้)
- ทุกเวลาวัดกับ `.env` ปัจจุบัน (`pgbouncer=true`) — เปลี่ยนเป็นพอร์ต 5432 เร็วขึ้นราว 2–3 เท่า
