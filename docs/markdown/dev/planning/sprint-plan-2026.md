**ทำไมจัดกลุ่มแบบนี้**
- **ธีรณัฎฐ์** ถือทุก feature ที่มีสูตรคำนวณ (ผล CLO CR-01…07 และเกรด CR-08…11) — สูตรต้องอยู่ในมือคนเดียว ไม่ให้เกิดการคำนวณซ้ำคนละที่ซึ่ง FR-88 ห้ามไว้ · จัดการรายวิชาผูกกับระบบสิทธิ์ที่เขาทำเป็นงานฐานอยู่แล้ว
- **นัจญมา** ถือ CLO → วัตถุประสงค์/เกณฑ์ ที่ต้องทำต่อกันเป็นลำดับ ไม่ต้องรอส่งงานข้ามคน · จัดการผู้ใช้เป็นงานที่เริ่มอยู่แล้วใน S1
- **นูรีน** ถือรายชื่อ → คะแนน ที่ใช้ระบบ Excel ชุดเดียวกัน · บัญชีของฉันเป็นงานเบา บาลานซ์กับงานคะแนนที่หนัก

## 8. กติกาทำงานขนานกัน

1. **1 feature = 1 เจ้าของ** — เจ้าของตัดสินใจเรื่องภายใน feature ได้เอง คนอื่นเสนอผ่าน PR review ไม่แก้โค้ดของ feature คนอื่นตรง ๆ
2. **แยกโฟลเดอร์ตาม feature** — `app/server/src/modules/<feature>/` และ `app/client/src/features/<feature>/` ตามโครง Route → Controller → Service → Repository ใน [[code-rule]] §3
3. **ไฟล์ที่ใช้ร่วม** (`database/schema.prisma` · migration · routes index · เมนู AppShell) — เปิด PR เล็กแยกต่างหาก · **ธ เป็นผู้ merge migration คนเดียว** เพื่อไม่ให้เลข migration ชนกัน
4. **Branch** `feature/<เลข feature>-<งาน>` เช่น `feature/f6-score-import` แตกจาก `develop` ตาม [[git-rule]] §2
5. **คู่ review:** สูตรคำนวณของ ธ (F5, F8) → น review · Excel ของ นู (F6, F7) → ธ review · ที่เหลือ review ข้ามคนตามสะดวก — [[git-rule]] บังคับอย่างน้อย 1 คนอยู่แล้ว
6. **จังหวะ:** จันทร์ต้น sprint planning 30 นาที · แจ้งในกลุ่มก่อนเริ่มทุก task ([[code-rule]] §7 ข้อ 1) · ศุกร์ทุกสัปดาห์ส่งสรุปให้เจ้าของโปรเจกต์ (§7 ข้อ 4) · ศุกร์สัปดาห์ที่ 2 demo เทียบ Exit criteria · อาทิตย์ท้าย sprint merge `develop` → `main` เมื่อ Exit ผ่าน
7. **DoD ทุก PR:** lint + typecheck ผ่าน · unit test ของ service ผ่าน · หน้าจอใช้ได้จริง · อัปเดตเอกสาร ([[git-rule]] §6 · [[code-rule]] §6)
8. **ต้นแบบคือสเปก** — ถ้าพฤติกรรมในแอปต่างจาก `index-q.html` ให้ถือต้นแบบเป็นหลัก เว้นแต่ขัดกับ [[srs]] แล้วแก้ต้นแบบหรือ SRS ให้ตรงกันใน PR เดียวกัน
