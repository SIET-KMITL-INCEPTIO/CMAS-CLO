# แผน Office Add-in: แก้คะแนนใน Excel แล้วหน้าเว็บเปลี่ยนตาม

สถานะ: **ข้อเสนอ ยังไม่ได้พัฒนา** · อ้างอิงโค้ด ณ 2026-11-12
เป้าหมาย: อาจารย์ส่งออกแบบฟอร์มคะแนนเป็น Excel แก้คะแนนในไฟล์ แล้วข้อมูลในหน้าเว็บเปลี่ยนตามโดยไม่ต้องอัปโหลดไฟล์

> ข้อความเรื่องพฤติกรรมของ Office.js (เหตุการณ์ ข้อจำกัดแพลตฟอร์ม เวอร์ชัน) มาจากความรู้ทั่วไป
> **ต้องตรวจกับเอกสาร Microsoft Learn ฉบับล่าสุดก่อนลงมือเขียน** ส่วนที่อ้างโค้ดของระบบตรวจกับโค้ดแล้ว

---

## 1. ทำไมต้องมีตัวกลาง

ไฟล์ `.xlsx` ที่ดาวน์โหลดเก็บในเครื่อง ส่งการแก้ไขกลับเองไม่ได้ ต้องมีตัวกลางเรียก API ของระบบ
ระบบปัจจุบันตั้งใจไม่ใช้ Macro: [`excel.ts`](../../../../app/server/src/lib/excel.ts) รับเฉพาะ `.xlsx`
ตรวจด้วย magic bytes ของ ZIP ปฏิเสธไฟล์ที่มีสูตร และไม่เก็บไฟล์ไว้ (อ่านในหน่วยความจำ) จึงเลือก Office Add-in เป็นตัวกลางแทน Macro

## 2. สิ่งที่ระบบมีอยู่แล้ว (ตรวจจากโค้ด)

| เรื่อง | สถานะ | ที่มา |
| --- | --- | --- |
| เขียนคะแนนเป็นชุด | มี `PUT /courses/:courseId/scores` (สิทธิ์ `score.edit`) | `scores.route.ts` |
| ค่าที่ส่งได้ | เลข ≥ 0, `"EXCUSED"` หรือ `null`; มี `source` และ `reason` | `scores.validator.ts` |

| ประวัติแก้คะแนน | `ScoreChange` เขียนพร้อมคะแนนในธุรกรรมเดียว; เซลล์ที่ไม่เปลี่ยนไม่เขียน | `score-writer.ts` |
| ขอบเขตรายวิชา | คนไม่มีสิทธิ์ได้ 404 ไม่ใช่ 403 | `access.middleware.ts` |

| ตรวจแก้ชนกัน (version/updatedAt) | **ไม่พบใน `score-writer.ts`** (ใครเขียนทีหลังชนะ) | `score-writer.ts` |

## 3. สถาปัตยกรรมที่เสนอ

```
Excel (task pane ของ Add-in)  ──HTTPS + Bearer access token──▶  API เดิม (/api/...)
        ▲                                                            │
        │ แบบฟอร์ม + ผูกคอลัมน์ด้วย [id] ใน header                    ▼
   ปุ่ม "เปิดจาก CMAS"                                      ฐานข้อมูล + ScoreChange
                                                                      │
หน้าเว็บ ◀── polling สั้น หรือ SSE ◀──────────────────────────────────┘
```

หลักการ: Add-in เป็น **ไคลเอนต์ API อีกตัว** ผ่านกฎเดียวกับเว็บ (Route → Controller → Service → Repository, `config: { access }`)
ห้ามเขียนตรงเข้าฐานข้อมูล ห้ามเปิดช่องทางที่ข้ามการตรวจสิทธิ์

### 3.1 ส่วนที่ต้องสร้าง

1. **โปรเจกต์ Add-in** (`app/addin/` หรือ workspace ใหม่): manifest, task pane (React ได้), โค้ดอ่าน/เขียนเซลล์ด้วย Office.js
2. **ล็อกอินใน Add-in**: ใช้หน้าต่าง Office Dialog API เปิดหน้า login ของเว็บ แล้วส่งโทเคนกลับ (ดู §5.3)
3. **API เสริมที่เหมาะกับ Add-in** (ถ้าจำเป็น): ดึงเฉพาะส่วนที่เปลี่ยนตั้งแต่เวลา T เพื่อซิงก์ทุกทิศ
4. **แจ้งหน้าเว็บ**: เริ่มจาก polling ลด `staleTime` เฉพาะหน้ากรอกคะแนน ยกระดับเป็น SSE เมื่อจำเป็น
5. **กติกาชนกัน** (ดู §6)

## 4. ขั้นตอนทำงาน (ที่เสนอ)

1. อาจารย์เปิด Excel → แผง CMAS → ล็อกอิน → เลือกรายวิชา
2. Add-in ดึงตารางคะแนนจาก `GET .../scores` แล้วเขียนลงชีต โดยหัวคอลัมน์ใช้รูปแบบเดิม `ชื่อ (เต็ม N) [id]` ([`activityHeader`](../../../../app/server/src/lib/excel.ts))
3. อาจารย์แก้เซลล์ → Add-in รับเหตุการณ์เปลี่ยนเซลล์ → รวมเป็นชุด (debounce) → `PUT .../scores` ด้วย `source: "MANUAL"`
4. API ตรวจและเขียน พร้อม `ScoreChange`; เซลล์ที่ผิดกติกา Add-in แสดงสีและข้อความ ไม่เขียนทับเงียบๆ
5. หน้าเว็บรีเฟรชข้อมูลตามรอบหรือเมื่อมีสัญญาณ

กิจกรรมใหม่ น้ำหนัก และวัตถุประสงค์ **ยังสร้างในเว็บเท่านั้น** (ผลรวมน้ำหนักกิจกรรมในรายวิชา = 100 และน้ำหนักวัตถุประสงค์ต่อกิจกรรม = 100)
Excel แก้ได้เฉพาะ **คะแนน** ถ้าเพิ่มคอลัมน์เองในชีต Add-in ต้องไม่ส่งและแจ้งเตือน

## 5. ข้อจำกัดของ Office Add-in

### 5.1 การพัฒนาและแจกจ่าย
- เขียนด้วย HTML/JavaScript (Office.js) ไม่ใช่ VBA; ต้องมีไฟล์ manifest
- หน้า Add-in ต้องโฮสต์บน **HTTPS** ที่เครื่องอาจารย์เข้าถึงได้ (ตอนพัฒนาใช้ localhost ได้)
- แจกอาจารย์หลายคนผ่าน **Microsoft 365 Admin Center** (Integrated Apps) ต้องมีผู้ดูแลของสถาบันดำเนินการ; ถ้าไม่มีสิทธิ์ ทำได้แค่ sideload รายเครื่อง (เหมาะกับสาธิต)
- ต้องดูแลเมื่อ Office/Office.js อัปเดต

### 5.2 ความสามารถของ Excel
- แพลตฟอร์มและเวอร์ชันรองรับไม่เท่ากัน (Windows, Mac, เว็บ, มือถือ) ต้องตรวจ **requirement set** ของ API ที่ใช้ก่อน
- เหตุการณ์เปลี่ยนเซลล์ทำงานเมื่อไฟล์เปิดและ task pane ทำงานอยู่เท่านั้น ถ้าปิดไฟล์หรือปิดแผง การแก้ไขไม่ถูกส่ง
- วางข้อมูลทีละหลายร้อยเซลล์ทำให้เกิดเหตุการณ์จำนวนมาก ต้องรวมเป็นชุดและจำกัดขนาดคำขอ
- ฝั่ง API ปัจจุบันจำกัดการนำเข้าไฟล์ 2,000 แถว (`MAX_ROWS`) และ 10 MB; การเขียนชุดผ่าน `PUT` ต้องกำหนดเพดานของตัวเอง
- Add-in ทำงานในแผงด้านข้าง ไม่ได้เปลี่ยนไฟล์ให้เป็นของระบบ ไฟล์ยังเป็นไฟล์ Excel ธรรมดา

### 5.3 การยืนยันตัวตนและความปลอดภัย
- **CORS:** ตอนนี้อนุญาต origin เดียว (`CORS_ORIGIN`) และโปรดักชันบังคับ `https://` Add-in มี origin คนละตัว ต้องขยายเป็นรายการ origin ที่อนุญาต โดยไม่เปิดกว้าง (`*` ใช้ร่วมกับ `credentials` ไม่ได้)
- **Refresh cookie ใช้ไม่ได้ข้ามไซต์:** `SameSite=Strict` ทำให้ cookie `cmas_rt` ไม่ถูกส่งจาก origin ของ Add-in ต้องออกแบบวิธีต่ออายุโทเคนแยก (เช่น ล็อกอินใหม่ผ่าน Dialog เมื่อ access token หมดอายุ) **ห้ามผ่อน `SameSite` ของ cookie เดิม** เพราะเป็นมาตรการ S-2
- **ห้ามเก็บโทเคนระยะยาวในไฟล์ Excel** (ต่างจาก Macro ที่มักฝังไว้ในไฟล์) เก็บในหน่วยความจำของ task pane หรือที่เก็บของ Add-in เท่านั้น
- Add-in ต้องส่ง access token ใน header `Authorization` เหมือนเว็บ และ `authMiddleware` ยังอ่าน User จากฐานข้อมูลสดทุกครั้ง (กฎข้อ 2) ห้ามทำทางลัดที่เชื่อ claim ใน JWT
- ทุก route ใหม่ต้องประกาศ `config: { access }` ไม่เช่นนั้นเซิร์ฟเวอร์ไม่ยอมบูต
- คนละรายวิชา/ไม่มีสิทธิ์ต้องได้ **404** เหมือนเดิม
- กรณีล็อกอินด้วย Google (นอกโดเมนสถาบันต้องรอผู้ดูแลอนุมัติ) ต้องทดสอบใน Dialog ของ Office ว่าหน้าต่างล็อกอินทำงานได้

### 5.4 การใช้งานจริง
- ต้องออนไลน์ตลอด ถ้าเน็ตหลุด การแก้ไขต้องเข้าคิวและส่งซ้ำ (หรือแจ้งชัดว่ายังไม่ซิงก์)
- Excel บนมือถือรองรับ Add-in จำกัดกว่า desktop
- `staleTime` 30 วินาทีของหน้าเว็บทำให้หน้าเว็บเห็นการแก้ไขช้ากว่า "real time" ถ้ายังไม่เพิ่มกลไก push

## 6. ข้อควรระวัง (ความถูกต้องของข้อมูล)

1. **แก้ชนกัน:** `score-writer.ts` ไม่มีการตรวจเวอร์ชัน อาจารย์แก้ในเว็บกับ Excel พร้อมกัน ฝั่งที่ส่งทีหลังทับ
   ข้อเสนอ: ส่ง `updatedAt` ของเซลล์ที่อ่านมา แล้วให้ API ปฏิเสธเมื่อค่าเปลี่ยนไปแล้ว (ต้องเพิ่มใน validator และ writer)
2. **ค่าว่าง:** การนำเข้าไฟล์ปัจจุบันถือว่า "ช่องว่าง = ไม่เขียนทับ" (FR-62) แต่ `PUT` รับ `null` ซึ่งหมายถึงล้างคะแนน
   Add-in ต้องไม่แปลงเซลล์ว่างเป็น `null` โดยอัตโนมัติ ต้องกำหนดกติกาชัดว่าลบเซลล์ = ล้างคะแนนหรือไม่ และแสดงให้อาจารย์เห็นก่อน
3. **กฎเดียวกับเว็บ:** เกรดถูกตรึง, กิจกรรมปิดรับ, นักศึกษาถอนรายวิชา, คะแนนเกินเต็ม/ติดลบ ต้องถูกปฏิเสธที่เซิร์ฟเวอร์ ห้ามพึ่งการตรวจใน Add-in อย่างเดียว
4. **คำว่า "ยกเว้น":** ไฟล์นำเข้าใช้คำไทย Add-in ต้องแปลงเป็น `"EXCUSED"` อย่างสม่ำเสมอ
5. **รหัสนักศึกษา:** เก็บเป็นข้อความเสมอ (เลข 0 นำหน้าหาย) เหมือนที่ `buildWorkbook` ตั้งรูปแบบ `@`
6. **สูตร:** ระบบปัจจุบันไม่รับสูตร Add-in อ่านได้เฉพาะ "ค่า" ของเซลล์ และควรเตือนเมื่อพบสูตรในช่องคะแนน
7. **ฉีดสูตร:** ข้อความที่ขึ้นต้นด้วย `= + - @` ต้องถูกนำหน้าด้วย `'` ตอนเขียนลงชีต (เหมือน `safeText`) เพื่อไม่ให้ชื่อนักศึกษารันเป็นสูตร
8. **จำกัดอัตราและบันทึก:** เส้นทางนำเข้ามี rate limit (`IMPORT_LIMIT`) การเขียนชุดจาก Add-in ต้องมีเพดานและ log ที่ไม่บันทึกโทเคน (`app.ts` ปิดบัง header `authorization` อยู่แล้ว)
9. **เอกสารและแผนภาพ:** เมื่อสร้างจริง ต้องแก้ SRS (FR/NFR) แผนภาพ DFD ระดับ 2 กระบวนการ 4.0 และ `docs/diagrams/` ให้ตรงกับระบบ และรัน `npm run docs:links`

## 7. เทียบกับ Macro (VBA)

| หัวข้อ | Office Add-in | VBA Macro (`.xlsm`) |
| --- | --- | --- |
| ภาษา/ที่รัน | JavaScript, รันในแผงของ Office | VBA, รันในเครื่องผู้ใช้ |
| แพลตฟอร์ม | Windows, Mac, เว็บ (มือถือจำกัด) | Excel desktop เป็นหลัก; ไม่ทำงานบน Excel เว็บ |
| คำเตือนความปลอดภัย | ไม่มี "Enable Content" | มี และหลายองค์กรปิด Macro |
| ความเสี่ยงมัลแวร์ | ต่ำ (sandbox, ผ่าน manifest/ผู้ดูแล) | สูง (ช่องทางแพร่มัลแวร์ทั่วไป) |
| เก็บโทเคน | หน่วยความจำ/ที่เก็บของ Add-in | มักฝังในไฟล์ → เสี่ยงรั่วเมื่อส่งต่อไฟล์ |
| การแจกจ่าย | ผ่านผู้ดูแล Microsoft 365 หรือ sideload | แจกไฟล์เอง แก้ทุกครั้งที่โครงสร้างเปลี่ยน |
| ผูกกับระบบ | โค้ดอยู่ที่เซิร์ฟเวอร์ อัปเดตครั้งเดียวทุกคนได้ | โค้ดอยู่ในไฟล์ทุกชุด |
| ความเข้ากับ `excel.ts` | ไม่ต้องรับ `.xlsm` (ส่งผ่าน API) | ถ้าเซฟเป็น `.xlsm` จะถูกปฏิเสธ |
| ความยากในการทำ | สูงกว่า (โฮสต์ HTTPS, manifest, ล็อกอิน) | ต่ำกว่า ทำเร็ว |
| ทำงานตอนปิดไฟล์ | ไม่ได้ | ไม่ได้ |

สรุป: Macro ทำเร็วกว่าแต่ติดความปลอดภัยและการใช้งานข้ามแพลตฟอร์ม Add-in ลงทุนมากกว่าตอนเริ่ม แต่แก้ปัญหาเหล่านั้น

## 8. ลำดับงานที่เสนอ

1. ปรับ API: เพดานการเขียนชุด, ตรวจแก้ชนกันด้วย `updatedAt`, ขยาย CORS เป็นรายการ origin
2. หน้าเว็บ: ลดเวลา refetch ของหน้ากรอกคะแนน (ยังไม่ต้อง SSE)
3. Add-in ขั้นต่ำ: ล็อกอินผ่าน Dialog, ดึงตารางคะแนนลงชีต, ส่งการแก้ไขเป็นชุด, แสดงเซลล์ที่ถูกปฏิเสธ
4. ทดสอบ: Excel desktop + เว็บ, เน็ตหลุด, แก้ชนกัน, สิทธิ์ข้ามรายวิชา (404), เกรดถูกตรึง
5. แจกจ่าย: sideload สำหรับสาธิต; ขอผู้ดูแล Microsoft 365 ของสถาบันสำหรับใช้จริง
6. เมื่อเสถียร ค่อยพิจารณา SSE และปรับเอกสาร/แผนภาพ

## 9. สิ่งที่ยังไม่ทราบ (ต้องยืนยัน)

- สถาบันอนุญาตให้ติดตั้ง Add-in ผ่าน Admin Center หรือไม่ และใครเป็นผู้ดูแล
- เวอร์ชัน Excel ที่อาจารย์ใช้จริง (desktop/เว็บ, Windows/Mac)
- ต้องการ "real time" ระดับไหน (ทันทีที่แก้เซลล์ หรือซิงก์เมื่อกดปุ่ม/บันทึก)
- กติกาเมื่อชนกัน: ฝั่งไหนชนะ หรือให้อาจารย์เลือก
