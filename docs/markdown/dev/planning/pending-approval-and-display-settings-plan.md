## 1 · หน้ารอการอนุมัติ (ผู้ใช้นอกโดเมน @kmitl.ac.th)

### 1.1 การไหล

```
ดำเนินการต่อด้วย Google → เลือกบัญชี
  ├─ @kmitl.ac.th, ยังไม่มีบัญชี  → สร้างบัญชีผู้สอน → เข้าระบบ           (เดิม)
  ├─ อีเมลใน ADMIN_EMAILS        → ผู้ดูแลระบบ → เข้าระบบ               (FR-05a)
  ├─ บัญชีถูกระงับ               → "บัญชีนี้ถูกระงับการใช้งาน"             (เดิม)
  └─ โดเมนอื่น                    → สร้างบัญชี PENDING → หน้ารอการอนุมัติ   (ใหม่)
                                   ล็อกอินซ้ำก่อนได้อนุมัติ → หน้าเดิม
```

ลงทะเบียนด้วยอีเมลและรหัสผ่านยังรับเฉพาะอีเมลของคณะ (FR-07) ไม่เปลี่ยน เพราะทางนี้พิสูจน์ตัวตนด้วย Google ไม่ได้

### 1.2 หน้าจอ (view `pending` ในการ์ดเข้าสู่ระบบเดิม)

```
┌──────────────────────────────────────────┐
│ </> CMAS                                 │
│ รอผู้ดูแลระบบอนุมัติ                       │
│ อีเมลนี้ไม่ใช่อีเมลของคณะ (@kmitl.ac.th)   │
│ จึงต้องได้รับอนุมัติก่อนเข้าใช้งาน           │
│                                          │
│ ┌──────────────────────────────────────┐ │
│ │ G  somchai.home@gmail.com  [รออนุมัติ] │ │
│ └──────────────────────────────────────┘ │
│ ได้รับอนุมัติแล้ว กลับมากด                  │
│ "ดำเนินการต่อด้วย Google" อีกครั้ง          │
│                                          │
│ [        ใช้บัญชีอื่น (บัญชีของคณะ)       ] │
│           กลับไปหน้าเข้าสู่ระบบ             │
└──────────────────────────────────────────┘
```

| ส่วน | การตัดสินใจ | เหตุผล |
|---|---|---|
| หัวข้อ | "รอผู้ดูแลระบบอนุมัติ" | ตอบคำถามแรกของผู้ใช้: ตอนนี้เกิดอะไรขึ้น |
| คำอธิบาย | บรรทัดเดียว บอกเหตุผล (โดเมน) | ผู้ใช้รู้ว่าทำไมและแก้เองได้ด้วยบัญชีคณะ |
| กล่องบัญชี | โลโก้ Google · อีเมล · chip `รออนุมัติ` (โทน warn) | ยืนยันว่าเลือกบัญชีถูกตัว ใช้ chip เดียวกับหน้าจัดการผู้ใช้ |
| ขั้นต่อไป | "ได้รับอนุมัติแล้ว กลับมากด…อีกครั้ง" | ระบบไม่มีบริการส่งอีเมล จึง**ไม่สัญญาว่าจะแจ้งเตือน** |
| ปุ่มหลัก | "ใช้บัญชีอื่น (บัญชีของคณะ)" → หน้าเลือกบัญชี Google | อาจารย์ส่วนใหญ่มีบัญชีคณะ ทางนี้เร็วกว่ารออนุมัติ |
| ลิงก์ | "กลับไปหน้าเข้าสู่ระบบ" | — |
| **ไม่ใส่** | ปุ่ม "ตรวจสถานะ" · ตัวนับเวลา · ช่องเขียนข้อความถึงผู้ดูแล | ล็อกอินซ้ำทำหน้าที่ตรวจสถานะอยู่แล้ว · ช่องข้อความต้องมีตารางใหม่ |

**ถ้อยคำต้องใช้ได้ทั้งครั้งแรกและครั้งต่อไป** เพราะล็อกอินซ้ำก่อนได้อนุมัติได้หน้าเดิม จึงไม่เขียนว่า "สร้างบัญชีแล้ว"

**ความปลอดภัย:** บอกสถานะรออนุมัติได้ เพราะ Google พิสูจน์แล้วว่าผู้ใช้เป็นเจ้าของอีเมลนั้น (เหตุผลเดียวกับใน `auth.service.ts`) ส่วนบัญชีที่ถูกระงับยังได้ข้อความเดิม

**ไม่ทำเป็น route ใหม่:** ไม่มี token ตอนอยู่หน้านี้ ถ้าเป็น URL แล้วกดรีเฟรช หน้าจะไม่รู้ว่าเป็นบัญชีไหน · ต้นแบบใช้ `AuthScreen.view = 'pending'` · แอปจริงใช้ state ใน `Login.page.tsx` แทน `toast.info`

### 1.3 ฝั่งผู้ดูแลระบบ (ต้องมี มิฉะนั้นไม่มีใครเห็นคำขอ)

| ส่วน | การตัดสินใจ |
|---|---|
| ตัวเลขแจ้งเตือน | ตัวเลขจำนวนรออนุมัติบนเมนู "จัดการผู้ใช้งาน" ในแถบซ้าย (เห็นจากทุกหน้า) · **แสดงที่นี่ที่เดียว** |
| กลุ่มในหน้าจัดการผู้ใช้ | เพิ่มกลุ่ม "รออนุมัติ" เป็นกลุ่มแรก แสดงเฉพาะเมื่อมีอย่างน้อย 1 บัญชี · ไม่ใส่ตัวเลขซ้ำในชื่อกลุ่ม |
| แถว | ชื่อ · อีเมล · chip `รออนุมัติ` · ปุ่ม `อนุมัติ` (primary) |
| ปฏิเสธ | **ไม่เพิ่มปุ่มใหม่** ใช้ "ระงับการใช้งาน" เดิม ซึ่งทำให้เข้าไม่ได้อยู่แล้ว · API ไม่มี endpoint ปฏิเสธ |
| หลังอนุมัติ | toast "อนุมัติ {ชื่อ} แล้ว" · แถวย้ายออกจากกลุ่ม · ตัวเลขบนเมนูลด |

### 1.4 ข้อมูลในต้นแบบ

- เพิ่ม `status:'ACTIVE'` ให้ผู้ใช้ตัวอย่างทุกคน และเพิ่มบัญชีตัวอย่าง `PENDING` 1 บัญชี (เช่น `somchai.home@gmail.com` ที่มีในหน้าเลือกบัญชีอยู่แล้ว)
- `status` มีใน `schema.prisma` (migration 0007) และ `index-q.sql` อยู่แล้ว **ไม่ต้องเปลี่ยนแบบจำลองข้อมูล**
- สิทธิ์: ใช้ `user.manage` เดิมใน `PERM` **ไม่ต้องเพิ่ม capability**
- **ต้องตัดสินใจก่อน:** เพิ่ม use case **1.7 อนุมัติบัญชีที่รออนุมัติ** ใน `USE_CASES` หรือไม่ · ถ้าเพิ่ม สคริปต์ UML ใน `scripts/` จะสร้างผังใหม่ และต้องรัน `check-diagrams.py`

## 2 · การตั้งค่าการแสดงผล

### 2.1 รูปแบบ: ขยายแผงเดิม ไม่สร้างหน้าใหม่

แนะนำให้**เปลี่ยนแผง "มุมมองตาราง" เป็น "การแสดงผล"** เปิดจากเมนูบัญชีที่เดิม แทนการสร้างหน้า `/settings`

- มีแค่ 3 ตัวเลือก ใช้เวลาตั้งครั้งเดียว ทั้งหน้าจะว่างเปล่าเกินไป และเพิ่มเมนูในแถบซ้ายโดยไม่จำเป็น
- แผงเดิมเห็นผลทันทีขณะเลือก (`applyLayout()` + `render()`) ผู้ใช้ไม่ต้องกดบันทึก
- ถ้าภายหลังมีตัวเลือกเกิน 5–6 ตัว ค่อยย้ายเนื้อหาเดียวกันไปเป็นหน้า `/settings/display`

```
┌ การแสดงผล ─────────────────────────────┐
│ ขนาดตัวอักษร                              │
│  ● ปกติ        ค่าตั้งต้น                    │
│  ○ ใหญ่        อ่านง่ายขึ้น                  │
│  ○ ใหญ่มาก     สำหรับจอใหญ่หรือฉายขึ้นจอ      │
│ ───────────────────────────────────────── │
│ ความหนาแน่นของแถว       (เดิม 3 ตัวเลือก)   │
│ ───────────────────────────────────────── │
│ ข้อความยาวในตาราง        (เดิม 2 ตัวเลือก)   │
│ ───────────────────────────────────────── │
│                       คืนค่าเริ่มต้น         │
└──────────────────────────────────────────┘
```

| ส่วน | การตัดสินใจ | เหตุผล |
|---|---|---|
| ชื่อเมนู | "มุมมองตาราง" → "การแสดงผล" | ขนาดตัวอักษรมีผลทั้งระบบ ไม่ใช่แค่ตาราง |
| ขนาดตัวอักษร | 3 ระดับ: ปกติ 100% · ใหญ่ 112.5% · ใหญ่มาก 125% | **ไม่มีระดับเล็กกว่าปกติ:** ต้นแบบใช้ตัวอักษร 12–12.5px อยู่ 73 จุด (และ 11px 2 จุด) ถ้าย่อ 90% จะเหลือราว 10–11px อ่านยาก · ต้องการเห็นข้อมูลมากขึ้นใช้ความหนาแน่น "แน่น" แทน |
| ลำดับกลุ่ม | ขนาดตัวอักษรก่อน | มีผลมากที่สุดและเป็นเหตุผลหลักที่คนเปิดแผงนี้ |
| คืนค่าเริ่มต้น | ลิงก์เดียวท้ายแผง | คืนทั้ง 3 ค่า และความกว้างแถบรายวิชา |
| ความกว้างแถบรายวิชา | ไม่ใส่ในแผง (ยังลากที่ขอบได้เหมือนเดิม) | ลากเห็นผลชัดกว่าตัวเลข |
| **ไม่ใส่** | ธีมมืด · สี · ฟอนต์อื่น · ภาษา | ไม่มีใครขอ และเพิ่มงานตรวจสีทุกหน้า |

### 2.2 การเก็บค่า

- เก็บในเบราว์เซอร์ (`localStorage` คีย์ `cmas:layout` เดิม) เพิ่มฟิลด์ `scale` · **ไม่ต้องมีตารางหรือ API ใหม่** เพราะเป็นความชอบส่วนตัวต่อเครื่อง
- บนมือถือ ความหนาแน่นตั้งต้นยังเป็น "แน่น" ตามเดิม ส่วนขนาดตัวอักษรตั้งต้น "ปกติ" ทุกจอ

### 2.3 วิธีทำขนาดตัวอักษร

| ที่ | วิธี | เหตุผล |
|---|---|---|
| ต้นแบบ | `html[data-scale]` → CSS `zoom: 1 / 1.125 / 1.25` | ต้นแบบเขียนขนาดตัวอักษรเป็น px ตายตัว **396 จุด** (`text-[14px]` ฯลฯ) ปรับฐาน rem ไม่ได้ผล |
| แอปจริง | `html { font-size: 100% / 112.5% / 125% }` | Tailwind v4 ใช้หน่วย rem อยู่แล้ว เปลี่ยนค่าเดียวมีผลทั้งแอป · **ห้ามใช้ px ตายตัว** ในหน้าใหม่ |

**ความเสี่ยงที่ต้องทดสอบในต้นแบบ:** `zoom` ทำให้ตำแหน่งจาก `getBoundingClientRect()` เป็นค่าที่ขยายแล้ว แผงที่คำนวณตำแหน่งเอง (`layoutPop`, `acctMenu`, เมนูของช่องคะแนน) อาจเลื่อนผิดที่ ต้องตรวจทั้ง 3 ระดับ

## 4 · ตรวจรับ

- ล็อกอินด้วยบัญชีนอกโดเมนในต้นแบบ ได้หน้ารอการอนุมัติ · ล็อกอินซ้ำได้หน้าเดิม ไม่สร้างบัญชีซ้ำ
- ผู้ดูแลเห็นตัวเลขบนเมนู กดอนุมัติแล้วตัวเลขลด และบัญชีนั้นล็อกอินได้
- ระงับบัญชีที่รออนุมัติแล้ว บัญชีนั้นได้ข้อความ "ถูกระงับ" ไม่ใช่ "รออนุมัติ"
- เปลี่ยนขนาดตัวอักษรเห็นผลทันที รีเฟรชแล้วค่ายังอยู่ · แผงและเมนูทุกตัวอยู่ถูกที่ทั้ง 3 ระดับ · ที่ "ใหญ่มาก" บนจอ 1366 px ไม่มีแถบเลื่อนแนวนอนในหน้าที่ไม่ใช่ตาราง
- "คืนค่าเริ่มต้น" คืนทั้ง 3 ค่าและความกว้างแถบรายวิชา
