## 1. บทนำ

### 1.1 วัตถุประสงค์ของเอกสาร

กำหนดความต้องการของ CLO System ให้ครบถ้วนพอที่จะ implement, ทดสอบ และตรวจรับได้
โดยไม่ต้องย้อนถามผู้ออกแบบ เอกสารนี้เป็น **contract** ระหว่าง Figma (UI) กับ
`schema.prisma` (data) — เมื่อสองฝั่งขัดกัน ให้ยึดเอกสารนี้ และแก้ฝั่งที่ผิดตาม §9

### 1.2 ขอบเขต (Scope)

**อยู่ในขอบเขต**
- บันทึกและติดตาม CLO ระดับ**รายวิชา** ตามหลักสูตร ค.อ.บ. เทคโนโลยีคอมพิวเตอร์ (ปรับปรุง พ.ศ. 2567)
- กำหนดกิจกรรมประเมิน (Activity) และผูกกับ CLO พร้อมน้ำหนัก
- นำเข้า/บันทึกคะแนนราย**กิจกรรม** และคำนวณการบรรลุ CLO
- Dashboard สรุปผลระดับวิชา และรายงานรายบุคคล
- **การตัดเกรดภายในรายวิชา แบบอิงเกณฑ์และอิงกลุ่ม** *(เพิ่ม 2026-08-23 — ดู CR-08…CR-11)*
- **การติดตามผู้เรียนที่ต้องช่วย** — ถอนรายวิชา · ปิดรับคะแนน · ยกเว้น · ประวัติการแก้คะแนน · แผนพัฒนาผู้เรียนรายบุคคล *(เพิ่ม 2026-11-13 — CR-05.1, FR-110…FR-119)*

**นอกขอบเขต (Out of Scope — v1)**
- **การจัดการหลักสูตร (Curriculum) และ PLO / มคอ.2 mapping ระดับหลักสูตร** — ตัดออกทั้งหมด
  ตามการตัดสินใจ 2026-08-04 (งาน 2.7) สูงสุดของลำดับชั้นข้อมูลคือ **Course**
- **การรองรับหลายสถาบัน (multi-institution / multi-tenant)** — ระบบเป็น **single-tenant**
  ใช้ภายในคณะเดียว ไม่มีตาราง `Institution` / `Membership`
- ระบบลงทะเบียนเรียน และการเชื่อมต่อ REG ของสถาบัน — ระบบ**ไม่ส่งเกรดเข้าระบบทะเบียน**
  เกรดที่คำนวณได้เป็นเครื่องมือช่วยตัดสินใจของผู้สอน ต้องกรอกเข้า REG เองตามขั้นตอนเดิม
- **การตัดเกรดข้ามหมู่เรียน** (รวมหลาย section ของรหัสวิชาเดียวกันเป็นกลุ่มเดียว) — ดู CR-10
- Mobile native app, การใช้งาน offline
- Single Sign-On แบบองค์กร (SAML) และผู้ให้บริการอื่นนอกจาก Google — การลงทะเบียนเองด้วยอีเมลหรือ Google **อยู่ในขอบเขตแล้ว** (FR-07, FR-08 · ปิด OI-06)

## 3. กฎการคำนวณ (Calculation Rules)

> ส่วนนี้คือหัวใจของระบบ ทุกตัวเลขบน Dashboard ต้องมาจากสูตรเหล่านี้เท่านั้น
> ห้าม hard-code และห้ามคำนวณซ้ำคนละที่ — ต้องอยู่ใน service เดียว (`services/attainment.service.ts`)

### CR-01 — ความหมายของน้ำหนัก

| Field | ความหมาย | Invariant |
|---|---|---|
| `Activity.weight` | สัดส่วนของกิจกรรมนั้นต่อคะแนนรวมรายวิชา (%) | ผลรวมทุก Activity ในวิชา = **100** |
| `AssessmentCriteria.weight` | สัดส่วนของกิจกรรมนั้นที่ใช้วัด**จุดประสงค์**ข้อนั้น (%) | ผลรวมต่อ **1 Activity** = **100** |
| `BehavioralObjective.weight` | สัดส่วนของจุดประสงค์ข้อนั้นต่อ CLO (%) — nullable จนกว่าจะกรอก | ผลรวมต่อ **1 CLO** = **100** (ไม่ครบ → ล็อกผลการประเมิน) |
| `CLO.weight` | สัดส่วนของ CLO ต่อรายวิชา (%) ที่ผู้สอนกรอกเอง — nullable | ผลรวมทุก CLO ในวิชา ควร = **100** · ไม่ตรงค่าคำนวณ (CR-02) → **เตือน ไม่บล็อก** |

### CR-02 — น้ำหนักของ CLO ที่คำนวณได้ (ใช้ตรวจความสอดคล้องกับค่าที่กรอก)

```
weight(CLO c) = Σ over activities a  [ Activity.weight(a) × Criteria.weight(a,c) / 100 ]
Criteria.weight(a,c) = Σ over objectives o ของ c  [ AssessmentCriteria.weight(a,o) ]
```
ผลรวมของทุก CLO ในวิชาเท่ากับ 100 โดยอัตโนมัติเมื่อ CR-01 เป็นจริงครบทุกข้อ · **ค่านี้ไม่ใช่ค่าที่เก็บ** — `CLO.weight` เป็นค่าที่ผู้สอนกรอก (E2) ระบบเทียบสองค่าและเตือนเมื่อต่างกัน ≥ 0.5 จุด แต่ไม่เขียนทับและไม่ล็อกการทำงาน

### CR-03 — คะแนนจุดประสงค์และคะแนน CLO ของนักศึกษา 1 คน (%)

> **แก้ไข 2026-08-23 — ปิด OI-10** สูตรถ่วง `Activity.weight` (สอดคล้องกับหลัก OBE ที่ว่าข้อสอบปลายภาคต้องมีน้ำหนักมากกว่าควิซ) ·
> ทดสอบจริง: A1 (น้ำหนักวิชา 30, ได้ 100%) + A2 (น้ำหนักวิชา 70, ได้ 0%) → สูตรไม่ถ่วง = 50.00% · สูตรถ่วง = **30.00%**
>
> **แก้ไข 2026-09-17 (migration `0006` · E1) — คำนวณสองชั้น** เพราะกิจกรรมผูกกับจุดประสงค์ ไม่ผูกกับ CLO

**ชั้นที่ 1 — คะแนนจุดประสงค์ `o`**
```
                 Σ over a  [ score(s,a) / maxScore(a) × Activity.weight(a) × Criteria.weight(a,o) ]
objScore(s,o) = ─────────────────────────────────────────────────────────────────────────────────── × 100
                          Σ over a  [ Activity.weight(a) × Criteria.weight(a,o) ]
```
- นับเฉพาะ Activity ที่ผูกกับจุดประสงค์ `o` และ**มีแถวคะแนนของ `s` แล้ว** · ไม่มีเลย → `objScore = null`

**ชั้นที่ 2 — คะแนน CLO `c`**
```
                Σ over o ของ c, objScore(s,o) ≠ null  [ objScore(s,o) × BehavioralObjective.weight(o) ]
cloScore(s,c) = ─────────────────────────────────────────────────────────────────────────────────────
                Σ over o ของ c, objScore(s,o) ≠ null  [ BehavioralObjective.weight(o) ]
```
- ตัวหารนับเฉพาะจุดประสงค์ที่มีคะแนนแล้ว · ทุกจุดประสงค์เป็น `null` → `cloScore = null` (แสดง `—` ไม่ใช่ 0) — ดู CR-03.1
- **ผ่านเมื่อ `cloScore(s,c) ≥ Course.cloPassMark`** (ค่าเดียวทั้งวิชา ค่าเริ่มต้น 60 · E1)
- `Activity.passMark` (% ของ `maxScore`) แสดงผลรายกิจกรรม **ไม่ใช่ส่วนหนึ่งของคำตัดสิน CLO**

### CR-03.1 — สถานะเมื่อ `cloScore = NULL` (ปิด OI-12)

`NULL < cloPassMark` ใน SQL ให้ผลลัพธ์ `unknown` นักศึกษาที่ยังไม่มีคะแนนจึงหายไปจาก
**ทั้ง**รายการ at-risk และรายการผ่าน ทำให้ FR-83 รายงาน at-risk ต่ำกว่าความจริงตอนต้นเทอม
ซึ่งเป็นตัวเลขที่อาจารย์ใช้ตัดสินใจแทรกแซงนักศึกษา

**มติ:** `NULL` **ไม่ใช่** at-risk แต่เป็น**สถานะที่สาม** ต้องนับและแสดงแยกเสมอ

| สถานะ | เงื่อนไข |
|---|---|
| ผ่าน | `cloScore ≥ Course.cloPassMark` |
| at-risk | `cloScore < Course.cloPassMark` |
| **ยังประเมินไม่ครบ** | `cloScore IS NULL` |

ผลรวมทั้งสามสถานะ = จำนวนนักศึกษาที่ไม่ถอนรายวิชาทั้งหมดเสมอ ถ้าไม่เท่ากันคือบั๊ก

### CR-04 — Attainment ระดับวิชา

```
attainment(c) = (จำนวนนักศึกษาที่ผ่าน c / จำนวนนักศึกษาที่มีคะแนนครบพอจะคำนวณ c) × 100
CLO c "บรรลุ"  ⟺  attainment(c) ≥ target(c)

target(c) = CLO.classTarget  ถ้าไม่ใช่ NULL
          = Course.classTarget  ถ้าเป็น NULL
```
- ตัวหารนับเฉพาะนักศึกษาที่ `cloScore(s,c) IS NOT NULL` (CR-03.1)
- ~~`CLO.classTarget` เป็นค่า override ราย CLO~~ — **ยกเลิก 2026-10-02 (FR-101)** · เป้าหมายของชั้นคือทุกคนผ่าน:
  `Course.classTarget = 100` เสมอ และ `CLO.classTarget` เป็น `NULL` ทุกข้อ (คอลัมน์ยังอยู่ใน schema ไม่มีหน้าจอให้ตั้ง)
- เพราะเป้าคือ 100% คำตัดสิน "บรรลุ / ไม่บรรลุ" จึงเกือบเป็น "ไม่บรรลุ" เสมอ — **ตัวเลขที่หน้าจอต้องเน้นคือจำนวนคนที่ไม่ผ่าน CLO ข้อนั้น
  ("ต้องช่วย N คน") และรายชื่อ** ไม่ใช่คำตัดสินเทียบเป้า · ดู CR-05.1

### CR-05 — คะแนนรวมรายวิชาและสถานะนักศึกษา

```
totalScore(s) = Σ over a [ score(s,a) / maxScore(a) × Activity.weight(a) ]     // 0–100
ผ่านรายวิชา  ⟺  totalScore(s) ≥ Pass Criteria
at-risk      ⟺  มี CLO อย่างน้อย 1 ตัวที่ cloScore(s,c) < Course.cloPassMark
กลุ่มเสี่ยง    ⟺  at-risk  ∨  ไม่ผ่านรายวิชา                // รายชื่อที่ต้องติดตาม (CR-05.1) · โค้ดยังมีระดับ "ขาดส่ง" เพิ่ม — OI-18
```
- **กิจกรรมที่ `Activity.weight = 0` ยังไม่เข้าการคำนวณ** *(เพิ่ม 2026-10-01 · ต้นแบบ `index-q.html` Q11)* — ทุกสูตรใน CR-03 และ CR-05
  คูณด้วย `Activity.weight` คะแนนของกิจกรรมนั้นจึงเปลี่ยนผลไม่ได้ และ**การที่มันยังไม่มีแถวคะแนนต้องไม่ทำให้นักศึกษา
  "ยังประเมินไม่ครบ"** · "คะแนนครบ" (ทั้งระดับรายวิชาและระดับ CLO) จึงนับเฉพาะกิจกรรมที่ `weight > 0` ·
  กิจกรรมที่เพิ่งเพิ่มในโหมดกรอกน้ำหนักทีละกิจกรรมเริ่มที่น้ำหนัก 0 จึงไม่ทำให้เกรดของทั้งชั้นหายจนกว่าผู้สอนจะให้น้ำหนัก
- ผ่านรายวิชาตัดสินได้เมื่อนักศึกษามีคะแนนครบทุกกิจกรรมที่ `weight > 0` เท่านั้น · ก่อนหน้านั้นแสดง "ยังประเมินไม่ครบ" ไม่ใช่ "ไม่ผ่าน" (FR-62)

### CR-05.1 — ถอนรายวิชา · ปิดรับคะแนน · ยกเว้น · ประวัติการแก้คะแนน (เสนอ 2026-10-02 · อยู่ใน schema ตั้งแต่ migration `0008`)

> ทั้งสี่ข้อมีไว้เพื่อให้คำถาม **"ใครต้องได้รับความช่วยเหลือ ใน CLO ไหน เพราะอะไร"** ตอบได้ถูก · เป้าหมายของชั้นคือทุกคนผ่าน (100%)
> คำตัดสิน "บรรลุ / ไม่บรรลุ" ราย CLO จึงเกือบเป็น "ไม่บรรลุ" เสมอและไม่ใช่ตัวเลขหลักของหน้าจอ — ตัวเลขหลักคือ**จำนวนคนที่ยังต้องช่วย**
> **สถานะ (2026-11-13):** อยู่ใน `schema.prisma` แล้ว (`Student.status` · `Activity.closedAt` · `Score.status` / `excuseReason` · `ScoreChange`) · มี API ถอน/คืนสถานะ (`POST /students/:id/withdraw|restore`) และอ่านประวัติ (`GET /courses/:id/score-changes`) · ข้อกำหนดรายข้ออยู่ใน FR-110…FR-113

| กติกา | ความหมาย | ผลต่อสูตร |
|---|---|---|
| **ถอนรายวิชา** (`Student.status = WITHDRAWN`) | นักศึกษาที่ถอนไม่ถูกนับในผลใด ๆ · คะแนนเดิมยังเก็บไว้ คืนสถานะได้ · เกรดแสดง `W` | ออกจากตัวหารของ CR-04, mean/SD ของ CR-10, ความครบของคะแนน และรายชื่อที่ต้องติดตาม |
| ~~**ปิดรับคะแนน** (`Activity.closedAt`)~~ | **ยกเลิกในต้นแบบ** — ไม่มีการปิดรับคะแนนและไม่มีสถานะ "ขาดส่ง" ช่องว่างคือ "ยังไม่ประเมิน" เสมอ (ผู้สอนไม่ต้องกรอก 0 ให้) | คอลัมน์ `closedAt` ใน `index-q.sql` ยังไม่ถูกถอด |

| **ยกเว้น** (`Score.status = EXCUSED`) | ไม่นับกิจกรรมนี้สำหรับนักศึกษาคนนี้ (มีเหตุอันควร) · ระบุเหตุผลได้ (ไม่บังคับ `Score.excuseReason`) และเหตุผลถูกเก็บลงประวัติ | กิจกรรมนั้นออกจากทั้งตัวตั้งและตัวหารของ CR-03 และ CR-05 สำหรับคนนั้น · ไม่ถือว่า "ขาด" จึงไม่ทำให้คะแนนไม่ครบ |

- รายชื่อที่ต้องติดตามเรียง: **ไม่ผ่านรายวิชา → ต่ำกว่าเกณฑ์ CLO → รอคะแนน** · ในระดับเดียวกันเรียงจากระยะห่างจากเกณฑ์ผ่านมากที่สุด
- ราย CLO แสดง "ต้องช่วย N คน" พร้อมรายชื่อ แยก "ห่างจากเกณฑ์มาก" (เกิน 10 คะแนน) กับ "ใกล้ผ่าน" และจุดประสงค์ที่อ่อนที่สุดของแต่ละคน
- เมื่อเกินครึ่งของชั้นไม่ผ่าน CLO ข้อเดียวกัน ให้แสดงว่าเป็นสัญญาณของการสอนหรือการวัดผล ไม่ใช่ของนักศึกษารายคน
- นักศึกษาที่มีคะแนนครบทุกกิจกรรมที่นับ ออกเกรดได้

### CR-05.2 — สถานะ ณ ตอนนี้ (`passNow`) นับช่องว่างเป็น 0 (เล่ม §2.2.6 · §3.3.2.1 ข้อ 6 · §3.5.2.2 · ต้นแบบ 2026-11-14)

> ขยายแถว "สถานะ ณ ตอนนี้" ของ CR-05.1 · การจัดการค่าว่างมี **2 ขั้น** เพื่อไม่ให้ผู้ที่ไม่มีคะแนนหลุดจากการเฝ้าระวัง:
>
> 1. **ระดับฐานข้อมูล** — ช่องที่ยังไม่มีคะแนนเก็บเป็น `NULL` ไม่เขียนทับด้วย 0 (FR-62 · CR-03.1)
> 2. **ระดับการแสดงผล** — นักศึกษาที่คะแนนยังไม่ครบ ให้นับช่องว่างของกิจกรรมที่นับ (`weight > 0` · ไม่ EXCUSED) เป็น 0
>    **ชั่วคราวขณะคำนวณ** แล้วแสดงป้าย **"ผ่านแล้ว"** (เขียว) หรือ **"ยังไม่ผ่าน"** (แดง) พร้อม "รอคะแนน N กิจกรรม"

```
ratio₀(s,a) = score(s,a)/maxScore(a)   ถ้ามีคะแนน
            = 0                         ถ้า NULL
            = ไม่นับ                    ถ้า EXCUSED หรือ weight(a) = 0
passNow(s)  = totalScore₀(s) ≥ passCriteria   (ราย CLO: cloScore₀(s,c) ≥ cloPassMark)
            = ไม่ระบุ   ถ้าไม่มีคะแนนจริงสักช่อง หรือรายวิชายังตั้งค่าไม่ครบ (FR-84)
```

- **ห้าม**ใช้ค่า ₀ ในตัวเลขของ CR-03 / CR-04 / CR-05 / CR-09 / CR-10 และไม่เปลี่ยนตัวนับ at-risk / "ไม่ผ่านรายวิชา" — ค่าเหล่านั้นยังยึด CR-03.1 (NULL ≠ 0)
- **ต่างจากถ้อยคำในเล่ม:** เล่ม §3.3.2.1 ข้อ 6 จำกัดไว้ที่ "กิจกรรมที่วัดผลหรือปิดรับคะแนนแล้ว" แต่ต้นแบบ**ตัดการปิดรับคะแนนออก** (develop 444242a)
  จึงนับทุกช่องว่าง — ต้องแก้เล่มให้ตรง (OI-18)
- **สถานะ:** ต้นแบบ `docs/index-q/index-q.html` ✅ · แอป ⬜ — `lib/attainment.ts` ยังไม่มี `passNow` และยังมี `Activity.closedAt` →
  ระดับ `OVERDUE` ("ขาดส่ง") ในรายชื่อที่ต้องติดตาม (OI-18)

### CR-08 — การตัดเกรด: หลักการแยกแกน

การตัดเกรดเพิ่มเข้ามา 2026-08-23 (แก้ §1.2) **สามแกนนี้ต้องไม่ปนกัน**

| แกน | ตอบคำถาม | ใช้อะไรตัดสิน | อิงกลุ่มมีผล |
|---|---|---|---|
| การบรรลุ CLO | CLO นี้บรรลุไหม | `Course.cloPassMark`, `target(c)` (CR-04) | **ไม่มี** |
| ผ่าน/ไม่ผ่านรายวิชา | นักศึกษาผ่านวิชาไหม | `Course.passCriteria` (CR-05) | **ไม่มี** |
| เกรด | ได้ A หรือ B+ | `Course.gradeMethod` + `GradeBand` | **มี** |

> **กฎบังคับ:** การบรรลุ CLO เป็น criterion-referenced **เสมอ** ตามนิยามของ OBE
> ต่อให้รายวิชานั้นตัดเกรดอิงกลุ่ม ห้ามให้ค่าสถิติของกลุ่ม (mean / SD / ลำดับที่)
> ไหลเข้าสูตร CR-03 หรือ CR-04 เด็ดขาด — ถ้าไหลเข้า ตัวเลข attainment จะอธิบายต่อ
> กรรมการหลักสูตรไม่ได้ ซึ่งเป็นผู้ใช้กลุ่มเดียวที่ระบบนี้มีอยู่เพื่อรองรับ

### CR-09 — ตัดเกรดอิงเกณฑ์ (Criterion-referenced)

```
grade(s) = GradeBand ที่ minValue สูงที่สุด ซึ่ง totalScore(s) ≥ GradeBand.minValue
```
- `totalScore(s)` มาจาก CR-05
- `GradeBand.minValue` อ่านเป็น**ร้อยละ** เสมอเมื่อ `Course.gradeMethod = CRITERION_REFERENCED`
  — ไม่มีคอลัมน์ `boundaryUnit` แล้ว หน่วยตามมาจากวิธีตัดโดยตรง
- ทุก scheme ต้องมี band ล่างสุด (`F` หรือ `U`) ที่ `minValue = 0` มิฉะนั้นจะมีนักศึกษาที่ตกร่องไม่ได้เกรด
  — ข้อนี้บังคับที่ระดับแอป ไม่มี trigger รองรับ
- ไม่มีคอลัมน์ `order` แล้ว ลำดับเกรดอ่านจาก `ORDER BY minValue DESC` ซึ่งมีคำตอบเดียวเสมอ
  เพราะ `UNIQUE (schemeId, minValue)` ห้ามสองเกรดใช้เส้นแบ่งเดียวกัน

### CR-10 — ตัดเกรดอิงกลุ่ม (Norm-referenced)

```
n    = จำนวนนักศึกษาในกลุ่ม (ดู "นิยามประชากร" ด้านล่าง)
mean = Σ totalScore(s) / n
SD   = √( Σ ( totalScore(s) − mean )² / n )        ← SD ประชากร หารด้วย n ไม่ใช่ n − 1
T(s) = 50 + 10 × ( totalScore(s) − mean ) / SD
grade(s) = GradeBand ที่ minValue สูงที่สุด ซึ่ง T(s) ≥ GradeBand.minValue
```

`mean` และ `SD` คำนวณ ณ เวลาที่กดตัดเกรด จากคะแนนรวมของนักศึกษาที่ประเมินครบ

**ชนิดของ SD และ T (ตัดสิน 2026-10-11)**

- **SD ประชากร (หารด้วย n)** — กลุ่มที่ใช้ตัดเกรดคือนักศึกษา**ทั้งหมด**ของหมู่เรียนนั้น ไม่ใช่ตัวอย่างที่สุ่มมา
  เพื่อประมาณค่าของกลุ่มที่ใหญ่กว่า จึงเป็นการบรรยายชุดข้อมูลที่มีอยู่ ไม่ใช่การอนุมาน (GraphPad, §1.4)
  ผลที่ตามมาคือ T ของกลุ่มมีค่าเฉลี่ย 50 และ SD 10 **พอดี** ตามนิยามของ T-score (Salkind 2008, §1.4)
  ถ้าหารด้วย n − 1 SD ของ T จะเป็น 10 × √((n − 1) / n) ซึ่งต่ำกว่า 10 เสมอ
- **ห้ามใช้ n − 1** — SD ที่ได้จะใหญ่ขึ้น √(n / (n − 1)) เท่า (n = 10 ต่างกันราว 5.4% · n = 30 ราว 1.7%)
  T ของทุกคนถูกดึงเข้าหา 50 นักศึกษาที่อยู่ใกล้เส้นแบ่งจึงได้เกรดต่างจากที่ต้นแบบแสดง
  ระวังค่าตั้งต้นของเครื่องมือ: `STDEV` / `STDEV.S` ของ Excel และ `STDDEV` / `STDDEV_SAMP` ของ PostgreSQL หารด้วย n − 1
  ตัวที่ตรงกับกติกานี้คือ `STDEV.P` และ `STDDEV_POP`
- **Linear T-score** — แปลงเชิงเส้นจากคะแนนดิบโดยตรง **ไม่ normalize** ผ่าน percentile rank
  T-score ต้นฉบับของ McCall (1922) เป็นแบบ normalized รูปการกระจายของ T ในระบบนี้จึงเหมือนคะแนนดิบ
  ถ้าคะแนนเบ้ T ก็เบ้ตาม · เลือกแบบนี้เพราะอาจารย์ตรวจทานด้วยเครื่องคิดเลขได้ และไม่ต้องใช้ตารางโค้งปกติ

`mean` / `SD` / `T(s)` / `z(s)` **ไม่ถูกเก็บลงฐานข้อมูล** ตั้งแต่ v2.2.0 — คำนวณในหน่วยความจำ
ตอนกดตัดเกรด แล้วเขียนเฉพาะ `StudentGrade.totalPercent` กับ `StudentGrade.grade` ลงไป

> **ข้อจำกัดที่ต้องรู้:** ผลลัพธ์ที่ให้ไปแล้ว**ไม่เปลี่ยน**เพราะเกรดถูกเก็บเป็นค่าจริง
> แต่ถ้าภายหลังมีคนถามว่า "ทำไมคนนี้ได้ B+" จะตอบจากฐานข้อมูลอย่างเดียวไม่ได้
> ต้องกดตัดใหม่ซึ่งได้ค่าคนละชุดถ้ามีคนถอนรายวิชาไปแล้ว
> ถ้าต้องการความสามารถนี้กลับมา ให้เพิ่ม **1 ตาราง** (`courseId`, `n`, `mean`, `sd`, `computedAt`)
> แล้วให้ `StudentGrade` ชี้มาที่ตารางนั้น — **ห้ามเอา `GradeScheme` กลับมาด้วย**

**นิยามประชากร (กลุ่ม)** — ข้อนี้ต้องชัด ไม่งั้นตัวเลขเปลี่ยนได้โดยไม่มีใครแก้คะแนน

- กลุ่ม = นักศึกษาใน **`Course` แถวเดียว = 1 หมู่เรียน** เท่านั้น
- **ไม่รองรับการรวมคะแนนข้ามหมู่เรียน** — `CLO` และ `Activity` ผูกกับ `courseId`
  กิจกรรม "สอบกลางภาค" ของหมู่ 01 กับหมู่ 02 จึงเป็นคนละแถวที่ไม่มีอะไรเชื่อมกัน
  การรองรับต้องเพิ่มลำดับชั้น `CourseOffering` เหนือ `Course` ซึ่ง**ขัดมติ 2.7** — ห้ามทำครึ่ง ๆ กลาง ๆ
- นับเฉพาะนักศึกษาที่มี `totalScore` (คะแนนครบทุกกิจกรรมที่ตรวจแล้ว)
- นักศึกษาที่ถอนรายวิชา **ไม่นับ** ใน mean / SD

**กรณีที่ต้องปฏิเสธ (บังคับที่ DB ใน migration 0004)**

| กรณี | เหตุผล | ผล |
|---|---|---|
| `SD = 0` | ทุกคนคะแนนเท่ากัน → หารด้วยศูนย์ | ปฏิเสธ · ให้ใช้ CR-09 แทน |
| `n < 2` | คำนวณ SD ไม่ได้ | ปฏิเสธ |
| `n < MIN_SAMPLE_SIZE` (ค่าคงที่ใน env) | อิงกลุ่มไม่มีความหมายทางสถิติ | **เตือน ไม่บล็อก** |

ทั้งสามกรณีบังคับที่ **service ตอนกดตัดเกรด** ไม่ใช่ที่ฐานข้อมูล เพราะไม่มีแถว `GradeRun`
ให้ผูก trigger ไว้อีกแล้ว — ตรวจก่อนเขียน `StudentGrade` แถวแรกเสมอ
| `gradeScale = PASS_FAIL` | S/U ตัดสินด้วย `passCriteria` เท่านั้น (CR-06) | ปฏิเสธ |

### CR-11 — การ freeze ผลการตัดเกรด

เกรดอิงกลุ่ม**คำนวณย้อนกลับจากคะแนนดิบไม่ได้** ถ้าไม่เก็บสถิติไว้ — นักศึกษาถอน 1 คน
ทำให้ mean/SD ขยับ และเกรดของ**ทุกคน**เปลี่ยนเงียบ ๆ ทั้งที่ไม่มีใครแตะคะแนนเลย

**สิ่งที่ยังรับประกันได้ (v2.2.0)**

- `StudentGrade.grade` และ `.totalPercent` เก็บเป็น**ค่าจริง** ไม่ได้คำนวณสดตอนอ่าน
  → นักศึกษาถอน 1 คน หรือแก้คะแนนดิบภายหลัง **ไม่ทำให้เกรดที่ให้ไปแล้วขยับ** แถวเดิมอยู่อย่างที่เขียนไว้
- การปรับเกรดด้วยมือต้องมี `overrideReason` เสมอ (CHECK ใน migration 0004)

**สิ่งที่รับประกันไม่ได้แล้ว**

- ย้อนพิสูจน์ที่มาของเกรด**อิงกลุ่ม**จากฐานข้อมูลอย่างเดียว — ไม่มี `n / mean / sd` เก็บไว้
- ไม่มีสถานะ ฉบับร่าง / ประกาศแล้ว และไม่มีการเก็บหลายรอบเพื่อเทียบกัน
  → หน้าจอเทียบอิงเกณฑ์กับอิงกลุ่มยังทำได้ แต่เป็นการ**คำนวณโชว์** ไม่ใช่ข้อมูลที่เก็บสองชุด

> ข้อนี้คือคำตอบของคำถามค้างใน [[dfd]] §10 ("แก้ได้ตลอดเวลาแม้หลังตัดเกรดแล้วหรือไม่?")
> **คำตอบ: ไม่ได้**

## 5. External Interface Requirements

### 5.1 User Interface

- ยึด [[design-system]] และ Design System Board ใน Figma — text styles (Display/H1–H4/Body/label/caption) และ color styles (Primary / Hover / Secondary / Background / Status)
- ทุกหน้าที่ดึงข้อมูลต้องออกแบบครบ 4 สถานะ: **loading / empty / error / success** (ปัจจุบัน Figma มีแค่ success — F11)
- การกระทำที่ทำลายข้อมูลต้องมี confirm dialog ที่ระบุผลกระทบเชิงตัวเลข
- ทุก action ต้องมี feedback (toast) ภายใน 200 ms
- ต้องเลือก IA ภาษาเดียว (ไทยหรืออังกฤษ) ให้ตรงกันทุกหน้า — ปัจจุบันมี 2 ชุดชนกัน (F10)

### 5.2 API

- REST, prefix `/api/v1`, response envelope และ error format ตาม [[dev]] §9–§10
- ทุก endpoint ที่ไม่ใช่ `/auth/google` · `/auth/email-link` · `/auth/email-link/verify` · `/auth/refresh` ต้องผ่าน auth middleware และ RBAC middleware
- ทุก request body ผ่าน Zod schema — ห้ามเชื่อ input ที่ยังไม่ผ่าน schema

### 5.3 File Interface (Excel)

| รายการ | ข้อกำหนด |
|---|---|
| รูปแบบ | `.xlsx` (SheetJS) — CSV เป็น SHOULD |
| ขนาดสูงสุด | 10 MB |
| Template คะแนน | คอลัมน์: `รหัสนักศึกษา`, `ชื่อ-นามสกุล`, แล้วต่อด้วย 1 คอลัมน์ต่อ 1 กิจกรรม (หัวคอลัมน์ = `<รหัสกิจกรรม> (เต็ม N)`) |
| Template รายชื่อ | คอลัมน์: `รหัสนักศึกษา`, `ชื่อ-นามสกุล` |
