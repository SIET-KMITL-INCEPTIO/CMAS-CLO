## 2. ผลสัมฤทธิ์สำคัญในสัปดาห์ที่ผ่านมา

1. **ได้ข้อสรุปขอบเขตของระบบที่ชัดเจน** — ตัดสินใจให้ระบบเป็นแบบสถาบันเดียว (single-tenant) แทนที่จะรองรับหลายสถาบัน ทำให้โครงสร้างฐานข้อมูลลดจาก 15 เหลือ **11 ตาราง** และหน้าจอลดจาก 15 เหลือ **13 หน้า** ปิดข้อขัดแย้งระหว่างวัตถุประสงค์โครงงานกับโครงสร้างฐานข้อมูลที่ค้างมาตั้งแต่ต้น
2. **ได้โครงสร้างฐานข้อมูลฉบับที่ใช้พัฒนาจริง** — `schema.prisma` 11 ตาราง พร้อมข้อบังคับความถูกต้องระดับฐานข้อมูล (CHECK constraint, trigger, partial unique index) และตรวจแล้วว่าสร้างฐานข้อมูลใหม่จากศูนย์พร้อมข้อมูลตัวอย่างได้จริง
3. **ได้แบบจำลองกระแสข้อมูลของระบบ** — DFD ระดับบริบท (3 external interactor) และระดับที่ 1 (10 process, 9 data store) พร้อมการกำหนดขอบเขตความเชื่อถือ (trust boundary)
4. **ได้สัญญา API ฉบับสมบูรณ์ก่อนเริ่มเขียนโค้ด** — รายการ 57 endpoint ครอบคลุมทุกโมดูล พร้อมรูปแบบ response มาตรฐาน รหัสสถานะ และกฎการออกแบบ 5 ข้อ ทำให้ฝั่งหน้าเว็บกับฝั่งเซิร์ฟเวอร์พัฒนาขนานกันได้
5. **ได้กลไกความปลอดภัยหลักที่ทำงานได้จริง** — การยืนยันตัวตนด้วย JWT ที่อ่านบทบาทจากฐานข้อมูลสดทุกครั้ง (การถอดสิทธิ์มีผลทันทีโดยไม่ต้องรอ token หมดอายุ) และการจำกัดขอบเขตข้อมูลระดับรายวิชาที่ตอบ 404 แทน 403 เพื่อไม่ให้ผู้ใช้ทราบว่ามีรายวิชานั้นอยู่จริง
6. **ได้สารบัญปริญญานิพนธ์ทั้งเล่ม** — บทที่ 1–5 พร้อมหัวข้อย่อยครบ 88 หัวข้อ และภาคผนวก ก–ญ ใช้เป็นกรอบเขียนเล่มและตรวจสอบว่าเอกสารใดยังขาด
7. **ระบุปัญหาที่บล็อกการทดสอบได้ชัดเจน 2 ข้อ** — OI-10 (สูตรน้ำหนัก) และ OI-12 (นิยามกลุ่มเสี่ยง) พร้อมหลักฐานเชิงตัวเลขว่าทั้งสองสูตรให้ผลต่างกัน 20 จุด เพื่อขอให้อาจารย์ที่ปรึกษาชี้ขาด

## 3. รายละเอียดในการปฏิบัติงาน

### 3.1 การตัดสินใจขอบเขตระบบและการปรับโครงสร้างฐานข้อมูล

โครงสร้างฐานข้อมูลเดิมออกแบบให้รองรับหลายสถาบัน โดยมีตาราง `Institution` เป็นรากของลำดับชั้น และมีตาราง `Membership` เก็บความสัมพันธ์ผู้ใช้–สถาบัน–บทบาท ทุก query ต้องมีเงื่อนไข `institutionId` กำกับ ซึ่งขัดกับวัตถุประสงค์ของโครงงานที่ระบุว่าเป็นระบบใช้ภายในสถาบันเดียว

หลังตัดสินใจเลือกแบบสถาบันเดียว โครงสร้างเปลี่ยนเป็น

| ประเด็น | ก่อน | หลัง |
|---|---|---|
| จำนวนตาราง | 15 | **11** |
| รากของลำดับชั้น | `Institution` | **`Course`** |
| ที่เก็บบทบาท | ตาราง `Membership` | ฟิลด์ `role` บนตาราง `User` |
| ด่านตรวจสิทธิ์ | 2 ชั้น (สถาบัน + รายวิชา) | **1 ชั้น (รายวิชา)** |
| จำนวนหน้าจอ | 15 | **13** |

ลำดับชั้นข้อมูลหลังปรับ: `Course` → `CLO` → `BehavioralObjective` และ `Course` → `Activity` → `AssessmentCriteria` โดย `AssessmentCriteria` เป็นตารางเชื่อม `Activity` กับ `CLO` พร้อมน้ำหนักต่อคู่ ซึ่งเป็นหัวใจของการคำนวณ

ข้อบังคับความถูกต้องที่บังคับใช้ที่ระดับฐานข้อมูล มิใช่เฉพาะระดับโปรแกรม

- `CHECK` — คะแนนต้องอยู่ในช่วง 0 ถึงคะแนนเต็มของกิจกรรม, คะแนนเต็มต้องมากกว่า 0, น้ำหนักต้องไม่ติดลบ
- `TRIGGER` — กิจกรรมและ CLO ที่ถูกผูกเข้าด้วยกันต้องอยู่ในรายวิชาเดียวกัน
- `Partial unique index` — หนึ่งรายวิชามีอาจารย์ผู้รับผิดชอบหลัก (LEAD) ได้ไม่เกิน 1 คน

**ข้อค้นพบเชิงออกแบบที่สำคัญ:** ตาราง `Score` กำหนดให้ฟิลด์คะแนนห้ามเป็นค่าว่าง และใช้ **การไม่มีแถวข้อมูล** แทนความหมาย "ยังไม่ประเมิน" แทนการเก็บค่า 0 หรือค่าว่าง เพราะหากเก็บ 0 ระบบจะไม่สามารถแยกได้ว่านักศึกษา "ทำแล้วได้ 0 คะแนน" หรือ "ยังไม่ได้ทำ" ซึ่งจะทำให้การคำนวณกลุ่มเสี่ยงผิดพลาดทั้งหมด ประเด็นนี้ตรงกับ FR-62 และเป็นเงื่อนไขของการพิสูจน์สมมุติฐาน H2

### 3.2 การออกแบบกระแสข้อมูลของระบบ (DFD)

**ระดับบริบท** — ผู้กระทำภายนอก 3 ราย คือ ผู้ดูแลระบบ, อาจารย์ผู้สอน และไฟล์ Excel ที่นำเข้า/ส่งออก

**ระดับที่ 1** — แบ่งเป็น 10 กระบวนการ ได้แก่ จัดการผู้ใช้และการเข้าสู่ระบบ · จัดการรายวิชา · มอบหมายอาจารย์ · จัดการ CLO · จัดการจุดประสงค์เชิงพฤติกรรม · จัดการกิจกรรมและเมทริกซ์เกณฑ์การประเมิน · จัดการรายชื่อนักศึกษา · นำเข้าคะแนนจากไฟล์ · บันทึกคะแนนรายกิจกรรม · คำนวณและแสดงผลการบรรลุ CLO และมีที่เก็บข้อมูล 9 แห่งตามตารางหลัก

กระบวนการที่ต้องแตกเป็นระดับที่ 2 คือ **P8 (นำเข้าคะแนน)** และ **P10 (คำนวณ attainment)** เพราะเป็นสองจุดที่มีตรรกะซับซ้อนที่สุดและเป็นจุดที่สมมุติฐาน H1 และ H3 ใช้วัด

### 3.3 การออกแบบสัญญา API

หลักการออกแบบที่กำหนดไว้ 5 ข้อ โดยข้อที่มีผลต่อโครงสร้างมากที่สุดคือ

- **การจัดวางเส้นทาง** — ทรัพยากรที่เป็นรายการนำไปซ้อนใต้รายวิชา เช่น `GET /courses/:courseId/clos` ส่วนทรัพยากรรายชิ้นอยู่ที่ระดับบนสุด เช่น `PATCH /clos/:cloId` และต้องค้นหา `courseId` จากฝั่งเซิร์ฟเวอร์ก่อนตรวจสิทธิ์เสมอ
- **การบันทึกข้อมูลเป็นชุด** — เมทริกซ์เกณฑ์การประเมินและตารางคะแนนใช้วิธีแทนที่ทั้งชุดใน transaction เดียว มิใช่บันทึกทีละช่อง เพื่อป้องกันสภาวะที่ข้อมูลถูกเขียนไปเพียงบางส่วน
- **การนำเข้าไฟล์แบบสองขั้น** — ขั้นตรวจสอบ (preview) จะคืนผลผ่าน/ไม่ผ่านรายแถวพร้อมโทเคนอายุ 15 นาทีที่ผูกกับรายวิชาและผู้ใช้ จากนั้นขั้นยืนยัน (commit) จึงบันทึกเฉพาะแถวที่ผ่าน
- **การไม่แสดงผล 0% เมื่อข้อมูลไม่พอ** — endpoint ของแดชบอร์ดคืนรายการสาเหตุที่คำนวณไม่ได้มาด้วย เช่น "CLO ข้อ 3 ยังไม่มีกิจกรรมใดวัด" หรือ "น้ำหนักของกิจกรรมที่ 5 รวมได้ไม่ครบ 100" ทำให้หน้าจอไม่มีทางแสดง 0% โดยที่ความจริงคือข้อมูลยังไม่ครบ ซึ่งบังคับด้วยรูปแบบข้อมูลของ API เอง มิใช่ด้วยวินัยของผู้เขียนหน้าเว็บ

### 3.4 การออกแบบระบบความปลอดภัย

**การยืนยันตัวตน** — ใช้ JSON Web Token โดย access token อายุ 15 นาที และ refresh token อายุ 7 วัน รหัสผ่านเข้ารหัสด้วย argon2

**จุดสำคัญของการออกแบบ** — เมื่อตรวจสอบโทเคนผ่านแล้ว ระบบจะอ่านบทบาทและสถานะการใช้งานจาก **แถวข้อมูลผู้ใช้ที่เป็นปัจจุบัน** ทุกครั้ง มิใช่อ่านจากค่าที่ฝังอยู่ในโทเคน เพราะหากผู้ดูแลระบบลดสิทธิ์หรือปิดบัญชี ผู้ใช้นั้นจะต้องถูกปฏิเสธในคำขอถัดไปทันที ไม่ใช่รอจนโทเคนหมดอายุ

**การควบคุมสิทธิ์** แยกเป็นสองคำถามที่ต้องถามทั้งคู่บนทุกเส้นทางที่อ้างถึงรายวิชา

1. *ผู้ใช้มีบทบาทใด* — ตรวจโดย middleware ควบคุมสิทธิ์ตามบทบาท
2. *ผู้ใช้ถูกมอบหมายให้สอนรายวิชานี้หรือไม่* — ตรวจโดย `assertCourseAccess()` ซึ่งค้นหารายวิชาโดยมีเงื่อนไขว่าต้องมีผู้ใช้คนนี้อยู่ในรายชื่อผู้สอน หากไม่พบจะคืน **404 มิใช่ 403** เพราะการคืน 403 เท่ากับยืนยันว่ารายวิชานั้นมีอยู่จริง ซึ่งเป็นการเปิดเผยข้อมูลโดยไม่ตั้งใจ

### 3.5 ประเด็นที่ต้องให้อาจารย์ที่ปรึกษาชี้ขาด

**OI-10 — สูตรน้ำหนักในการคำนวณคะแนน CLO รายบุคคล**

ปัจจุบันมีการตีความน้ำหนักได้สองแบบ

- แบบที่หนึ่ง คิดน้ำหนักของกิจกรรมคูณกับน้ำหนักของเกณฑ์ในเมทริกซ์ แล้วหารด้วยผลรวมของน้ำหนักทั้งหมดที่มีคะแนนแล้ว
- แบบที่สอง คิดจากคะแนนที่ได้จริงเทียบกับคะแนนเต็มที่เป็นไปได้ของ CLO นั้นทั้งหมด

บนข้อมูลชุดเดียวกัน สองสูตรนี้ให้ค่าที่ต่างกันประมาณ **20 จุด** ซึ่งเปลี่ยนผลว่านักศึกษาผ่านหรือไม่ผ่าน CLO นั้นได้ทั้งกลุ่ม จึงต้องตัดสินใจก่อนเขียนโปรแกรมส่วนคำนวณ มิฉะนั้นจะไม่มีเกณฑ์ตัดสินว่าโปรแกรมคำนวณถูกหรือผิด

**OI-12 — นิยามนักศึกษากลุ่มเสี่ยงเมื่อยังไม่มีคะแนนใด ๆ**

หากถือว่า "ยังไม่มีคะแนน = เสี่ยง" ต้นภาคการศึกษาจะขึ้นเตือนทั้งห้อง ทำให้การเตือนไร้ความหมาย หากถือว่า "ยังไม่มีคะแนน = ยังไม่ประเมิน ไม่นับเป็นเสี่ยง" นักศึกษาที่ขาดเรียนต่อเนื่องจะไม่ถูกตรวจจับเลย ซึ่งเป็นกลุ่มที่โครงงานนี้ตั้งใจจะช่วย
