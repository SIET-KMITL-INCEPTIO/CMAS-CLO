## 2. ผลสัมฤทธิ์สำคัญในสัปดาห์ที่ผ่านมา

1. **ได้สถาปัตยกรรมของโครงงานที่พร้อมสำหรับการพัฒนาครบทุกด้าน** — ฐานข้อมูล · สถาปัตยกรรมระบบ · การไหลของข้อมูล · สัญญา API · ระบบออกแบบหน้าจอ · แผนผังเส้นทาง และชุดเครื่องมือพัฒนา ทุกส่วนมีไฟล์จริงที่ทีมหยิบไปเขียนโค้ดต่อได้ทันที ไม่ต้องตีความเพิ่ม
2. **ปิดข้อขัดแย้งเชิงขอบเขตที่ค้างมาตั้งแต่ต้นโครงงาน** — ตัดสินใจให้ระบบเป็นแบบใช้งานคณะเดียว (single-tenant) ทำให้โครงสร้างข้อมูลลดความซับซ้อนลงหนึ่งชั้น ขอบเขตการตรวจสิทธิ์เหลือระดับเดียวคือ *รายวิชา* และจำนวนหน้าจอลดจาก 15 เหลือ 13 หน้า
3. **ได้ต้นแบบระบบที่กดใช้งานได้จริง** ซึ่งทำหน้าที่เป็นข้อกำหนดที่ตรวจสอบได้ — ผู้ทรงคุณวุฒิและอาจารย์ที่ปรึกษาเห็นการไหลของงานจริงก่อนเขียนระบบ และทีมถอดโครงเมนู ฟอร์ม และสูตรคำนวณจากต้นแบบไปใช้ได้โดยตรง
4. **ผ่านการทบทวนต้นแบบกับผู้ทรงคุณวุฒิแล้ว 1 รอบ** — ข้อเสนอแนะ 14 ข้อถูกแปลงเป็นมติออกแบบ 7 ข้อ และแก้ต้นแบบไปแล้ว 7 เฟส เหลือประเด็นค้าง 2 เรื่องที่ต้องรอข้อมูลภายนอก
5. **ได้แบบจำลองการไหลของข้อมูลที่ใช้ทำ Threat Model ได้จริง** — DFD ชุดนี้ผ่านการตรวจตามกฎการเขียน DFD (black hole / miracle) และระบุถึงระดับ *ตาราง.คอลัมน์* ที่แต่ละเส้นแตะ จึงใช้เป็น input ของการวิเคราะห์ภัยคุกคามแบบ STRIDE ได้โดยไม่ต้องวาดใหม่
6. **ระบบเริ่มรันได้จริงจาก clean clone** — ติดตั้งด้วยคำสั่งเดียว ฐานข้อมูลสร้างจาก migration ได้ มีข้อมูลตัวอย่าง มีการตรวจคุณภาพโค้ดอัตโนมัติทุกครั้งที่ส่งงาน และมีหน้าจอชุดแรกที่เข้าสู่ระบบได้

## 3. รายละเอียดในการปฏิบัติงาน

> เนื้อหาส่วนนี้จัดทำเพื่อนำไปสรุปเป็น **บทที่ 3 (การวิเคราะห์และออกแบบระบบ)** ของปริญญานิพนธ์

### 3.1 ภาพรวมสถาปัตยกรรมของโครงงาน

ระบบออกแบบเป็น **โครงสร้างสามชั้นที่แยกการดีพลอยออกจากกัน (Decoupled Three-Tier)** ภายใต้ที่เก็บโค้ดเดียว (Monorepo) ด้วย npm workspaces

| ชั้น | ส่วนประกอบ | หน้าที่ | ปลายทางการติดตั้ง |
|---|---|---|---|
| **Presentation** | `app/client` — React 19 SPA | หน้าจอทั้งหมด · จัดการสถานะฝั่งผู้ใช้ · เรียก API ผ่าน REST | Vercel |
| **Application** | `app/server` — Fastify 5 API | ยืนยันตัวตน · ตรวจสิทธิ์ · ตรรกะทางธุรกิจ · กฎการคำนวณ · อ่าน/เขียนไฟล์ Excel | Railway / Fly.io |
| **Data** | PostgreSQL 15+ ผ่าน Prisma 6 | เก็บข้อมูลถาวร · บังคับความถูกต้องระดับฐานข้อมูลด้วย CHECK constraint และ trigger | Supabase |

**เหตุผลที่แยกสองแอปออกจากกัน:** ทั้งสองฝั่งแชร์กันเพียง *สัญญา API* และ *โครงสร้างฐานข้อมูล* จึงเปลี่ยนรุ่นและติดตั้งแยกกันได้ ไม่ต้องปล่อยงานพร้อมกัน และเมื่อฝั่งหน้าจอมีปัญหาก็ไม่กระทบการทำงานของ API

**เหตุผลที่เลือก SPA ไม่ใช่การเรนเดอร์ฝั่งเซิร์ฟเวอร์:** ระบบทั้งหมดอยู่หลังการเข้าสู่ระบบ ไม่ต้องการให้เครื่องมือค้นหาเข้าถึง จึงไม่มีประโยชน์ที่จะแลกความซับซ้อนของการเรนเดอร์ฝั่งเซิร์ฟเวอร์

### 3.2 การออกแบบฐานข้อมูล

**หลักการออกแบบ 4 ข้อ**

1. **ให้รายวิชาเป็นรากของลำดับชั้น** — เมื่อระบบใช้งานคณะเดียว ชั้นสถาบันและหลักสูตรไม่มีความหมาย จึงถูกตัดออก และรายวิชารับคุณสมบัติที่ชั้นหลักสูตรเคยถืออยู่ (หน่วยกิต ชั่วโมงเรียน รูปแบบเกรด) · ความไม่ซ้ำของรายวิชาคือ *รหัสวิชา + ภาคการศึกษา + ปีการศึกษา + หมู่เรียน*
2. **ให้บทบาทอยู่ที่ตัวผู้ใช้** — หนึ่งคนมีสถานะเดียวในคณะ จึงไม่ต้องเก็บบทบาทแยกรายสถาบัน ทำให้การตรวจสิทธิ์เหลือคำถามเพียงสองข้อ: *เป็นบทบาทใด* และ *ถูกมอบหมายในรายวิชาใดบ้าง*
3. **เก็บปีการศึกษาตามที่คณะใช้จริง** — บันทึกเป็นพุทธศักราชตรงตามที่ผู้ใช้กรอก คณะเดียวจึงมีธรรมเนียมเดียว ไม่ต้องมีคอลัมน์ระบุศักราชให้เกิดความสับสน
4. **นำข้อบังคับที่เครื่องมือ ORM เขียนไม่ได้ไปไว้ในสคริปต์ย้ายโครงสร้าง** — ข้อบังคับสามกลุ่มต่อไปนี้ต้องอยู่ในฐานข้อมูลเพื่อกันข้อมูลผิดที่เล็ดลอดผ่านชั้นแอปพลิเคชัน

| ประเภท | ตัวอย่างข้อบังคับ | เหตุผล |
|---|---|---|
| CHECK constraint | คะแนนต้องไม่ติดลบ · น้ำหนักอยู่ระหว่าง 0–100 · คะแนนเต็มต้องมากกว่า 0 · เกณฑ์ผ่านอยู่ระหว่าง 0–100 | ค่าที่เป็นไปไม่ได้ต้องเขียนลงฐานข้อมูลไม่ได้ ไม่ว่าจะมาจากทางใด |
| Trigger | คะแนนที่ได้ต้องไม่เกินคะแนนเต็มของกิจกรรม · กิจกรรมและนักศึกษาต้องอยู่ในรายวิชาเดียวกัน | เป็นกฎข้ามตาราง ซึ่ง CHECK constraint ธรรมดาตรวจไม่ได้ |
| ข้อห้ามเชิงปฏิบัติ | **ห้ามใช้คำสั่ง `prisma db push` ทุกสภาพแวดล้อม** | คำสั่งนี้ลบ constraint และ trigger ที่ ORM มองไม่เห็นออกอย่างเงียบ ๆ ต้องใช้ระบบ migration เท่านั้น |

**โครงสร้างข้อมูล 13 ตาราง** แบ่งได้เป็น 5 กลุ่ม

| กลุ่ม | ตาราง | สาระสำคัญ |
|---|---|---|
| ผู้ใช้และการยืนยันตัวตน | `User` · `EmailVerificationToken` | บทบาท (ผู้ดูแลระบบ / ผู้สอน) · สถานะใช้งาน · รหัสผ่านเข้ารหัสแบบทางเดียว · โทเคนยืนยันอีเมลสำหรับการสมัครด้วยตนเอง |
| รายวิชา | `Course` · `CourseInstructor` | ข้อมูลรายวิชาที่เปิดสอนจริงต่อภาคการศึกษา และการมอบหมายผู้สอน (ผู้สอนทุกคนในรายวิชามีสิทธิ์เท่ากัน) |
| โครงสร้างผลลัพธ์การเรียนรู้ | `CLO` · `BehavioralObjective` · `Activity` · `AssessmentCriteria` | หัวใจของการเชื่อมโยงอย่างสอดคล้อง (Constructive Alignment): ผลลัพธ์การเรียนรู้ → จุดประสงค์เชิงพฤติกรรม → กิจกรรมประเมิน → น้ำหนักของแต่ละคู่ |
| นักศึกษาและคะแนน | `Student` · `Score` · `ScoreUploadLog` | รายชื่อผู้ลงทะเบียน · คะแนนรายกิจกรรม · ประวัติการนำเข้าไฟล์ |
| การตัดเกรด | `GradeBand` · `StudentGrade` | ขั้นบันไดเกรดของรายวิชา และเกรดที่ตรึงค่าแล้วของนักศึกษาแต่ละคน |

**การออกแบบเรื่องเกรดที่ต้องแยกให้ชัด** — ระบบแยกสองแนวคิดที่มักถูกสับสนออกจากกัน

- **สเกลผลลัพธ์** คือรูปแบบที่รายวิชารายงานออกไป (ระดับตัวอักษร หรือ ผ่าน/ไม่ผ่าน) เพราะบางรายวิชาของคณะรายงานเป็นผ่าน/ไม่ผ่านเท่านั้น
- **วิธีหาเส้นแบ่งเกรด** คือวิธีคำนวณจุดตัด (อิงเกณฑ์ที่ประกาศล่วงหน้า หรือ อิงกลุ่มที่คำนวณจากการกระจายของผู้เรียนเอง) หน่วยของขั้นบันไดตามมาจากวิธีที่เลือกโดยอัตโนมัติ

### 3.3 การออกแบบการไหลของข้อมูล (Data Flow Diagram)

**กฎการเขียนที่กำหนดไว้ล่วงหน้า 5 ข้อ** เพื่อให้แผนภาพใช้วิเคราะห์ความปลอดภัยได้จริง ไม่ใช่เป็นเพียงภาพประกอบ

| กฎ | เหตุผล |
|---|---|
| สิ่งที่ยังไม่มีในโค้ดต้องทำเครื่องหมายว่าเป็นแผน | แผนภาพที่วาดจากความตั้งใจจะให้รายการภัยคุกคามที่ผิด |
| นักศึกษาไม่ใช่ผู้กระทำภายนอก | นักศึกษาเป็น *ข้อมูล* ไม่ใช่ผู้ใช้ระบบในรุ่นแรก แต่เป็นเจ้าของข้อมูลส่วนบุคคลตามกฎหมายคุ้มครองข้อมูล |
| ชั้นตรวจสิทธิ์ต้องเป็นกระบวนการแยกของตัวเอง | เพื่อให้มองเห็นภัยคุกคามที่เกิดจากเส้นทางที่ลืมต่อชั้นตรวจสิทธิ์ |
| ขอบเขตความเชื่อถือคือรายวิชา ไม่ใช่เครือข่าย | เพราะบังคับที่ชั้นแอปพลิเคชัน ไม่ใช่ที่ระดับเครือข่าย จึงต้องเขียนกำกับไว้ให้ชัด |

| 9.0 การตรวจสถานะระบบ | กระบวนการเดียวที่ไม่ต้องยืนยันตัวตน |
| 10.0 การวิเคราะห์ผลและออกรายงาน | คำนวณระดับการบรรลุผลลัพธ์การเรียนรู้ · ตัดเกรด · ออกรายงาน |

**ขอบเขตความเชื่อถือ 4 ชั้น** — ระหว่างเบราว์เซอร์กับเซิร์ฟเวอร์ · ระหว่างแอปพลิเคชันกับฐานข้อมูล · เขตที่ยังไม่ยืนยันตัวตน · และ**ขอบเขตรายวิชา** ซึ่งเป็นชั้นที่สำคัญที่สุดเพราะเป็นเส้นแบ่งข้อมูลชั้นเดียวที่เหลืออยู่หลังตัดสินใจใช้งานคณะเดียว

**ระดับ 2** — แตกสองกระบวนการที่ซับซ้อนที่สุด

1. **การนำเข้าไฟล์คะแนน** — รับไฟล์ → ตรวจชนิดและขนาด → อ่านเนื้อหา → จับคู่หัวคอลัมน์กับกิจกรรมในระบบ → ตรวจความถูกต้องทีละแถว → เขียนหรือปรับปรุงคะแนน → บันทึกสรุปผลการนำเข้า → ส่งรายงานข้อผิดพลาดกลับให้ผู้ใช้แก้
2. **การวิเคราะห์ผลและออกรายงาน** — อ่านคะแนน เกณฑ์การประเมิน และค่าที่ตั้งไว้ของรายวิชา → คำนวณตามกฎการคำนวณที่กำหนดไว้ → สรุปผลระดับชั้นเรียน → ระบุนักศึกษาที่ต้องติดตาม → ส่งออกรายงาน

**การนำไปใช้ต่อ** — แผนภาพชุดนี้ระบุถึงระดับ *ตาราง.คอลัมน์* ที่แต่ละเส้นทางแตะจริง จึงนำเข้าเครื่องมือวิเคราะห์ภัยคุกคามเพื่อออกรายการภัยคุกคามตามกรอบ STRIDE ได้โดยตรง

### 3.4 การออกแบบสัญญาการเชื่อมต่อ (API Contract)

| หัวข้อ | การออกแบบ |

| การตรวจสอบย้อนกลับ | มีตารางเทียบข้อกำหนดเชิงหน้าที่กับช่องทางเรียกใช้ทีละข้อ เพื่อพิสูจน์ได้ว่าไม่มีข้อกำหนดใดตกหล่นและไม่มีช่องทางใดที่ไม่มีข้อกำหนดรองรับ |
| ความปลอดภัยเชิงออกแบบ | ผู้สอนที่พยายามเข้าถึงรายวิชาที่ไม่ได้รับมอบหมาย จะได้รับคำตอบว่า *ไม่พบข้อมูล* ไม่ใช่ *ไม่มีสิทธิ์* เพราะคำตอบอย่างหลังเป็นการยืนยันว่ารายวิชานั้นมีอยู่จริง ซึ่งถือเป็นการรั่วไหลของข้อมูล |

### 3.5 การออกแบบส่วนติดต่อผู้ใช้

**ระบบการออกแบบ (Design System)** — จัดทำเป็นเอกสารมาตรฐาน 15 หมวด ครอบคลุมเอกลักษณ์ของระบบ · ระบบตัวอักษร · ระบบสี · สีบอกสถานะ · ระยะห่างและรูปทรง · ระดับความสูงและเงา · ชุดไอคอน · คอมโพเนนต์ · การเคลื่อนไหว · การเข้าถึงสำหรับผู้พิการ · ตารางอ้างอิงค่าออกแบบ · การใช้สีตามความหมายในบริบทการศึกษา · การลากวางเพื่อจัดลำดับ · หลักการโต้ตอบให้รู้สึกเหมือนโปรแกรมบนเครื่อง และเมนูคลิกขวา

**ต้นแบบที่กดใช้งานได้จริง** — พัฒนาเป็นไฟล์เดียวที่เปิดได้โดยไม่ต้องติดตั้งเซิร์ฟเวอร์ ประกอบด้วย 9 หน้าจอ · 7 กลุ่มข้อมูลที่เพิ่ม แก้ไข และลบได้ · ข้อมูลตัวอย่าง 4 รายวิชา 30 การลงทะเบียน และ 120 แถวคะแนน ทำหน้าที่เป็นข้อกำหนดที่ตรวจสอบได้ด้วยการกดใช้งาน แทนการอ่านเอกสารแล้วตีความ

**แผนผังหน้าจอของระบบจริง 13 หน้า**

| กลุ่ม | หน้าจอ |
|---|---|
| ระดับระบบ | หน้าแรก · เข้าสู่ระบบ · จัดการผู้ใช้งาน · รายการรายวิชา · สร้างรายวิชา |
| ระดับรายวิชา | ภาพรวมรายวิชา · กำหนดผลลัพธ์การเรียนรู้ · กิจกรรมและเกณฑ์การประเมิน · รายชื่อนักศึกษา · คะแนน · ประวัติการนำเข้าไฟล์ |
| การรายงานผล | แดชบอร์ดสรุปผล · รายงานรายบุคคล |

**เส้นทางการใช้งานหลักที่ออกแบบไว้ 3 เส้น** — (1) ตั้งค่ารายวิชาครั้งแรกจนถึงเห็นแดชบอร์ด (2) การนำเข้าคะแนนที่ตั้งเป้าให้ทำได้ภายใน 10 นาที (3) การอ่านผลและติดตามนักศึกษารายบุคคล · ทุกหน้าจอถูกตรวจครบ 4 สถานะ (ยังไม่มีข้อมูล · กำลังโหลด · มีข้อมูล · เกิดข้อผิดพลาด)

**ผลการทบทวนกับผู้ทรงคุณวุฒิ** — ข้อเสนอแนะ 14 ข้อถูกแปลงเป็นมติออกแบบ 7 ข้อ ที่ส่งผลย้อนกลับไปถึงโครงสร้างฐานข้อมูล เช่น การยุบบทบาทผู้สอนให้เหลือระดับเดียว และการเปิดให้ผู้สอนสมัครบัญชีเองแล้วยืนยันผ่านอีเมลเฉพาะโดเมนของคณะ ซึ่งทำให้ต้องเพิ่มตารางโทเคนยืนยันอีเมลเข้าไปในโครงสร้างข้อมูล

### 3.6 ชุดเครื่องมือพัฒนาและโครงสร้างโปรเจกต์

| ชั้น | เครื่องมือที่ยืนยันแล้วในโค้ดจริง | เหตุผลที่เลือก |
|---|---|---|
| ส่วนติดต่อผู้ใช้ | React 19 · React Router 7 · Vite 7 · TypeScript | ระบบอยู่หลังการเข้าสู่ระบบทั้งหมด จึงใช้รูปแบบหน้าเดียวได้เต็มที่ · Vite ให้รอบการพัฒนาที่เร็ว |
| การจัดรูปแบบหน้าจอ | Tailwind CSS 4 · shadcn/ui · Recharts | ค่าออกแบบชุดเดียวใช้ได้ทั้งระบบ · ได้กราฟสำหรับแดชบอร์ดโดยไม่ต้องเขียนเอง |
| การจัดการสถานะ | TanStack Query (ข้อมูลจากเซิร์ฟเวอร์) · Zustand (สถานะการเข้าสู่ระบบเท่านั้น) | แยกข้อมูลที่มาจากเซิร์ฟเวอร์ออกจากสถานะของหน้าจอ ลดปัญหาข้อมูลค้างไม่ตรงกัน |
| เซิร์ฟเวอร์ | Node.js รุ่นสนับสนุนระยะยาว · Fastify 5 · TypeScript | เร็วกว่าและมีการตรวจสอบรูปแบบข้อมูลในตัว |
| ความปลอดภัย | ส่วนเสริมด้านส่วนหัวความปลอดภัย · การจำกัดต้นทาง · การจำกัดอัตราการเรียก · โทเคนอายุสั้นคู่โทเคนต่ออายุ · การเข้ารหัสรหัสผ่านแบบ argon2 | ครอบความเสี่ยงพื้นฐานตามรายการช่องโหว่ที่พบบ่อย |
| การตรวจสอบข้อมูลนำเข้า | Zod | นิยามรูปแบบข้อมูลชุดเดียวใช้ได้ทั้งการตรวจสอบและการกำหนดชนิดข้อมูล |
| การอ่านเขียนไฟล์ตาราง | SheetJS | คณะทำงานด้วยไฟล์ตารางอยู่แล้ว การนำเข้าและส่งออกจึงเป็นความสามารถหลัก |
| การเข้าถึงฐานข้อมูล | Prisma 6 · PostgreSQL | ตรวจชนิดข้อมูลได้ถึงระดับคำสั่งค้นหา ลดข้อผิดพลาดตอนเขียนโค้ด |
| เครื่องมือประกอบ | ที่เก็บโค้ดเดียวแบบหลายพื้นที่ทำงาน · ตัวตรวจรูปแบบโค้ด · ตัวจัดรูปแบบ · ชุดทดสอบ · คอนเทนเนอร์ | มีคำสั่งตรวจรวมคำสั่งเดียวที่ต้องผ่านก่อนส่งงานทุกครั้ง |

**โครงสร้างไดเรกทอรีและมาตรฐานการตั้งชื่อ** — ฝั่งเซิร์ฟเวอร์ใช้สถาปัตยกรรมแบบแบ่งชั้น โดยแต่ละชั้นมีเอกสารกำกับสัญญาของตัวเองอยู่ในโฟลเดอร์

| ชั้น | หน้าที่ที่อนุญาต | สิ่งที่ห้ามมี |
|---|---|---|
| เส้นทาง (routes) | ลงทะเบียนเส้นทางและต่อชั้นตรวจสิทธิ์เท่านั้น | ตรรกะทางธุรกิจ |
| ตัวควบคุม (controllers) | รับคำขอ ส่งคำตอบ | การเข้าถึงฐานข้อมูลโดยตรง |
| บริการ (services) | ตรรกะทางธุรกิจและกฎการคำนวณทั้งหมด | การอ้างถึงรูปแบบของคำขอหรือคำตอบ |
| ตัวตรวจสอบ (validators) | นิยามรูปแบบข้อมูลที่ยอมรับได้ต่อทรัพยากร | — |
| ชั้นกลาง (middlewares) | ยืนยันตัวตน ตรวจบทบาท จัดการข้อผิดพลาด | — |
| ไลบรารีภายใน (lib) | ค่าตั้งต้นจากสภาพแวดล้อม การเชื่อมต่อฐานข้อมูล โทเคน ตัวช่วยสร้างคำตอบ | — |

ฝั่งหน้าจอกำหนดให้การเรียก API เกิดขึ้นในชั้นตะขอข้อมูล (hooks) เพียงชั้นเดียว เพื่อคุมการเก็บชั่วคราว การลองใหม่ และการจัดการข้อผิดพลาดไว้ที่จุดเดียว

### 3.7 กฎสถาปัตยกรรมที่บังคับใช้กับทุกคนในทีม

| กฎ | เหตุผลที่ต้องเป็นกฎ ไม่ใช่ข้อแนะนำ |
|---|---|
| ทุกคำขอที่ต้องยืนยันตัวตนต้องอ่านข้อมูลผู้ใช้สดจากฐานข้อมูลทุกครั้ง | บัญชีที่เพิ่งถูกระงับต้องใช้งานไม่ได้ทันที ไม่ใช่รอจนโทเคนหมดอายุ |

| กฎการคำนวณทั้งหมดต้องอยู่ที่เดียว | ป้องกันการคำนวณซ้ำคนละที่แล้วได้ตัวเลขไม่ตรงกัน ซึ่งทำให้ผลการประเมินเชื่อถือไม่ได้ |
| ห้ามใช้คำสั่งผลักโครงสร้างฐานข้อมูลโดยตรง | จะลบข้อบังคับและตัวกระตุ้นในฐานข้อมูลออกอย่างเงียบ ๆ |
| เส้นทางตรวจสถานะระบบเป็นเส้นทางเดียวที่ไม่ต้องยืนยันตัวตน | ทุกอย่างที่เหลือถือว่าต้องเข้าสู่ระบบ เป็นค่าตั้งต้นที่ปลอดภัยกว่า |

| มีการตรวจคุณภาพอัตโนมัติก่อนรวมโค้ด | ✅ | สายงานตรวจอัตโนมัติ: จัดรูปแบบ · ตรวจรูปแบบโค้ด · ตรวจชนิดข้อมูล · ทดสอบ · สร้างไฟล์ติดตั้ง |
| มีโครงหน้าจอและเส้นทางตัวอย่างที่ทำงานได้จริงแล้ว | ✅ | หน้าเข้าสู่ระบบ จัดการผู้ใช้ รายการรายวิชา และเส้นทางตรวจสถานะระบบ |
| ข้อตัดสินใจเชิงออกแบบที่ค้างอยู่ ไม่บล็อกการเริ่มพัฒนา | ⚠️ มีข้อค้าง 4 เรื่อง | ดู §3.9 — ทั้งหมดอยู่ในส่วนการคำนวณและการแสดงผล ไม่กระทบโครงสร้างข้อมูลหรือสัญญาการเชื่อมต่อ |

### 3.9 ข้อตัดสินใจที่ยังค้างและผลกระทบ

| ประเด็น | ผลกระทบ | กำหนดที่ต้องได้ข้อสรุป |
|---|---|---|
| ยังไม่ชี้ขาดว่าจะใช้สูตรถ่วงน้ำหนักแบบใดในการคำนวณระดับการบรรลุผลลัพธ์การเรียนรู้ — สองสูตรให้ผลต่างกันถึง 20 จุดบนข้อมูลชุดเดียวกัน | เขียนชุดทดสอบของส่วนคำนวณไม่ได้ เพราะยังไม่ทราบว่าคำตอบที่ถูกคือค่าใด · กระทบการพิสูจน์สมมติฐานข้อแรก | ก่อนเริ่มพัฒนาส่วนวิเคราะห์ผล (ต้น พ.ย. 2569) |
| ยังไม่นิยามว่านักศึกษาที่ยังไม่มีคะแนนเลย ถือเป็นกลุ่มเสี่ยงหรือไม่ | กระทบการระบุนักศึกษาที่ต้องติดตาม ซึ่งเป็นความสามารถหลักที่ตอบสาเหตุรากของโครงงาน | พร้อมกับประเด็นข้างต้น |
| ยังไม่สรุปว่าน้ำหนักของผลลัพธ์การเรียนรู้ให้ผู้สอนกรอกเอง หรือให้ระบบคำนวณจากกิจกรรม | กระทบหน้าจอกำหนดผลลัพธ์การเรียนรู้ และกฎการคำนวณน้ำหนัก | ก่อนเริ่ม Sprint 3 (5 ต.ค. 2569) |
| ชื่อระดับของกรอบการจำแนกพฤติกรรมที่คณะใช้ ยังรอเอกสารต้นทาง | ออกแบบหน้าจอให้สลับกรอบได้โดยไม่ผูกตายไว้ก่อน — ระดับที่ผิดแย่กว่าไม่มีระดับ | เมื่อได้รับเอกสารจากคณะ |
